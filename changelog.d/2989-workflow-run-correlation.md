### Added

- **One shared seam for Cloudflare workflow instance starts (Qunsultant/cfagent#2989):** `src/workflows/workflowInstanceSeam.ts` now owns the create → adopt → fallback algorithm every workflow start rides — screener (`CfWorkflowAdapter`), saga legs (`sagaLegPort`), saga entry, and payment binding starts — replacing three hand-rolled variants (plus the direct `binding.create` calls). The seam persists the ACTUAL instance id used at start (derived or fallback) as the correlation id on the job record: `ShardJobRow.workflowRunId` (new nullable column via migration 0038, carried through screener child rows, saga entry projection rows, and saga payment-leg audit rows as `paymentWorkflowId`), the manual goal-submit audit (mirroring the scheduled path), and a new best-effort `trade.approval_started` audit. The Cloudflare workflow id IS the instance id — `create()` returns only `instance.id` and `status()` returns only status/output/error — so no second identifier is invented. The payment `PaidSubmissionRecord` stays as the commercial idempotency record (first-record-wins guards double-charge, which binding create-or-adopt does not provide); its workflow id now comes from the seam. Not covered: `mas_async_jobs` (proven: no workflow start writes it), outcome rows (correlated by join on job id, not stamped), and host-door starts' create step (payment/trading SDK host code — recorded through the seam's convention instead).
- **Migration pins updated for 0038 (Qunsultant/cfagent#2989):** the mesh golden-tasks, mesh RSI-pipeline, and mesh traces pins now expect migration 0038 as the latest (was 0037), following the same-PR pin rule; one #2989 comment in workflowPorts.ts reworded provider-neutrally to satisfy the port-purity pin.
