### Added

- **Options publishes its three stage boundaries, and only when the evidence exists (#3072, #3069 S2/R1/R2):** an options screen is a request handler, not a durable workflow — there is no `step.do` to point a message at. `emitOptionsStageBoundaries` therefore publishes **once at the end of a successful run**, in phase order (`provider-screen`, `report-pipeline`, `deliver`), each referencing the artifact that actually exists: the canonical report row (`generationId`), the report key the pipeline returned, and the recorded delivery states. A phase with no artifact publishes nothing and says why — a boundary is evidence, not a progress bar. A run that fails before its artifacts land publishes nothing at all, which is the honest outcome. Wired into `executeOptionsScreen` behind the same degradation rule as every other family: a seam gap never turns a completed screen into a failed request.
