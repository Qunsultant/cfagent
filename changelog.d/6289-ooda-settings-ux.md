### Changed

- **The OODA settings page manages and displays the one execution configuration (#5975 UX slice, sub-issue #6289):** the per-stage execution modes that a run resolves are editable on the existing settings card (`?tab=options-screener&view=ooda` → `ResearchRunsPanel`), saved through the same `POST /api/research/settings` as `stageModes` — six stages × four axes, an empty axis means **inherit**, and the effective value with its source (stored override or deployment default) is shown under each box. The stage, axis and venue lists are **served** (`GET /api/research/settings` → `execution`, built from `RESEARCH_STAGE_KINDS`, `EXECUTION_MODE_AXES`, `ROUTED_BROKER_IDS`, `RESEARCH_VENUE_MODES`), so the panel holds no second copy; a broken deployment default is reported beside the read instead of failing it, and the stored map still governs. The two free-text **Broker / venue** and **Mode** boxes are replaced by `Select`s over the catalogue with an explicit tenant default, and the page states the effective venue it will use. A validation refusal is now rendered verbatim — the 400 previously surfaced as "Save failed: HTTP 400" because the panel assumed a 200-with-errors. No new endpoint, no new store, no second mode model. #COO-spr9
