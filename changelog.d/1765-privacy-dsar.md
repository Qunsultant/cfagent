### Added

- Privacy/DSAR surfaces (#1765, #1717 slice F-41 / PRV-001–PRV-004 / PRV-006): session-gated `GET /api/privacy/status` (ADMT pre-use notice + Sec-GPC state + effective preferences), `GET`/`POST /api/privacy/preferences` (ADMT opt-out + sale/sharing opt-out, boolean fields only, GPC forces opt-outs on), `GET /api/privacy/export` (consolidated subject-scoped JSON payload with per-source coverage), and `POST /api/privacy/erasure` (automated erasure cascade with a per-leg report; the response clears the caller's session cookie). One scoped switch, `PRIVACY_DSAR_MODE` (standard|strict, run > session > user > env > built-in standard, invalid fails closed with a privacy.config_error audit; no production value set). A shared retention registry (`src/privacy/privacyDsar.ts`: mas_messages, screener_runs, research_runs, 30-day bound) is the extension point the #1766 slice builds on — no second retention mechanism. Pinned by `tests/privacy_dsar_1765.test.ts` (TDD red-first, 18 tests) and the endpoint-catalog pin. Honest boundary, named not hidden: the production cascade's DO legs (Orchestrator/Research/Screener) and Vectorize are registered as deferred — no per-subject delete RPC or vector key exists on current main — so a production erasure report reads complete=false until one eraseSubjectData callable per DO lands (follow-up); export sources without a per-subject server read path are listed as not_wired in coverage, never implied included; and other sessions of the same subject cannot be enumerated (KvLike has no list), so erasure clears the caller's own session only.
