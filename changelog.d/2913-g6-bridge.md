### Changed

- **One delivery bridge + durable (runId, destination) suppression, G6 (#2913, under #2764):** the bridge is now defined once — `scheduleScreenerFollowups` → main job → report job → one `followup.deliver` job per channel → the followup delivery port, with pipeline-policy gates and suppression in the executor — and the suppressor's store is durable: a `mas_delivery_claims` table in the DO SQLite store, wired by the orchestrator's `asyncJobsContext` (lazily ensured, so building a context never eagerly touches SQL), so a claim survives an instance eviction and a resubmitted deliver job is suppressed across instances. The table's SQL lives in `src/data/deliveryClaimsStore.ts`, the data-layer home for this table (the global D-D census pins above-layer exec sites as shrink-only, so new SQL belongs in `src/data/`). The REST bridge stamps outcomes with the stable deliveryId the legacy fallback already uses (`manual:<timestamp>:<universe>`), so a bridge delivery and a legacy-fallback delivery for one run share one suppression key. Named exceptions, unchanged: the legacy `publishManualScreenerRun` fallback runs only when `scheduleScreenerFollowups` is absent (and shares the key space, so it cannot double-deliver against the bridge); goal/discovery/recommendation content is delivered by the #1162 `screeningDelivery` module (different draft research content with its own senders, not run reports); market-data screens are persist-only by design (Slice 1 spec, no deliver step); options delivery paths are a separate domain and untouched. A deliver job carrying no deliveryId at all is still keyed by its own job id, with the `mas_async_jobs` completion marking as the durable guard against re-execution.
