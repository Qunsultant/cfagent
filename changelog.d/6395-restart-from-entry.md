### Added

- **Restart from a named journal entry (#6395):** the checkpoint was the only resume point an operator had, so a fault three stages back forced a whole-job re-run even though the platform already holds every journaled step result. `restartFromJournalEntry(jobId, runId, entryId)` is the general form of #6552's stage rewind: a journal entry and a step execution id are the same name by construction (`stepExecutionId`), so the operation hands the named entry to the platform's `restart({ from: { name } })` and the flow replays with earlier results reused. Addressability is proved against the run's own record, never guessed — the id's run segment must be this run and its stage segment must be a stage the run recorded — otherwise `journal_entry_not_addressed`. The run's pinned definition version executes (#5278, reused): `resume_pre_retention_run` and `resume_definition_version_unresolved` refuse rather than running today's configuration against a half-executed run. The `restart` stage event is published only after the platform accepts the rewind, naming the entry. Pins: `tests/restart_from_entry_6395.test.ts`; the engine reference (§3.10) states the operation beside the stage rewind.
