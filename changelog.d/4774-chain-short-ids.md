### Chain short ids (#4774)

- Name every chain shape by its ruled short id: `stockscr` (screener chain), `optionsscr` (options chain), `goalscr` (goal screen), `strategyscr` (strategy discovery), `feedsrc` (feed chain). Catalog ids, job ids, and tool names are unchanged; the short ids ride as aliases in the workflow catalog, the job-definition spec, the feed-chain catalog entries, and the options-chain leaf, and surface in the catalog panel and the Data Providers feed-chain section.
- No behavior change: resolution, schedules, and run records are untouched.
- Scope extension (user ruling, #4774 comment 6959360479): the short-id system now covers all execution-tree levels (`src/services/executionTreeIds.ts` — `chain` / `pipe` / `wf` / `job` / `stage` / `unit` / `task` / `run` / `txn`, one printable id per instance as `<level>:<local-id>`). Stage/step execution ids reuse the engine's existing `job-stage:` event-id prefix and `job-step:` journal-id shape — no new formats invented. The OODA ambiguity is resolved by level: candidate-loop steps are `ooda:*`, run-level research stages are `respipe:*`, and each trace entry carries its qualified `shortId` (bare stage strings unchanged). Every run/transaction instance already carries a unique id (engine `run-*`, research `rsr_*`, async-job UUID, ledger `id` PK); a trace step's instance id is derived, not stored.
- Not in this slice: the research run's engine onboarding (#5109, CFO lane) — the engine job id (`research:<runId>`) and data ports landed (#5121); the trigger dispatch (#5120) and cutover flag (#5122) are recorded merged; the analyze.ooda step registration (#5118, PR #5143 open), AOP compliance (#5119, PR #5144 open), and Copilot execution (#5123, no PR) remain. The `ooda:` / `respipe:` ids are names the #5118 step registration can reuse; CLO-arsi does not build it.
