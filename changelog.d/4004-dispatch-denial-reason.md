### Fixed

- **A dispatch denial now says what to do about it (#4004, incident #4003):** `schedule.dispatch_denied` recorded the reason code and (sometimes) a detail, but the schedules audit trail rendered neither — an operator saw four denials for the stock screen with no way to tell an unowned schedule from a revoked membership. The audit payload now carries an `action` per reason (`NO_IDENTITY`, `SHARED_ADDRESS`, `SERVICE_NOT_CONFIGURED`, `SERVICE_NOT_PROVISIONED`, `SERVICE_TENANT_MISMATCH`, `BROKER_REQUIRED`, `OWNER_MEMBERSHIP_REVOKED`, `PDP_DENIED`), and the audit trail renders a Reason column (reason code, with detail and action on hover). The denial pin in `tests/serviceDispatchCallbacks.test.ts` now asserts the actionable field so a future reason cannot ship without it.

- **A recorded instance address no longer shadows the authenticated owner (#4004, incident #4003):** `resolveScheduledLogin` preferred `payload.userLogin` unconditionally. A legacy schedule record whose payload carried `shared_orchestrator` / `default_trader` (or a malformed value) therefore resolved a principal the dispatch gate refuses by design, and every firing denied `SHARED_ADDRESS`/`NO_IDENTITY` while the per-instance context stored by the last signed-in request held a real owner. Resolution now prefers a usable login: the payload when it can be a principal, otherwise the saved context, otherwise the recorded value unchanged so the audit still names the real reason. Pinned by `tests/schedule_owner_resolution_4004.test.ts` (6 tests, including the incident case resolving as an owner through `resolveDispatchCandidate`).
