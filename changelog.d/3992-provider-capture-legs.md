### Added

- **Feed-job provider + capture legs timeout (#3992 PR-3):** the provider-fetch awaits in `src/services/feedJobs.ts` are now raced against the PR-1 substrate bound `FEED_JOB_TIMEOUTS.fetchMs` (60s) via `withFeedDeadline`, and the run-record store write inside each runner's `record()` is raced against `FEED_JOB_TIMEOUTS.captureMs` (30s). A fetch that never settles no longer hangs a feed run forever with nothing recorded: the quotes runner's single batch await records exactly one failed run coded `FEED_FETCH_TIMEOUT` (distinctly from `FEED_FETCH_FAILED`, a fetch that threw), and the per-symbol loops of the fundamentals, technicals, and sentiment runners share ONE whole-loop deadline — each symbol races with the remaining budget, a timed-out symbol is missing with the timeout named, and once the budget is exhausted no further fetch starts (the remaining symbols are marked missing in one pass), so in-loop progress survives as a partial run and a run that fetched nothing fails with its existing no-data code and the timeout named as the cause. A store write that never settles is answered by exactly one degraded fallback write — same run id, a failed empty record coded `FEED_CAPTURE_TIMEOUT` — and if the fallback also fails, the run still settles with `FEED_CAPTURE_TIMEOUT` and an empty artifact id (never a fabricated one); a store that throws keeps propagating its original error exactly as before. All four runners (quotes, fundamentals, technicals, sentiment) carry both bounds the same way. The sentiment classification batches are NOT bounded in this PR — they are covered by the pipeline-level execution deadline in PR-4 — and the refresh leg remains as bounded in PR-2.
