### Added

- **Feed-job whole-execution deadline (#3992 PR-4):** a feed job's execution tree in the pipeline engine (`src/services/jobPipelineEngine.ts`) is now raced against a whole-run bound — `FEED_JOB_TIMEOUTS.executionMs` (240s) from the PR-1 catalogue, overridable per host through the new optional `JobPipelineDeps.feedExecutionDeadlineMs` (resolved by the exported `resolveFeedExecutionDeadlineMs`: a positive finite value wins; absent, non-positive, or non-finite takes the catalogue value, so hosts that never set it are bounded by default). A feed run whose legs each settle slowly — or whose sentiment classification batches run long — can no longer exceed every per-leg bound indefinitely: past the bound the run settles FAILED with `FEED_DEADLINE_EXCEEDED` named in the dispatch outcome, the job instance's `lastError`, and the terminal run record, through the engine's one existing failed-settle path. The guarantee is exactly one terminal outcome per run: the race abandons the execution (it is not aborted — a timed-out execution keeps running in the host, the abandon-not-abort idiom of the substrate), and its late writes land in the step journal and the feed dataset store, never in the settled run's terminal path, so the recorded outcome cannot flip. Busy truthfulness follows from the durable instance state: while a run is genuinely live a second dispatch still refuses with `job_already_running`, and after a deadline settle the same job dispatches a fresh run immediately — the deadline unwedges the job instead of wedging it. Deliberate exclusions: the bound applies to feed jobs only (a job is a feed job when any node in its definition tree invokes the `feed.pull` step; non-feed jobs are unbounded by this PR), stage-level actions (`executeStageAction`) are not wrapped, and where a timed-out execution physically runs to completion — its residency — is PR-5's question.
