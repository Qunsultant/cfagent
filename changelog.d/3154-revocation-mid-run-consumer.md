### Added

- Revocation-mid-run consumer (#3154, parent #945 Q6): runs whose owner was revoked now deny at the next check instead of running on. New `src/security/runRevocationGate.ts` (`recheckRunAuthority` pure gate + `enforceOwnerDispatch` seam helper) hooks the existing guard/dispatch seams: scheduled-callback dispatch (`resolveCallbackDispatch` owner branch) and async-job execution (`executeAsyncJob`, which is also the pipeline-stage boundary since every stage re-executes through it). A denied run audits the denial (`schedule.dispatch_denied` / `async_job.dispatch_denied` + `async_job.failed`), preserves the schedule (never deletes it), and fails closed; a denied job never reaches a capability leg. Denial needs positive revocation evidence only (membership records exist but none live, where live mirrors `serviceDispatch.ts`: `revokedAtMs` undefined + a live binding); unresolvable logins, empty membership lists, missing stores, and lookup failures preserve pre-existing behavior (allow, logged) rather than fabricating a denial. New denial reason `OWNER_MEMBERSHIP_REVOKED`. Approval-consumer inventory + bridge: every inventoried approval-consumer shape validates through `lifecycle.ts validateApproval` (directly for lifecycle Approval records; via `validateWorkflowApprovalViaLifecycle` for workflow approval decisions, with revoked approver → `APPROVAL_REVOKED`, changed terms → `PROPOSAL_CHANGED`, unverifiable approver → `INVALID_APPROVAL` fail-closed). Wiring the bridge into the trade/payment settle paths is a named follow-up (money paths, CTO+CISO review); the run-path consumers are wired in this slice. No change to #1750 target values, the Q6 measure table, or the legacy-session §8 bound; no new revocation triggers.
