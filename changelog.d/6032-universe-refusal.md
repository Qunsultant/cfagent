### Fixed

- **An unresolvable universe refuses by name instead of publishing an empty run (issue #6032):** `resolveUniverse("ALL", …)` returned `[]` ("sharded by caller — never resolved directly") and the research provider `.map`ped it, so selecting `ALL` or a typo'd universe (`dow`, `sp400`, `NASDAQ 100`) produced a **published** report reading "Universe retrieval failed; no candidates evaluated" — indistinguishable from a genuine zero-qualification night and naming no id. The accepted set is now one declaration (`researchUniverseIds()`: the screener registry minus `ALL`); `ALL` refuses as *"a shard plan is not resolvable for a single run"*; an unknown id refuses with `research_universe_unknown` before any listings read or quote attempt. `ResearchConfig.universe` validates against the same set (the settings POST answers `400` with the accepted ids), the settings GET serves the set, and the filter editor renders Universe as a select fed from that response — no client-side universe list. The run's report carries `dataRefusal: { code: "research_universe_unknown", message }` and a summary naming the id, so a legacy stored value fails visibly instead of publishing a plausible zero. Pinned by `tests/research_universe_refusal_6032.test.ts` (accepted set, normalisation, `ALL`, unknown id, the eight universes still resolving, config validation, the editor select) and `tests/research-pipeline.test.ts` (a refusing universe → coded refusal, zero quote calls). The selectable set is not expanded here: `dow`, `sp400`, `russell1000`, `russell3000` and the 11 sectors stay out until #3667's `IndexMembershipPort` integration lands.
