### Added

- **Scheduling consolidation Slice #3310 — per-stage workflow scheduling (#3121):** one workflow stage can now be scheduled on its own — a fifth unified-store kind (`workflow-stage`, record id = alarm id, the #3123 screen precedent) whose firing is the internal-only callback `runWorkflowStage` (recorded via the #2964/#3788 wrapper, never agent-creatable): SDK alarm → OrchestratorAgent host method → ScheduledAgent door `runPipelineStage` → `runJob` scoped to the stage, with the dispatching schedule id threaded through the engine and stamped on the terminal record (`run_schedule_id`, probed ADD COLUMN — the DO migration framework cannot express a conditional ADD COLUMN, so the column rides `ensureSchema` in both modes; D1 keeps versioned v59) alongside `workflowId` (the pipeline run id) and explicit-null `asyncJobId`. Creation is one route (`POST /api/schedules/workflow-stages`) plus the #3122 capability (`workflow-stage` kind, PDP + approval gate + provenance + ledger) plus the `schedule.*` A2A ops (optional `kind` arg, no new ops); pause/resume/trigger/delete/update flow through the existing `/:id/*` routes, and the Schedules home lists stage-schedules (workflow + stage named). The config-declared node schedules keep firing through the Think declarations (unchanged); their runs now stamp the Think task id as `scheduleId`. No create form on the home (#2329 — creation is API + agent channels), no unification of Think declarations into the unified store, no whole-workflow schedules in the unified store, no stage-scheduling for a workflow with no stage registry, no NLQ planner support for stage-schedules — each filed as an [Out-of-Scope] sub-issue under #3310 (Qunsultant/cfagent#4229, #4230, #4231, #4232, #4233). #3121
