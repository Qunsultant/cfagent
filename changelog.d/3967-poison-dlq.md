### Added

- **Poison runs land in the operator's DLQ (#3967):** the engine already refused to retry a coded failure that can never succeed, but "dead-letter" only meant "do not retry" — the run was marked terminal-failed and the operator had the error, not the material to act on it. A poison unit now hands the host a `JobPoisonLanding` (job, run, node path, stage, unit, code, message), which the host maps onto the platform's one dead-letter store as source `job-pipeline`, reason `poison_run` — the same surface the queue drops land in (`GET /api/ops/dlq/records`). The record carries no envelope, so queue replay refuses it (`no_envelope`) instead of pretending to re-drive a run; the remedy is the retry route, which starts a fresh run on the current definition. Best-effort by contract: a failing sink is logged and swallowed, so the run's own coded error is never masked, and a host with no sink keeps the old behaviour exactly. Pins: `tests/job_poison_dlq_3967.test.ts`; the engine reference (§3.9) and the DLQ runbook state the landing and the re-drive route.
