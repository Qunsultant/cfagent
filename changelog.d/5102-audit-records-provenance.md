### Added

- **Every run, trade, report, and delivery record carries the binding it executed against (#5102, F5 of #5094):** `JobRunRecord` gains the four binding fields (`accountType` / `accountId` / `bindingScope` / `bindingSource`) in D1 (migration 0084), DO-SQLite, and in-memory stores — new rows stamped, legacy rows read as explicit nulls, no backfill; the builder rejects poisoned `"undefined"`/`"null"` literals like the linkage ids. Run summaries ride the run row (canonical reports inherit their D1 ledger twin's tuple in the merge), delivery runs carry their generating run's tuple, and `GET /api/runs` + `GET /api/workflow-runs` take a binding filter (invalid value is a 400, never a silent empty page). Every surface renders the tuple masked only — a masked Account column per row on the run ledger, Docs & Reports, and the trade ledger, a masked binding cell per brokered audit event, and a masked `accountId` in the run-details provenance. The screener CSV bytes are unchanged (its columns mirror the XLSX tab and the module forbids comment lines); the engine's own `job-pipeline` terminal records still read unbound pending a follow-on to thread the dispatch binding through the instance schema. #cpo-dhmp
