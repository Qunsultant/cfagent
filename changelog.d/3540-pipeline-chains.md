### Added

- Pipeline J7 (#3540, epic #3533 capstone): the composed pipeline chains — one J1 job per quotes lineage whose nested nodes ARE the lineage's five stage jobs' own definitions (feed → enrich → analyze → generate → deliver, plus the Yahoo fundamentals feed node the enrich join declares), derived from the stage registries at every ensure and re-derived from the stored stage definitions on every chain read/dispatch, so a stage job reconfigured through the control plane flows into its chain and the chain can never drift into a forked copy of a stage's parameters. The stages compose nested — each stage the single child of the stage before it — which is the shape the engine's persisted hand-off rule assumes, so the uniform stage operations (#3549) resolve a real hand-off at every stage of the chain. One chain schedule (the `PIPELINE_CHAIN_<ID>_CADENCE_MINUTES` knob, defaulting to the head feed job's cadence) drives the whole chain as one pipeline (32 declared pipeline tasks on the host); every stage job keeps its own schedule, configuration, and management surface unchanged, and a chain job's completion dispatches nothing through the completion intake (the chain already ran its stages). The end-to-end status roll-up answers "where is today's pipeline?" as ONE query on both surfaces: per-stage states aggregated from the chain run's stage ledger (the fundamentals node folds into the feed stage), the FRONTIER (the stage the current/last chain run stopped advancing at; derived from the stage jobs' own runs when the chain has never run), each stage job's own latest run state, and the next scheduled chain run — composed from the existing run records, no new persistence. Failure semantics are the engine's, surfaced not re-built: a failing stage halts the chain at its visible frontier, downstream stages never run on missing inputs (the stages' named input refusals stand), a stopped stage resumes from its persisted checkpoint under the same run id, and a failed stage re-runs from its persisted input without re-executing the completed stages. Full surface parity (#3514): 4 copilot tools (`run_pipeline_chain`, `get_pipeline_chain_status`, `list_pipeline_chains`, `manage_pipeline_chain` with chain pause/resume/cancel/retry plus `stage_pause`/`stage_resume`/`stage_cancel` addressed by stage kind — catalog 114), Data Providers routes (`/data-providers/:id/pipeline-chains` + actions, stage actions naming their stage in the request body) and a Pipeline panel column with chain actions and frontier-stage actions, reusing the existing feed-job cell classes (no new stylesheet). Proof runs over the real machinery (no stage mocked): the NASDAQ100 chain through to a delivered report in two execution-mode combinations — defaults (sequential/batch/async/monolith) and sync delivery with the deliver stage sharded (pairs partitioned across units, no pair delivered twice) — plus failure-halt/frontier, stage stop/resume, and stage cancel suites. #CAIO-quns
