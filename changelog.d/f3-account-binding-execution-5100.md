### Fixed

- **Schedules, autopilot, and copilots now execute against exactly the bound account (#5100, F3 of #5094):** every schedule, autopilot run, and copilot run resolves, stores, and honors the full tuple `{ broker, mode, accountType, accountId }`; execution against any other account is refused, and run records carry the tuple as provenance. Two holes close: a body-supplied `accountId` was previously accepted verbatim as an "explicit" resolution, and an unbound tenant previously resolved to an "unset" context that no caller refused. A body-supplied account id is now an untrusted hint validated against the broker's enumerated accounts (unknown 404 / unowned 403 / asset-type mismatch 400 / cross-broker 409); unbound resolves to `FAILURE_ACCOUNT_BINDING_MISSING` and is refused loud at order preview, order execute, schedule create (REST + NLQ), schedule fire, autopilot evaluate, and copilot order tools. Refusals are recorded as skipped runs with the failure code as the detail reason, never failed runs, never silent. Schedules stamp the tuple at creation (the asset class defaults to the callback's class — options analysis resolves the options account) and re-validate it at fire time; a pre-F3 unstamped schedule is refused, not executed. A legacy order draft with no binding stamp is refused with "re-preview required" instead of silently defaulting to E*TRADE. The E*TRADE-only balance snapshot is unchanged (#4571 owns any routing change); the tuple is threaded to its call site and recorded on the verdict only. #cpo-dhmp
