### Added

- **Queue transport for the analysis-done stage message, slice 1 (#2869, under #2764) #clo-arsi:** after the canonical `mas_reports` row lands (`persistScreenerReportCanonical`, the one recorder), the analysis-done `StageMessage` is published to the shared `screener-events` Cloudflare Queue (producer binding `SCREENER_EVENTS`, already declared with its consumer + DLQ — no new queue, recorder, catalog, or port layer). `src/server.ts` `queue()` routes such messages to the owning ScreenerAgent DO's new `consumeQueuedAnalysisDone` method, which consumes them through the existing `consumeAnalysisDone` consumer with the durable `mas_stage_claims` claims store and the one generation module's PDF leg. In the normal path the in-process leg has already claimed `runId::analysis-done`, so the queued consume duplicate-suppresses and never regenerates; when the in-process leg failed (claim released on failure), the queued consume is the recovery path. Publish failure never fails the run (the row is durable, the in-process leg already ran); poison/over-budget messages are dead-lettered and acked; a missing persisted analysis throws so the platform retries to the DLQ. Pinned by `tests/stage_queue_transport_2869.test.ts` (11).
