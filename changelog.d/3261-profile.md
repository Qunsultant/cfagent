### Added

- Profile management in the account flow (#3261, sub-issue of #3256): display name and phone, viewable and editable self-service from the first-run account step (with the saved values shown read-only in the step 5 summary), over new self-only GET/POST /platform/accounts/profile routes backed by a new D1 `agent_user_profiles` table (migration 0050). An unset display name shows as the login (PROPOSED default, display-only); phone is an unverified contact field, never used for sign-in. Writes are audited with the outcome code + message + login + changed-flags (never profile values). Email change is NOT included: it touches IAAA / session / auth and needs CISO review first (#3261 comment 6681436382, refs #945) — the section says so in one fixed line instead of offering a field that goes nowhere. All profile success/failure messages come from six new outcome-catalog entries (SUCCESS_PROFILE_READ/UPDATED, FAILURE_PROFILE_VALIDATION/NOT_SIGNED_IN/STORE_UNAVAILABLE/DUPLICATE) resolved through the single resolver; validation is structural (field + kind, no throws) and the panel renders the coded business message, marking the failing field invalid. Saves are idempotent on a client-supplied key (replay → 409; key + write land in one D1 batch, migration 0050 also creates `agent_profile_idempotency_keys`). Validation length bounds live in `config/profile-limits.json` (single source of truth, same pattern as session limits).
