### Fixed

- **The six OODA stages are addressable from the definition flow and the binder (issue #6031):** the `research` spec nests `feed → enrich → analyze → generate → deliver → evaluate` under one `research` wrapper node, so the Define page rendered a single row and `bindStageOverrides` judged `stageModes` against the top level only — `{ analyze: { pacing: "online" } }` refused with *"its stages are: research"*. `addressableStages(spec)` now walks the tree and returns the executable stages (a stage carrying `children` is a container, not a step); the binder validates `stageModes`/`stageTimeouts`/`stageMaxParallel`/`stageRetryBuckets`/`stageProcessing` against that list, the flow renders it, the define response counts it, and the built definition carries the override on the child node the engine executes. The spec also declares the run parameters the page could not collect — `universe` (`enumSource: "universes"`, now the accepted set from #6032 rather than the raw registry), `brokerId` and `mode` — so the existing binder validates them instead of refusing them as undeclared. Precedence, stated and pinned: a stored definition's per-stage mode is what that definition runs; `RESEARCH_STAGE_MODES` remains the deployment default for the per-run `research:<runId>` jobs the OODA dispatch builds (the shared store and the run-record write stay with #5975/#4766). Pinned by `tests/ooda_stage_addressability_6031.test.ts`.
