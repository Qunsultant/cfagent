### Added

- **Alpaca order placement client (#3158, follow-on of S3 #3089):** `AlpacaTradingPlatform.placeOrderRemote` submits equity orders to the Alpaca Trading API v2 through the existing `AlpacaMarketDataProvider.placeOrder` client (key/secret auth, `time_in_force: "day"`), so broker-routed execute paths that prefer a remote-submit method pick it up through the existing approvals door — no new approval path, no HITL or DID changes. Equity only: option legs, non-positive quantities, empty symbols, and order types other than market/limit are refused without any fetch; limit orders require a limit price. Failures map by HTTP status to business errors (credentials / rejected details / busy / temporarily unavailable / unreachable), never upstream text. A success is reported only with a broker order id in hand, as `submitted` (accepted, fill pending — nothing settled, no fabricated execution). The hardcoded `getAccounts` / `getPositions` paper stubs (`alpaca_paper_01`, $100,000, empty positions) are replaced by live Trading API reads with the same fail-explicit rule: unconfigured or failed reads throw instead of returning fabricated data. Paper vs live is resolved from one place: the default base URL is `https://paper-api.alpaca.markets`, and a base URL counts as live only when set and not a paper host — this also fixes `getStatus()` reporting live when `ALPACA_BASE_URL` was unset while trading defaulted to paper. Pinned by `tests/alpaca_place_order_remote_3158.test.ts` against a stubbed Trading API, including the #2389 honest-failure pin on `executeOrder`. No broker-routed `/api/broker/order/*` route exists on main yet; the route-surface decision still belongs to S3 #3089, so this slice is adapter-level only.
