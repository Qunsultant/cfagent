### Added

- **The feed family has a definition spec, and its inputs are vocabulary values (#5493):** `src/config/jobDefinitionCatalog.ts` gains the `feed` spec — one `feed.pull` stage plus the run parameters a feed input carries (`feedJobId` required, `universe`, `sources`, `dataset`, `shards`, `minDte`/`maxDte`). It is the second spec on the existing catalog/spec-builder/binder mechanism, so the define route and `buildJobConfigFromSpec` needed no new path, and `feed.pull`'s universe input — the #3930 precedent with no production carrier — now has one. A spec can declare `axes` (the feed family declares `dataset` and `universe`), and a parameter can name an `axis`; both resolve through the one reader (`src/config/vocabulary.ts`, #5515) at read/bind time, so an alias binds to its canonical id, an unknown value refuses by name, and a conflated value refuses with its pointer (`TECH` → `sector-information-technology`) carrying the vocabulary's own code. `sources` is a `multi-select` over the provider axis with `capabilityFrom: "dataset"`: a provider that declares capabilities and lacks the dataset refuses as a pair, while a provider added as data (`config/vocabulary.json` / the `setVocabulary` seam) binds with no code change. `minDte`/`maxDte` carry declared bounds and the `maxDte ≥ minDte` relation; `shards` is a string list. The universe axis gains the two stored lists the refresh service already maintains (`russell1000`, `russell3000`) as data, so the feed's declarable universes match what it can pull. Pins (`tests/feed_spec_axes_5493.test.ts`) drive a spec-defined run end to end through the engine — the bound universe is the one pulled — and prove a parameterless run pulls the job's own universe. #CAIO-quns
