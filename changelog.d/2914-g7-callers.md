### Changed

- **Must-fix private/direct callers, G7 (#2914, under #2764):** (1) One parent command builder — `screenExecutionBroker.buildParentScreenCommand` now builds every server-side run-screen parent command (broker REST start, NLQ chat-screen builder, mesh door builder), which previously each wrote the literal out by hand sharing only `shardsForUniverse`; a pin test fails any new hand-built command in those files. (2) NLQ fallback via spec/broker/planner — the fallback builds a source "nlq" spec with `asyncRequested: false` and consults the broker (null = the sync-branch routing decision, per the broker's own contract) before running sync; behavior unchanged. (3) Goal execution stays goal-owned by dated decision (2026-11-03, recorded in the capability inventory): the goal engine screens thesis legs internally via the provider registry, goal reports and delivery are goal-owned surfaces, and the broker guard (null for goal specs) is the routing decision, not a gap; revisit trigger is workflow multi-leg goal semantics + goal report/delivery parity. (4) Scheduled sharded starts through the broker — `startScheduledShardedChain` owns the feed-start submission + shardSubmit port, so `scheduledTasks` no longer imports the chain planner for its start. Stated plainly, this is NOT a migration of scheduled-sharded execution onto the ScreenerScreenWorkflow, and that literal migration was considered and rejected in G7: the chain is the stage pipeline (its `stageChain` config has no workflow equivalent), the chain run model (`chain_id`) is read by the workflowRuns surface, the chain's serve step feeds the same delivery bridge the workflow feeds, and per-run delivery channels ride the chain context while the workflow command carries no channel fields — moving execution would drop staging + channels and fight the #2869 production-wiring direction. A workflow-start migration, if ever wanted, needs channel plumbing + stageChain-in-workflow + chain-run-model migration as its own designed issue. (5) `persistRun` reconciled in the lossless manifest: the capability inventory gains a `screener-delivery-cache` entry stating 1:1 with the canonical `mas_reports` row, never a second count — the cache exists only for the download getters, and a pin test asserts `persistRun` writes no canonical row. Named exception, out of G7 scope: the paid-fulfillment path (`premium.ts`) keeps its own symbols-shard literal (own scheme, own tests), listed in the pin test's allow-list, not silently passed.
