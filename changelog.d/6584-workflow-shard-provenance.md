### Fixed

- **Workflow-shard runs now record their provenance too (#6584):** #6557 gave the sync residency its run provenance, and the workflow-shard residency — the one that executes the scheduled options chain — still recorded four nulls, so the largest durable run on the ledger showed `—` for broker and mode while a small sync run beside it showed both. `JobPipelineWorkflowPayload` now carries the same `JobRunProvenance` carrier and `runJobPipelineWorkflowFlow` passes it to `runJob`, normalized through `normalizeRunProvenance` — the one field rule `parseRunProvenance` uses, so the payload and stored-carrier paths cannot drift. The scheduled source is the chain itself: `startOptionsChainWorkflow` reads the four facts the firing schedule already stamped on `ShardChainContext` (#3655) via `chainRunProvenance` and puts them on the instance it creates. A manual chain start names none and the record keeps explicit nulls (the owner decision behind #6557), a malformed carrier reads as nulls and never fails the run, and `startPipelineJobWorkflow` offers the same optional carrier so every creator of a `JobPipelineWorkflow` instance has one payload shape.
