### Added

- **Scheduled engine runs now record their provenance — broker, data provider, mode and mode source (#6557):** the run record has carried those four #3655 fields since it existed and the engine never had values to fill them: the payload that fired a scheduled run never reached the engine's own record, and D1 had no columns for them at all. The firing payload is now the one source (owner decision 2026-11-25): `runPipelineJobSchedule` parses it into a `JobRunProvenance` carrier, the dispatch persists it on the instance (`run_provenance_json`, D1 migration 0090 + the DO probed ALTER — the settle path can be another process), and `recordTerminal` stamps the four fields from the instance. Migration 0091 adds the four columns to the D1 run record so a D1-recorded run and a DO-recorded run agree. A manual, retried, replayed or re-run dispatch records explicit nulls — never an inferred broker or mode — and a resume keeps the run's own provenance. Pins: `tests/run_provenance_6557.test.ts` (carrier, nulls, retry, resume, payload parser, both migrations, both adapter residencies, the callback wiring); the schema fixtures, recreate counts and catalogue pins moved with the two migrations; the engine reference (§3.13, §3.14) states the stamp instead of the gap.
