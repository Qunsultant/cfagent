## 0. Safety verdict — Public.com + paper mode (read this first)

**Verdict: NO — Public + TEST does not place live orders today, and it cannot simulate them either.** Placement in TEST is refused server-side, before any broker call, on both placement entry points. Preview and reads still work in TEST; only placement is refused. In PROD the same code places a real order on Public's single live MCP endpoint — there is no paper host and no simulation anywhere.

**The code path.** The mode is one stored key, never a request header: `src/agents/routes/brokerEnvironment.ts:31` (`BROKER_ENVIRONMENT_SETTING_KEY = "etrade:environment"`), and `resolveTradeEnvironmentFromSettings()` falls back to `"TEST"` for anything but exact `TEST`/`PROD` (`:91-101`). The mode default is paper, never live. Preview (`POST /broker/order/preview`, `src/agents/routes/brokerOrders.ts:199`) resolves the platform with that environment (`:240`) and stores the draft stamped `broker: "public", mode: "paper"` (`:253`); `previewOrder()` has no paper-mode check (`src/trading/public/platform.ts:269`). Execute (`POST /broker/order/execute`, `brokerOrders.ts:288`) takes the broker from the stored draft, never the caller (mismatch = 409, `:331-333`), re-resolves the platform (`:393`), and prefers `placeOrderRemote` for non-E*TRADE brokers (`src/agents/routes/etradeBrokerOrders.ts:232-233`). Both placement methods refuse in TEST before any MCP call: `noPaperModeRefusal()` (`src/trading/public/platform.ts:145-160`, called from `placeOrderRemote` at `:524-533` and from `executeOrder` at `:390,459`) returns `publicRefusedExecution({code: FAILURE_PUBLIC_NO_PAPER_MODE, message})` (`src/services/publicTrading.ts:42,45-51,376` — `success: false, status: "failed"`, nothing placed, nothing retried, draft stays `previewed`). If the outcome code were missing from the catalog it throws rather than proceeding. The outcome catalog entry (`src/outcomes/outcomeCatalog.json`, `FAILURE_PUBLIC_NO_PAPER_MODE`) says: "Public.com has no paper trading mode, so this order cannot be placed while the trading mode is paper. Switch to live mode to place it, or use preview to check it first." (403, retryable false.) The client talks to one endpoint in either mode — `PUBLIC_MCP_URL = "https://mcp.public.com/mcp"` (`src/mcps/public/publicMcp.ts:34,130`) — and reads the environment only to decide the refusal; it never selects a different base URL or credential set per mode. The catalog states the same (`src/trading/brokerCatalog.ts:335-341`).

**The UX gap (not a safety gap).** The refusal surfaces as a plain error string after approval: the user can preview, reach the "Approve & Submit Trade" button (`src/client/ETradeTradingHub.tsx:2135`), approve, and only then learn placement is refused (`:1704,1713,1737` — `setOrderError(data.message || "Order execution failed")`). The only in-app warning today is `PublicTokenCard.tsx:130-134` (an inline info Notice inside the settings menu, rendered at `src/client/BrokerDynamicMenu.tsx:906`): a repo-wide search for "no paper" in `src/client` finds only this card — nothing warns in the order ticket, the crumb, or at the toggle itself.

**The live-money edge, now closed.** `cancelOrderRemote()` (`src/trading/public/platform.ts:579`) used to call only `refuseDeploymentCredential()` and then the MCP `cancel_order` tool — it had **no** `noPaperModeRefusal()` check, so a TEST-mode cancel would cancel a real (PROD-placed) order, and it returned `success: true` unconditionally. **Fixed in #4650 (PR #4765):** the cancel seam shares the placement gate (`noPaperModeRefusalCode()`) and refuses in TEST before any MCP call with `FAILURE_PUBLIC_NO_PAPER_MODE`; in PROD the receipt comes from `publicCancelReceipt()` (`src/services/publicTrading.ts`), which requires an explicit `success: true` or a cancellation status word and reports a refusal, an error, or a signal-free payload as *not cancelled*.

**Comparison.** Alpaca really does switch hosts: `ALPACA_PAPER_HOST = "https://paper-api.alpaca.markets"` vs `ALPACA_LIVE_HOST = "https://api.alpaca.markets"` (`src/trading/alpaca/optionsData.ts:97-98,113-137`); paper orders go to the paper host. E*TRADE really does have a sandbox: live `https://api.etrade.com/v1`, otherwise `https://apisb.etrade.com/v1` (`src/config/environment.ts:86-87,121-123`).

**Mode is global, not per-broker.** The mode is one value (`etrade:environment`; client default `TEST`, `src/client/brokerEnvironment.ts:28,53`; single hook `useBrokerEnvironment()`, `:140`). `src/client/Chat.tsx:157-162` derives `accountMode: "paper" | "live" = brokerEnv === "PROD" ? "live" : "paper"`. Broker selection lives in a different store (`tenantProviders.brokerId`, default `alpaca`); switching broker never changes the mode and switching mode never changes the broker (`src/client/BrokerDynamicMenu.tsx:186-192,407,421-422,766`). Consequence: a user on Public + Paper who switches to Alpaca stays on Paper (real paper host); flipping to Live while on Public arms real-money placement with one click and no confirm today (`BrokerDynamicMenu.tsx:574-583` posts with no confirmation dialog; toggle UI at `:802-812` mini-toggle and `:983-1006` "Policy Mode" PillGroup).

**Where a guard hooks in (earliest catch first).** The server already refuses placement, so every UI hook is disclosure, not safety — **(1) and (5) shipped in #4649 (PR #4769)**: `BrokerDefinition.paperMode` declares the fact, `brokerModeLabel` renders Public as Live in both stored modes, selecting Public in TEST opens the `ConfirmModal` and auto-switches the stored mode to PROD on confirm, and a persistent `Notice` sits in the settings menu and above the ticket's Approve button for any surviving `public + TEST` state. (1) mode toggle + broker selection in `BrokerDynamicMenu` — persistent inline **Notice** while `brokerId === "public" && env === TEST`, plus a **ConfirmModal** on the TEST→PROD switch while on Public; (2) order ticket / preview pane — Notice above the Approve button when the impossible combination holds, plus disabling/relabeling Approve; (3) execute confirmation — defence-in-depth only; (4) do **not** block preview (preview in TEST is intentional); (5) crumb wording — display only, weakest guard. Governing rule, `docs/architecture/UX/ux-architecture.md:230-273` ("Dialogs: one system", "Toasts: one place for transient feedback"): every dialog is built with the `Modal` primitive (`src/client/components/ui/Modal.tsx:4,32`); transient feedback goes through the global Toast (`src/client/components/ui/Toast.tsx:31,50-61,87`, mounted at `src/client/main.tsx:121`); persistent state that must remain visible belongs to the inline **Notice** (`src/client/components/ui/Notice.tsx:3,25`); no native `alert()`/`confirm()` dialogs, no per-panel toast one-offs. The one existing confirm dialog is `ConfirmModal` (`src/client/scheduledOptionsManager/ConfirmModal.tsx:4,26`, built on Modal, `tone="danger"` default), used only by `src/client/SchedulesPanel.tsx:745` and `src/client/ScheduledOptionsManager.tsx:815`. So a Public+Paper guard wants **Notice for the standing warning + ConfirmModal (on Modal) for the Live-switch confirmation**.

## 1. The bar — what an advanced / leading brokerage provides

This is the reference bar, not a description of what the system does today. Each item is what a leading retail brokerage (and a leading brokerage API) offers for stocks and options. Section 4 measures the system against it.

### 1.1 Order types (stocks)
- **Market** — execute immediately at the best available price.
- **Limit** — execute only at the limit price or better.
- **Stop (stop-loss)** — becomes a market order when the stop price trades.
- **Stop-limit** — becomes a limit order when the stop price trades.
- **Trailing stop** — stop price trails the market by a fixed amount or percent.
- **Trailing stop-limit** — trailing stop that becomes a limit order.
- **Market-on-open / market-on-close / limit-on-open / limit-on-close (MOO/MOC/LOO/LOC)** — execute at the open or close auction.
- **Notional / fractional-share orders** — order by dollar amount rather than share count.

### 1.2 Time in force (TIF)
- **Day** — expires at the end of the trading day.
- **Good-til-cancelled (GTC)** — stays open until filled or cancelled.
- **Immediate-or-cancel (IOC)** — fill what can fill now, cancel the rest.
- **Fill-or-kill (FOK)** — fill entirely now or cancel entirely.
- **Good-til-date (GTD)** — expires on a named date.
- **On-open / on-close (OPG/CLS)** — valid for the opening/closing auction only.
- **Extended hours** — eligible for pre-market / after-hours / overnight sessions, with the session named on the order.

### 1.3 Advanced orders
- **Bracket** — entry order with attached take-profit and stop-loss exits, managed as one unit at the broker.
- **OCO (one-cancels-the-other)** — two orders, first fill cancels the other.
- **OTO (one-triggers-the-other)** — fill of the first submits the second.
- **Conditional orders** — trigger on price, time, or another condition.
- **Scale-out / bracket ladder** — staged exits at multiple price levels.
- **Replace / modify** — change price, quantity, or TIF on a live order without cancelling and re-entering.

### 1.4 Options order types and multi-leg strategies
- Single-leg options orders in every type above (market/limit/stop/stop-limit).
- **Multi-leg strategies submitted as one order** — vertical spreads, straddles, strangles, iron condors, butterflies, calendars, covered calls, cash-secured puts, PMCC (stock + long call legs).
- Net debit / net credit pricing on the strategy as a whole.
- **Exercise and assignment** — exercise a long option, and visibility into assignment of short options.

### 1.5 Order views
- **Open orders** — live state from the broker, not a local draft list.
- **Order history** — filled, cancelled, rejected, expired, with timestamps.
- **Order status** — live transitions (new, partially filled, filled, cancelled, rejected, expired).
- **Fills** — per-order filled quantity and average fill price, including partial fills.

### 1.6 Cancellations and modifications
- Cancel a live order from every surface that can place one (ticket, chat, API, MCP), with a truthful receipt.
- Cancel-all and cancel-by-symbol, with a preview-then-confirm step for destructive scope.
- Modify (replace) a live order's price/quantity/TIF.
- The local record reflects a live cancel (no stale draft rows).

### 1.7 Account capabilities
- **Short selling / locate** — short sales with borrow availability and locate.
- **Margin** — margin balances, buying power, and margin-aware order validation.
- **Fractional shares** — fractional quantities and notional orders.
- **Extended-hours trading** — pre-market, after-hours, overnight sessions.
- **Dividend / corporate-action handling** — ex-dates, dividends, splits, and their effect on orders and positions.

### 1.8 Data
- Real-time quotes (bid/ask, last, volume, day range).
- Options chains with expirations, strikes, and **Greeks** (delta, gamma, theta, vega, rho, IV) — live and historical.
- Fundamentals (P/E, EPS, margins, growth, balance sheet).
- Earnings dates and estimates; news; corporate-action calendar.

## 2. Measured capability matrix

Columns: Alp-S / Alp-O / ET-S / ET-O / Pub-S / Pub-O / Tasty-S / Tasty-O / IBKR-S / IBKR-O (Alpaca, E*TRADE, Public.com, Tastytrade, IBKR × stocks / options). Tastytrade and IBKR are ➖ not integrated throughout; see §2.7 for what exists.

**The finding that shapes every table: four layers disagree.** (1) Ticket + preview route: `OrderTicketModel` allows only `MARKET|LIMIT|STOP|STOP_LIMIT` (`src/client/OrderTicketPanel.tsx:59`), rendered as exactly those four `<option>`s (`:681-695`); no TIF field anywhere in the ticket or hub (zero `timeInForce|time_in_force|TIF` hits in `OrderTicketPanel.tsx` / `ETradeTradingHub.tsx`). The hub preview body sends `broker, assetClass, symbol, orderAction, quantity, orderType, limitPrice, optionLegs, strategyNetDebit` — no `stopPrice`, no `timeInForce`, no `orderClass`, no `takeProfit/stopLoss` (`src/client/ETradeTradingHub.tsx:1673-1690`), and `limitPrice` is sent only when `orderType === "LIMIT"` (`:1684`). So a STOP ticket's stop price is typed into a field labelled "Stop Price ($)" (`OrderTicketPanel.tsx:697`) and then dropped before any API call. (2) Preview route: `POST /broker/order/preview` does accept and forward `stopPrice` (`src/agents/routes/brokerOrders.ts:219,249`) but accepts no `timeInForce`, `orderClass`, `session`, `takeProfit`, or `stopLoss` — anything sent under those names is silently ignored (`:217-260`). `OrderPreviewParams.orderType` is the 4-type union (`src/trading/interfaces.ts:53`), `orderClass` is `simple|bracket|oco|oto` (`:59`), and `OrderPreviewParams` has no `timeInForce` field. `PlaceOrderParams` does have `timeInForce?: "day"|"gtc"|"ioc"|"fok"|"opg"|"cls"` (`:120`) — TIF exists only at placement, never at preview. (3) Neutral platform seam (`placeOrderRemote` / `executeOrder`) — the narrowest path; e.g. Alpaca's rejects everything but MARKET/LIMIT equity. (4) MCP / direct provider path + `advancedOrders.ts` registry — the widest path for Alpaca (trailing stops, IOC/FOK, brackets, ladders), and a registry whose claims sometimes have no client code behind them (see Appendix B).
