**Spec status on main:** **PROPOSED, not adopted.** This draft does not adopt the spec, does not change production identity, secrets, permissions, or infrastructure, and does not select a provider.
**Filing:** filed in `docs/architecture/security/iaaa-945-assurance-review.md`, related to epic #945. Not posted to any issue, per owner directive 2026-10-25.
**Baseline verified for this draft:** cfagent main `1418ee0` (`1418ee0890cb19e64a996e70d6dd985b79caccdc`, "feat(enforcement): policy gate + main audit so gitops cannot be bypassed (#1487)", 2026-10-25T12:34:44Z)
**Epic:** cfagent #945, "[EPIC] IAAA-with-Auth0 — Multi-Tenant IAAA and Fine-Grained Authorization (RSI-CISO mission)"

**Mission basis:** `docs/agentic-org/mission.md` — RSI-CISO: "Verify delegated authority on one consequential workflow," including that users cannot cross tenant boundaries, agents cannot expand their own tool access, child tasks cannot exceed delegated authority, untrusted content cannot authorize actions, and changed proposals cannot reuse invalid approvals.
**Method:** Read-only review of current main via the public GitHub API and raw file reads. No code was written, no issue/PR was opened, no comment was posted, no other lane's branch or PR was touched. Production behaviour was **not** probed; see "What could not be verified" at the end.

## Verdict in one paragraph

The spec is sound as a requirements and architecture document and should be adopted **subject to the clarifications in §4**, not unconditionally. Its normative core — stable internal identity bound to validated `(issuer, subject)`, default-deny server-side authorization, bounded revocable delegation, and attributable audit — matches epic #945 §§3–7 and is the right shape. But adoption as written would adopt three things that are no longer true: a §2 assessment frozen at main `975c3ed` (2026-10-21) that predates Slices 1–3, Google login, PDP, admin UI, delegation, audit, and revocation code now on main; an unverified provider-cost assumption behind the recommended Option A; and several underspecified controls (genesis/bootstrap, CSRF, delegation approval binding, audit-failure blocking set, revocation propagation measure, service/workload identity) that are exactly the controls an attacker or a misconfiguration would test first. The correct adoption path is: answer §4, refresh §2 to main `1418ee0`, reconcile the conflicts in §1.5, and then adopt the refreshed spec as the delta baseline — not as a fresh plan.

## 1. Spec-vs-epic gap check

Epic sections referenced: §3 Identification, §4 Authentication, §5 Authorization, §6 Accountability, §7 Lifecycle, §8 Acceptance tests, §9 Provider-selection implications, §10 assignment (identity → login/session → membership → scoped authorization → delegation → accountability → lifecycle verification).

### 1.1 Stable identity — spec complete as a model; assessment stale as a description

- **Epic §3 requires:** distinct identifiers for human user, external login identity, tenant, workspace, service principal, agent definition, agent instance, agent run, task, delegation, approval; external binding by validated issuer + subject; invitation acceptance with expiring single-use tokens, explicit membership creation, proof of control for linking, audited linking/unlinking, defined recovery and duplicate handling; never merge accounts on matching email, never grant tenant access on matching email domain, never treat GitHub-org/Slack-workspace membership as application authorization without an approved mapping policy.
- **Spec §4 provides:** `IdentityBinding { internalUserId, providerIssuer, providerSubject, linkedAt, proofOfControl: "oidc" | "invitation" | "recovery" }`, with `internalUserId` stable and "never derived from email/login". That is the right model.
- **Gap in the spec:** it names `proofOfControl` values but never defines what proof is for each value, what evidence is stored, how long a linking proof is valid, or what happens on a duplicate `(issuer, subject)` or a duplicate email across issuers. The epic's prohibitions (no email-match merging, no domain-match granting) are stated in the spec's §2 gap table only as "no duplicate-account handling" — they are not carried into §4 as normative rules or into §6 as named negative tests beyond "unproven provider linking is rejected."
- **Main has moved past the spec's assessment:** `src/security/identityBinding.ts` (binding by user + issuer, `deriveInternalUserId`), `tests/iaaa_identity_binding.test.ts`, `tests/iaaa_stable_id.test.ts`, and `docs/architecture/adr/0001-derived-stable-identity.md` now exist. The spec's §2 claim "No internal user ID" is therefore **stale, not wrong at the time it was written**. Adoption must refresh §2 rather than re-adopt a stale assessment.

### 1.2 Federated login + sessions + step-up — spec partial; main implements more than the spec describes

- **Epic §4 requires:** Google and GitHub initially, Microsoft and others later through the same integration boundary; provider/callback configuration, authorization-response validation, CSRF protection and state handling, PKCE where applicable, OIDC nonce validation, token signature and algorithm validation, issuer/audience/expiry/intended-use validation, maintained integrations rather than custom protocol code; session duration, idle and absolute expiry, rotation, logout, revocation, secure cookie settings, CSRF protection for cookie-authenticated mutations, recovery behaviour, authentication freshness; step-up for changing auth methods, linking a new provider, assigning privileged roles, exporting sensitive records, changing payment configuration, managing integration credentials; fail closed when required assurance evidence is unavailable.
- **Spec provides:** Option A/B/C provider boundary (§3), session evolution in §4 (extend `SessionData` with `internalUserId`, `providerIssuer`, `providerSubject`, `tenantId`, `authTime`, `sessionVersion`, "all optional until adoption, so old sessions are not invalidated by the spec"), and a §6 step-up test row. It does **not** specify: any idle/absolute duration, rotation triggers, the step-up threshold list, the freshness window, CSRF handling, PKCE/nonce/algorithm rules, or JWKS handling. Those are deferred to §8 open decisions ("Step-up thresholds: which actions require freshness, and how fresh — CISO, due before Slice 2").
- **Main has moved past the spec:** `docs/architecture/security/iaaa-google-defaults.md` and `docs/architecture/security/iaaa-github-end-to-end-defaults.md` describe Google alongside GitHub, bootstrap-on-login, and `/api/me` exposing `internalUserId`; `src/security/iaaaSessionActivity.ts` (Wiring Phase 2a) implements idle enforcement and a step-up wrapper, with an explicit honesty note that idle enforcement is accurate only to ±60s and that a session without `authTimeMs` (every legacy session) is treated as stale, never fresh — i.e. fail closed. `tests/iaaa_step_up.test.ts`, `tests/iaaa_session_policy.test.ts`, and `tests/iaaa_oidc_validation.test.ts` exist.
- **Conflict to reconcile on adoption:** the spec's "old sessions are not invalidated" backward-compatibility promise sits uneasily with main's fail-closed legacy step-up behaviour. Both cannot be the adoption statement. The CISO position is: legacy sessions may continue for low-sensitivity reads, but any sensitive action under §4 must treat a session without `authTime` as stale. Adoption must say that explicitly, including the ±60s idle slack as a stated tolerance, not as exact enforcement.

### 1.3 Tenant/workspace membership — spec complete as a model; assessment stale

- **Epic §§3/5 require:** tenant/workspace memberships, scoped role bindings, platform administration separate from tenant administration, and the permission list (membership:invite/revoke, role:assign, task:create/read/cancel, artifact:read/edit/export, integration:connect/use/manage, action:propose/approve/execute, audit:read/export), with grant rules defined per permission and "possessing a permission must not automatically mean permission to grant it to others."
- **Spec §4 provides:** `Membership` and `RoleBinding` (scope platform/tenant/workspace/resource, `grantedBy`, optional `expiresAt`), and §5 provides the full permission matrix with platform/tenant/workspace/member/approver/auditor columns and the default-deny evaluation formula (principal + active membership + role permissions + resource relationship + tenant/workspace policy + delegation limits + approval requirements + context; "Role alone never decides"). That is complete as a model.
- **Spec gaps:** §5 itself says "grant rules to be confirmed." It does not state who may grant `role:assign` at each scope, whether a grant requires a second approver, whether grants expire by default, or how a grant is revoked when the granter's own membership is revoked. It is also silent on tenant creation itself: who may create a tenant, what the first tenant admin's authority is, and how a tenant is deleted — the genesis problem, treated separately in §2 risk R1.
- **Main has moved past the spec:** `src/security/iaaaMembershipStore.ts`, `src/security/iaaaBootstrap.ts`, `tests/iaaa_authorization.test.ts`, and `tests/iaaa_tenant_isolation.test.ts` now exist. The spec's §2 claim "No tenant, workspace, membership, or role model" is stale.

### 1.4 RBAC + FGA default-deny — spec strong in principle; enforcement inventory missing

- **Epic §5 requires:** a policy decision point (PDP), policy enforcement points, authoritative policy and membership sources, policy versioning, cache invalidation, failure behaviour, and enforcement across APIs, background jobs, agent tools, storage, retrieval, artifacts, exports, and notifications — not only in the UI.
- **Spec provides:** the PDP concept in §5 ("Every permission above is evaluated at the PDP") and §7 Slice 3 ("default-deny enforcement at APIs, jobs, tools, storage, retrieval, artifacts, exports, notifications — not only UI"). It does **not** provide: an enforcement-point inventory (which routes/jobs/tools are PEPs today, which are not yet), a policy-versioning scheme, a cache-invalidation rule, or a failure behaviour (what a route does when the PDP is unavailable, when the policy version is unknown, or when a cached decision has expired).
- **Main has moved past the spec:** `src/security/iaaaPdpSeam.ts` (default-deny inherited from Slice 3; cross-tenant requests and scope/resource mismatches deny), `src/security/iaaaEnforcement.ts`, `src/client/iaaaEndpointCatalog.ts`, and `docs/architecture/security/iaaa-github-end-to-end-defaults.md` ("PDP route enforcement, flag-gated" behind `IAAA_PDP_ENABLED`, default OFF per the Google defaults doc; legacy sessions without `internalUserId` keep byte-for-byte legacy behaviour). The flag-gating is the right rollout shape, but it is also the central adoption risk: while the PDP flag is OFF, the spec's default-deny claim is aspirational for the routes not yet wired, and the spec does not require an inventory proving which routes are covered before any "PDP enabled" claim is made.
- **No Auth0 authorization code on main:** a tree search of main `1418ee0` finds zero paths containing "auth0" (any case) and zero containing "microsoft". That is consistent with the spec (no provider wired in the spec step) and with Option A not yet being implemented — but it means any adoption statement must not imply Auth0 authorization exists.

### 1.5 Bounded agent delegation — spec model complete; two concrete mismatches with main

- **Epic §5 requires:** effective authority = initiator's authority ∩ tenant/workspace policy ∩ resource policy ∩ tool permissions ∩ explicit delegation ∩ valid approval; delegation defines allowed actions, resource scope, expiration, budget, re-delegation rules, approval requirements, revocation behaviour; re-check authority before delayed or consequential execution.
- **Spec §4 provides:** `Delegation { initiatorId, agentInstanceId, taskId, allowedActions (explicit, not "all"), resourceScope, expiresAt, budget?: { maxActions?, maxCost? }, reDelegation: "forbidden" | "scoped", revokedAt? }`. That matches the epic's shape.
- **Mismatch 1 — cost budget:** main's `src/security/delegation.ts` states explicitly that its budget "is an action count only" and that "claiming a cost budget from this module would be false." The spec's `maxCost` is therefore not implemented and must not be adopted as an implemented control. Either adoption drops `maxCost` to a future requirement, or a cost-accounting slice is added to the plan.
- **Mismatch 2 — "scoped" re-delegation is undefined:** the spec never defines what a scoped re-delegation may do. The safe definition, which adoption should state, is: a re-delegation may only narrow actions, scope, and expiry, never widen them; it requires the same approval rules as the original delegation; and it is itself revocable through the original delegation's revocation. Without that definition, "scoped" is a label, not a control.
- **Mismatch 3 — approval binding:** the spec's `AuthorizationDecision` carries `approvalId` but no proposal version, hash, or snapshot field. Epic §8 requires "Material proposal changes invalidate prior approval," and the #1393 mission cycle (email → trade-approval, invariants 4 + 5) is built on exactly that lesson: an approval must bind to the frozen proposal terms, not merely to an approval ID. The spec's §6 test row ("Material proposal changes invalidate prior approval → `tests/iaaa_approval.test.ts`") names the test but the §4 model does not carry the field the test needs. Adoption must add a proposal-version/hash binding to the decision and delegation models. (`tests/iaaa_approval.test.ts` now exists on main; the adoption question is whether it covers snapshot binding, which this review did not re-execute — see "What could not be verified.")

### 1.6 Attributable audit — spec model matches the epic; mechanism and blocking set are open

- **Epic §6 requires:** the full audit field set (id, trusted timestamp, type, actor principal + type, initiating principal, tenant, workspace, task, agent instance/run, delegation, correlation, action, resource, decision, policy version, approval, outcome succeeded/failed/pending/unknown, error code, external operation id); the event list (login success/failure, session revocation, linking/recovery, membership changes, role/permission changes, delegation creation/revocation, sensitive access/export, approval decisions, consequential attempts/outcomes, admin/support access, audit configuration changes); restricted writers/readers, defined retention, missing/failed-write detection, integrity/tamper detection, cross-async correlation, privacy-aware minimization, audit access itself logged; a defined blocking set for when durable audit cannot be recorded; outcome states distinguished (proposed/authorized/attempted/succeeded/failed/unknown/reconciled), never recording "success" merely because authorization passed or a tool call started.
- **Spec §4 provides:** `IaaaAuditEvent` with actor, initiating principal, tenant/workspace, task, agent instance/run, delegation, correlation, action, resource, decision, policy version, approval, outcome, and error code, plus "Never raw credentials or tokens. Authentication assurance/session references only." That matches the epic's field set, with two exceptions: it omits `externalOperationId`, and it does not include an audit-access event type (audit reads/exports must themselves be audited per the epic).
- **Spec gaps:** the spec's audit event carries no hash/previous-hash field and no tamper-detection mechanism; its §7 Slice 5 defers the audit-failure blocking set, retention, and tamper mechanism to open decisions. Main's `src/security/iaaaAudit.ts` does define a hash-chain mechanism ("every hash and checks every link, so tampering with an [event is detectable]"), an `AuditFailureClassification { blocked }` model, and audit-access input — but its own header states the tamper mechanism is "the proposed tamper-detection mechanism, not a settled [policy]" and that "this module makes no retention claim." Adoption must therefore not claim "tamper-proof audit" or a settled retention policy; the correct claims are "tamper-evident hash chain (proposed)" and "retention undecided."
- **Main has moved past the spec:** `src/security/iaaaAudit.ts`, `src/security/iaaaAuditStore.ts`, `src/security/iaaaAuthAudit.ts`, and `tests/iaaa_audit.test.ts` now exist. The spec's §2 claim that `mas_events` rows lack initiator/tenant/policy-version/decision/correlation fields is stale as a description of the IAAA audit path (the legacy `mas_events` rows may still lack them; the adoption statement must distinguish the legacy path from the IAAA path, and state which path is authoritative for which events).

### 1.7 Lifecycle / revocation — spec direction is right; the measurable contract is missing

- **Epic §7 requires:** the full lifecycle (enrollment → binding → authentication → membership → role assignment → delegation → resource access → privilege change → revocation → offboarding → retention/deletion), explicit revocation behaviour for active sessions, cached decisions, API credentials, running tasks, pending approvals, queued tool actions, and re-delegated work, and a **measurable** revocation propagation requirement — "Do not promise instantaneous revocation unless the architecture can demonstrate it."
- **Spec provides:** §7 Slice 6 (revocation, recovery, offboarding, §8 acceptance suite end-to-end, flag-gated rollout with rollback) and §8 open decisions ("Revocation propagation requirement (measurable, not 'instant') — CISO + CTO, due before Slice 2"). It does **not** define the per-trigger behaviour table the epic requires (session vs cached decision vs API credential vs running task vs pending approval vs queued action vs re-delegated work), nor any number for propagation (seconds? minutes? next-request?).
- **Main has moved past the spec:** `tests/iaaa_revocation.test.ts`, `tests/iaaa_recovery.test.ts`, and `src/security/iaaaSessionActivity.ts` (revocation, absolute and idle expiry treated separately) exist, and the ±60s idle slack is a concrete tolerance the spec never mentions. Adoption should adopt that tolerance pattern for revocation too: state a number (or a per-trigger number) and the test that proves it, rather than "prompt" or "instant."
- **Spec gap — offboarding and deletion:** the epic's lifecycle ends in "retention/deletion." The spec's migration plan says nothing about deleting identity, membership, delegation, or audit data on offboarding, or about how long audit evidence is retained after a tenant or user is deleted. That is a §4 adoption question, not a detail to discover in Slice 6.

### 1.8 Machine / service identity — spec under-specified against the epic

- **Epic §§3–4 require:** distinct service-principal identities, unique/attributable workload identity, short-lived credentials where supported, rotation and revocation, audience restrictions, no credentials in prompts/comments/URLs/logs, and separation between authentication and delegated authority ("A valid agent credential identifies a workload. It does not automatically authorize the workload to act for every tenant").
- **Spec mentions** service principals in its §1 outcome ("Every human or agent action") and in the §2 gap table ("no service principal"), but its §4 data model contains **no ServicePrincipal or workload-credential type**, no credential issuance/rotation/audience rules, and no statement that a workload credential is not authorization. Main now has `src/security/serviceIdentity.ts` and `docs/operations/runbook/service-identity.md`. Adoption should incorporate that module's model into the spec or explicitly scope service identity as a separate slice with its own acceptance tests, rather than leaving it as an unmodelled epic requirement.

### 1.9 Conflicts between the spec and current main — consolidated list

1. **Stale assessment (§2).** Frozen at 2026-10-21, main `975c3ed`. On main `1418ee0`, Slices 1–3, Google login, PDP seam, membership store, delegation, audit, revocation, step-up, tenant isolation, and admin UI code/tests all exist. The spec's gap table is a historical record, not a current assessment.
2. **Session backward compatibility vs fail-closed legacy step-up.** Spec §4: new session fields "optional until adoption, so old sessions are not invalidated." Main `iaaaSessionActivity.ts`: a session without `authTimeMs` is stale for step-up purposes. Reconcile as in §1.2.
3. **Delegation cost budget.** Spec §4: `budget.maxCost`. Main `delegation.ts`: action count only, cost budget explicitly not implemented. Reconcile as in §1.5.
4. **Slice order vs implemented order.** Spec §7: identity → login/session → membership → PDP → delegation → accountability → lifecycle. Main already contains delegation, audit, and revocation modules alongside identity and PDP work, behind flags. Adoption is a delta against implemented code, not a green-field sequence; the adoption document must map each spec slice to what is already on main, what is flag-gated, and what remains.
5. **No conflict — provider state.** Spec §9 / non-goals: no Auth0 tenant, application, secret, or callback created; no production identity changed. Main confirms this: zero Auth0 paths, zero Microsoft paths. The provider decision is genuinely still open, and no adoption statement should imply otherwise.

## 2. Security risks in the spec as written, with evidence and required negative tests

Each risk names the spec/epic evidence and the negative tests that adoption must require. Test names are requirements, not code — no test code is written in this draft, and several of the spec's §6 "future test" files now exist on main, so the requirement in those cases is to extend and prove the named case, not to create the file from scratch. Tests were not executed for this review.

### R1 — Genesis / bootstrap trust is unspecified (highest adoption risk)

- **Evidence:** Epic §5 requires platform administration separate from tenant administration and grant rules per permission. Spec §5 gives the matrix but no genesis procedure: who creates the first platform admin, how that grant is validated, how it is audited, and how it is revoked. Main fills the gap with `src/security/iaaaBootstrap.ts` (source: "ONLY the optional Env var `IAAA_BOOTSTRAP_ADMINS`") and `docs/architecture/security/iaaa-admin-bootstrap-genesis.md`, but the spec never mentions bootstrap at all. An env-var list is a privileged credential-equivalent: anyone who can set it can mint a platform admin.
- **Required negative tests (name only):** a login whose identifier is absent from `IAAA_BOOTSTRAP_ADMINS` cannot self-grant platform admin; a bootstrap grant is recorded as an auditable membership event with granter attribution (not self-attribution); removing an identifier from the bootstrap list does not silently retain or silently drop an already-granted platform membership — the behaviour is defined and tested either way; a bootstrap grant cannot be used to grant a second platform admin unless the matrix's grant rule allows it.
- **Adoption requirement:** a genesis procedure section (who sets the list, through which channel, with what review, with what audit event, and the revocation rule) must be added before adoption. This is the single largest gap between the spec and a deployable authorization system.

### R2 — Account linking, duplicate handling, and email-change races are under-defined

- **Evidence:** Epic §3 prohibitions (no email-match merging, no domain-match granting, no org-membership-as-authorization) and the spec §4 `proofOfControl` enum. The spec never defines proof for "invitation" vs "recovery" vs "oidc," token expiry/single-use for invitations, or the behaviour when the same email appears under two issuers or when a provider subject is recycled.
- **Required negative tests:** email change does not create a new identity or transfer another user's account (epic §8; spec §6 row 1); matching email domain does not grant tenant access; unproven linking is rejected (spec §6 row 2); a linking attempt with an expired or already-used invitation token is rejected; two different issuers with the same email do not merge without explicit, audited, proof-of-control linking for both.

### R3 — Token validation rules are listed, not specified

- **Evidence:** Epic §4 lists issuer, audience, expiry, intended use, signature and algorithm validation, nonce, state/CSRF, and PKCE. Spec §3/§6 reduce this to "Invalid, expired, wrong-issuer, or wrong-audience tokens are rejected" and a §6 test-file name (`tests/iaaa_oidc_validation.test.ts`, which now exists on main). The spec never states: the allowed signature algorithms (and that `none` is rejected), JWKS fetching/rotation/caching rules, acceptable clock skew, nonce binding per flow, PKCE applicability per client type, or token replay handling.
- **Required negative tests:** `none`-algorithm token rejected; token signed with an unlisted algorithm rejected; token from a rotated-out key rejected after JWKS refresh; expired, wrong-issuer, wrong-audience, and wrong-intended-use tokens rejected; replayed authorization code / nonce mismatch rejected; clock-skew boundary defined and tested (not left to a library default).

### R4 — PDP enforcement surface and failure behaviour are unproven

- **Evidence:** Epic §5 enforcement architecture (PDP, PEPs, policy versioning, cache invalidation, failure behaviour) and spec §7 Slice 3 ("not only UI"). The spec provides no PEP inventory, no policy-version scheme, no cache rule, and no failure behaviour.
- **Required negative tests:** Tenant A cannot access Tenant B's resources via direct IDs, search, exports, or jobs (epic §8; spec §6 row 5; `tests/iaaa_tenant_isolation.test.ts` now exists — extend it to search-index and job paths, not only direct-ID routes); a consequential action is denied, not allowed, when the PDP is unavailable, when the policy version is unknown, or when a cached decision has expired; a tenant admin cannot grant platform privileges (spec §6 row 6); an error response does not disclose whether a tenant or resource exists (no 404/403 oracle).

### R5 — Delegation expansion, re-delegation, and approval binding

- **Evidence:** Epic §5 delegation intersection rule and re-check before delayed/consequential execution; epic §8 "Agents cannot expand delegated scope or reuse revoked authority" and "Material proposal changes invalidate prior approval"; spec §4 delegation model and §6 test rows. As noted in §1.5, "scoped" re-delegation is undefined and the decision model lacks a proposal-version/hash binding.
- **Required negative tests:** an agent cannot expand delegated scope or reuse revoked authority (spec §6 row 7; `tests/iaaa_delegation.test.ts` now exists); a re-delegation that widens actions, scope, or expiry is rejected; a delegated action after expiry, after revocation, or after budget exhaustion is denied, including under concurrent-action pressure; a delayed action is re-checked against current authority, not the authority at proposal time; a material proposal change after approval requires fresh approval and the old approval cannot settle the changed proposal (this is the #1393 invariant-5 lesson, applied to the IAAA delegation model, not only to the trade-approval workflow).

### R6 — Audit integrity, audit failure, and audit access are deferred, not decided

- **Evidence:** Epic §6 (blocking set, tamper detection, retention, audit access logged, outcome states). Spec §4 audit model and §7 Slice 5 defer all three decisions. Main's `iaaaAudit.ts` proposes a hash chain and a blocked/not-blocked classification but explicitly leaves retention unsettled.
- **Required negative tests:** audit failures are detected and handled per policy (spec §6 row 10); a consequential action in the blocking set is blocked, not executed, when durable audit cannot be recorded, and the failure itself is recorded or alerted by a defined path; a non-blocking action's audit failure is still detected and reconciled, not silently dropped; audit reads and exports are themselves audited; tampering with, reordering, or deleting an audit event is detectable by the hash-chain verification; an outcome is never recorded as "succeeded" merely because authorization passed or a tool call started.

### R7 — Session and CSRF controls are missing from the spec

- **Evidence:** Epic §4 requires secure cookie settings, CSRF protection for cookie-authenticated mutations, session duration/idle/absolute expiry, rotation, logout, revocation, and recovery behaviour. The spec's §4 session evolution lists only the new session fields; it never mentions CSRF, rotation triggers (privilege change, auth-method change, provider re-linking), or any duration value.
- **Required negative tests:** a cookie-authenticated mutation without a valid CSRF token is rejected; a session is rotated on privilege change and on auth-method change; an idle-expired session cannot be resurrected from a cached copy (main's `iaaaSessionActivity.ts` already warns that enforcing idle expiry against a cached copy is wrong in both directions — the adoption test must prove the fresh-read path); an absolute-expiry breach ends the session even under continuous activity; logout revokes the session server-side, not only by deleting a client cookie.

### R8 — Tenant isolation in retrieval, search, and asynchronous work

- **Evidence:** Epic §5 ("Enforce across APIs, background jobs, agent tools, storage, retrieval, artifacts, exports, and notifications") and epic §8 tenant-isolation demonstration. Spec §6 row 5 names direct IDs, search, exports, and jobs, but the spec's §5 matrix and §7 Slice 3 do not assign an owner or an inventory to the retrieval/search/job surfaces, which are the surfaces most likely to leak across tenants through an index, a cache, or a queued job created before a revocation.
- **Required negative tests:** search results, retrieval chunks, scheduled-job outputs, and notification payloads are tenant-filtered at the data layer, not only hidden in the UI; a job queued before a membership revocation is re-checked before it emits tenant data; a correlation ID does not leak tenant B's data into tenant A's trace or log view.

### R9 — Admin UI must not become a second authorization path

- **Evidence:** Spec §5 matrix grants membership, role, audit-read/export, and (for platform admin) platform permissions, but never discusses the admin UI. Main has a read-only admin UI (`src/client/IaaaAdminPanel.tsx`, `src/client/iaaaAdminApi.ts`, `docs/architecture/security/iaaa-admin-ui.md`, `tests/iaaa_admin_tabs.test.tsx`, `tests/iaaa_admin_api.test.ts`) described in the program record as fail-closed and usable only after the owner's post-activation re-login. The spec's silence is the risk: if the UI later gains write actions, every matrix permission needs a UI-to-API parity rule.
- **Required negative tests:** an admin UI action is denied when the same API action is denied (no UI-only privilege); the admin UI fails closed when the PDP flag is OFF or when the session lacks `internalUserId` (legacy session), rather than falling back to legacy scoping for admin actions; admin UI reads are audit-logged like API reads.

### R10 — Provider economics, exit, and assurance-level claims

- **Evidence:** Epic §9 ("A free authentication tier may still charge for custom roles, enterprise federation, organization scale, or audit features. Your application must fill any approved gaps rather than assuming the provider supplies all four pillars") and epic §2 ("do not assume social login establishes a person's legal identity or a particular assurance level"). Spec §3 states Auth0 costs are "not verified in this document" and that free-tier availability "must not be assumed," then recommends Option A "unless the cost verification in Open decisions changes it."
- **Required negative tests / verification (not code):** a written Auth0 cost verification covering custom roles, federation, organization scale, and audit retention/export, for production user counts — not development-mode availability; a provider-exit plan (identity export, binding migration, deletion) before Slice 2, so adopting Option A does not create an unplanned lock-in; no user-facing or audit claim that social login establishes legal identity or a NIST assurance level, unless a defined assurance profile is adopted (epic §4 cites NIST SP 800-63B-4; the spec never selects a profile).

## 3. Provider decision pack — recommendation, not a decision

**This section recommends; it does not decide. The provider decision stays an owner decision (with CTO + CISO input per spec §8), and no provider tenant, application, secret, or callback may be created on the basis of this draft alone.**

### Option A — Auth0 for identity, application-owned authorization — RECOMMENDED

- **What it is:** Auth0 (or Auth0 Organizations) issues human identities; the application binds validated `(issuer, subject)` to a stable `internalUserId` and owns tenant/workspace memberships, roles, delegation, the PDP, and audit evidence. This is the spec §3 recommendation and the epic's title option.
- **Why it is recommended:** it matches the epic's provider-selection matrix (§9) most directly; it keeps the authorization decision inside the application, where resource, tenant, delegation, approval, and context state actually live — the same reason the spec rejects Option C as the default; it leaves the core authorization layers provider-independent in design, so a later provider change does not require re-deriving the PDP; and it matches what main already implements for the application-owned layers (identity binding, membership, PDP seam, delegation, audit), so Slice 2 becomes a provider-boundary integration rather than a re-architecture.
- **What would change the recommendation:** the cost verification in §4. If Auth0's production pricing for custom roles, enterprise federation, organization scale, or audit features exceeds the approved budget, or if the owner OAuth/tenant actions required for Auth0 cannot be completed in the Slice 2 window, the fallback is Option B — not Option C.
- **Owner actions this option requires (not yet done, verified by absence on main):** create an Auth0 tenant and application, configure callbacks, provision the secrets through the approved channel (GitHub Actions secrets + deploy, never the dashboard alone and never in chat), and confirm the production cost tier. None of these exists on main today: zero Auth0 paths, zero Auth0 secrets referenced in the spec.

### Option B — Application-owned OIDC, Google + GitHub first, Auth0 later — FALLBACK

- **What it is:** keep GitHub OAuth, add Google through the same integration boundary, implement the internal identity, membership, PDP, delegation, and audit layers first, and add Auth0 later behind that boundary.
- **Advantages:** lowest immediate provider dependency and secret surface; the core layers are provider-independent and survive a later provider change; main already demonstrates the pattern (GitHub end-to-end defaults + Google defaults docs, OIDC validation and Google provider tests on main), so Slice 2 can proceed without waiting for an Auth0 procurement or tenant decision.
- **Disadvantages:** the application owns more of the provider-integration burden the spec names — session handling, step-up, recovery, token validation (including the R3 algorithm/JWKS/nonce rules), and federation — and that burden must be staffed with maintained libraries, not custom protocol code (epic §4). It also defers, but does not remove, the eventual Auth0 migration cost if Option A is later chosen.
- **When to choose it:** if Auth0 cost verification fails, if owner Auth0 actions are blocked, or if the owner prefers to prove the application-owned layers in production before adding a paid provider dependency. Choosing B now does not preclude A later, provided the provider boundary in §4 is kept clean and no Google/GitHub-specific assumption leaks into the PDP, membership, or audit layers.

### Option C — Auth0 for identity AND authorization — NOT RECOMMENDED as the default

- **What it is:** delegate roles and permissions to the provider's authorization features.
- **Advantages:** less application code for role storage and permission assignment; provider-managed role administration UI.
- **Disadvantages (decisive against the epic):** epic §5's decision inputs — resource relationship, tenant/workspace policy, delegation limits, approval requirements, and context — live in application state and cannot be evaluated by a provider role check alone; a token carrying provider permissions goes stale between issuance and a delayed or consequential execution, which conflicts with the re-check rule; provider pricing for exactly the custom-role, organization, and audit features this epic needs is the epic §9 warning, and it applies most strongly here; authorization availability becomes provider availability; and audit evidence would be split between the provider and the application, weakening the epic §6 single-trace requirement. The spec itself states this rejection "to be challenged in review" — this review upholds it.
- **What would be required to reconsider C:** a written mapping showing how each epic §5 check (resource, tenant, delegation, approval, context, re-check before delayed execution) is evaluated server-side in the application for every consequential action, not only in the UI or in a token, plus a cost and exit analysis. That mapping does not exist in the spec today.

### Decision the owner must make (presented, not made here)

1. Provider for Slice 2: Option A (recommended) or Option B (fallback). Option C only with the reconsideration mapping above.
2. If Option A: approve the Auth0 cost verification and authorize the owner-only Auth0 tenant/application/secret actions.
3. Tenant model: Auth0 Organizations vs application-owned tenants (spec §8, CTO + CDO, due before Slice 3) — this decision changes Slice 3's data model and must be made before, not during, Slice 3.

## What could not be verified from main (reported honestly, not assumed)

- **Production flag values.** `IAAA_WIRING_ENABLED`, `IAAA_PDP_ENABLED`, and `IAAA_BOOTSTRAP_ADMINS` are runtime environment values. Their presence in code and docs on main proves the flags exist; it does not prove their production values, whether the PDP is actually enabled in production, or whether the owner has completed the post-activation re-login the admin UI requires. No production endpoint was probed for this review.
- **Production behaviour.** `/api/me` exposing `internalUserId`, the read-only admin UI's fail-closed behaviour, Google login in production, and the genesis platform-admin grant are documented on main (GitHub/Google defaults docs) but were not live-tested here. Treat them as implemented-and-flag-gated, not as production-verified.
- **Test execution.** The `tests/iaaa_*.test.ts` files listed in this review were inventoried from the main tree; their contents were sampled (identity binding, session activity, delegation, audit, PDP seam, enforcement, bootstrap, login) but the full suite was not executed for this draft. A test file's existence is not proof that its named negative case passes.
- **Provider costs.** No Auth0 pricing was verified; the spec's own statement that costs are "not verified in this document" stands.
- **Microsoft provider.** Epic §4 contemplates Microsoft later through the same boundary. Main contains no Microsoft paths, and the spec contains no Microsoft timeline. That is a scope note, not a finding of non-compliance, provided adoption records it as deferred.
- **Legacy `mas_events` vs IAAA audit authority.** The spec's §2 description of legacy audit rows and main's IAAA audit module may both be accurate for their respective paths. This review did not determine which path is authoritative for each event type in production; adoption should state it.
