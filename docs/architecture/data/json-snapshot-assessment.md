## 2. Part A — Snapshot locations

A snapshot is a frozen copy of data that lives elsewhere, kept because the source can change and the copy must not. Under the zero-exception rule a snapshot is denormalization unless it is restructured into a reference to a versioned/immutable source — or the user rules the frozen fact is the value itself (a decision point, never an exception).

Comment: "Terms are snapshotted at issuance." The code VALUE is never stored — only its SHA-256 hash + display prefix. | The rule row can change after issuance; the code must keep the terms it was issued under. | Duplicated data, no FK to the rule row's terms, staleness by design. ## 3. Part B — Per-column JSON assessment

Conventions: **Store** D1 = `src/data/drizzleSchema.ts` (Drizzle mapping; DDL authority in `src/data/schemaComponent/d1Catalogue.ts` + `src/data/migrationRunner.ts`); DO = `src/data/schemaComponent/doCatalogue.ts` unless noted (ORM = `ormCatalogue.ts`, REM = `remainderCatalogue.ts`). **Line** is the mirror tip `b525e049`. **Readers** are the `src/` files referencing the column name (bulk `git grep` on `origin/main`; counts include the schema/catalogue files themselves). **Decomposed** means some query parses the JSON and reads/joins/filters on its parts (verified by `JSON.parse` + field access in the readers); **read whole** means it is written once and read whole, never decomposed. - **The 9 KEEP recommendations are decision points, not exceptions.** Under the zero-exception rule, if the user does not accept a KEEP, its CONVERT alternative (named in its row) is the fallback — there is no third option and no silent acceptance.
- **Sequencing:** the conversions land with their owning domains/slices — join tables with S4, EAV/typed settings with S8, the snapshot-reference conversions with the owning domain (referrals/bundles with the commerce domain, pipeline definitions with the job-pipeline domain), and the dataset-rows conversion with the dataset family. - **I/O classification method:** every column was classified by its actual readers/writers at mirror tip `b525e049` (`git grep` over `src/` for the column name, snake_case and camelCase; the adapter/service file is named in each row's I/O basis). ### 4.4 Input / Output / Both delineation

**Method:** INPUT = the JSON is written as an input to a process (a definition, config, payload, criteria, or request supplied by a user/system and consumed by an engine/job). OUTPUT = the JSON is produced as an output of a process (a result, report, summary, artifact, evaluation, or record generated by an engine/job). BOTH = the JSON is written as input and then updated/produced as output during its lifecycle (a task record created on submission and updated with results; a checkpoint written during execution and read back on resume; an active set written by promotion and consumed by runs). The I/O column on every row in §2 and §3 carries the class plus a one-line basis (writer → reader).
