## 1. Executive Summary & Context

Autonomous financial and quantitative trading platforms require a user experience that harmonizes two distinct operational paradigms:
1. **Conversational AI (Stock Copilot)**: Natural language reasoning, prompt-driven strategy formulation, automated diagnostic analysis, and asynchronous goal dispatch.
2. **Operational Workspace (Trading Desk & Telemetry)**: Deterministic execution grids, multi-leg bracket ladders, real-time pipeline telemetry, and high-density financial data visualizations.

When design patterns fracture between these modes, user cognitive load increases, risk of erroneous trade execution elevates, and maintenance velocity deteriorates. 

This document defines the architectural standards, industry frameworks, code-generation patterns, and generative UI techniques necessary to maintain a single, cohesive, accessible, and resilient user experience across the platform.

```
+--------------------------------------------------------------------------------+

+--------------------------------------------------------------------------------+
```

## 2. Industry Standards and Compliance Frameworks

### 2.1 WCAG 2.2 Level AA & WAI-ARIA Accessibility

Every interface component—whether statically rendered or dynamically generated by an agent—must satisfy Web Content Accessibility Guidelines (WCAG) 2.2 Level AA.

#### Core Technical Requirements:
1. **Target Size Minimum (Success Criterion 2.5.8 - Level AA)**:
   - All interactive touch and pointer targets must measure at least **24x24 CSS pixels**, or provide sufficient spacing (undershoot circle of 24px diameter does not intersect another target).
   - Primary operational triggers (Buy, Sell, Cancel, Confirm) must meet the enhanced **44x44 CSS pixels** target area to prevent accidental misclicks during live market conditions.
2. **Focus Appearance & Navigation (Success Criterion 2.4.11 / 2.4.13)**:
   - Never suppress focus indicators with `outline: none` without providing an explicit `:focus-visible` replacement.
   - All interactive components must render a distinct focus indicator: 2px solid ring with an offset of 2px using semantic token `ring-focus` (`rgba(59, 130, 246, 0.5)`).
   - Complex widgets (data grids, order books, bracket ladders) must implement roving `tabindex` or ARIA grid keyboard semantics (`ArrowUp`, `ArrowDown`, `Home`, `End`).
3. **Screen Reader Live Regions (WAI-ARIA 1.2)**:
   - Asynchronous streaming responses from Stock Copilot must use `aria-live="polite"` and `aria-atomic="false"` to prevent auditory disruption while streaming tokens.
   - High-consequence operational events (circuit breaker trip, order rejection, trade fill, safety stop) must announce through an `aria-live="assertive"` alert region.
4. **Accessible Naming & Form Controls**:
   - Every input, select, and button must possess an accessible name via explicit `<label>`, `aria-label`, or `aria-labelledby`.
   - Icon-only buttons must provide screen-reader-only descriptive text (`<span className="sr-only">Refresh quotes</span>`).
5. **Reduced Motion**:
   - Honor user preferences via `@media (prefers-reduced-motion: reduce)`.
   - Streaming text cursors, shimmer loaders, and chart animations must gracefully collapse to static visual indicators when reduced motion is requested.

### 2.2 Microsoft Human-AI Interaction Guidelines (HAX G1–G18)

Autonomous AI copilots must foster trust through transparency, controllable autonomy, and predictable error recovery. The 18 HAX guidelines are mapped directly into our interaction architecture:

| HAX Phase | Guideline | Platform Implementation |
| :--- | :--- | :--- |
| **Initially** | **G1: Make clear what the system can do** | Stock Copilot surfaces contextual quick action chips (e.g., `⚡ Generate strategy code`, `🧪 Run sandboxed backtest`, `📊 Screen momentum candidates`) on blank and active states. |
| | **G2: Make clear how well the system can do what it can do** | Tool results and backtest summaries surface clear confidence indicators, parameter bounds, and historical limitations. |
| **During Interaction** | **G4: Show contextually relevant information** | Surfacing portfolio exposure, active ticker symbols, and market state alongside Copilot recommendations without requiring prompt re-entry. |
| | **G5: Match relevant social and domain norms** | Financial calculations display recognized industry metrics (Sharpe ratio, max drawdown, win rate) formatted according to standard conventions. |
| **When Wrong** | **G9: Support efficient correction** | Generated code and strategies are stored in persistent sandboxes with interactive parameter editors, allowing single-click modifications. |
| | **G10: Scope services when in doubt** | High-uncertainty queries trigger interactive multi-choice disambiguation dialogs instead of making speculative trade executions. |
| **Over Time** | **G11: Make clear why the system did what it did** | Comprehensive step-by-step reasoning transparency, tool invocation audit trails, and execution logs visible in the tool preview drawer. |
| | **G13: Learn from user behavior** | System captures user approvals, favorite screeners, and risk tolerances in durable preferences to refine prompt context. |

### 2.3 OWASP Top 10 for Agentic Applications & UI Security

Autonomous agent interfaces present novel attack vectors (indirect prompt injection, unexpected tool invocation, unverified code execution). The presentation layer serves as the critical line of defense:

1. **Step-Up Human-In-The-Loop (HITL) Verification (ASI-01)**:
   - Consequential state changes (order dispatch, position liquidation, capital allocation, webhook configuration) require an explicit user confirmation dialog.
   - The UI displays an unforgeable Safety Guarantee banner (`🛡️ Safety Guarantee: No money has been moved. Explicit human authorization is required before execution.`).
2. **Indirect Prompt Injection Defense (ASI-02)**:
   - External inputs (untrusted web search scrapes, raw news feeds, peer agent messages) are sanitized and visually distinguished from system instructions using distinct styling and container boundaries.
   - Markdown parsers strictly forbid unsanitized HTML evaluation and execute inside isolated iframe/shadow DOM wrappers when rendering external web artifacts.
3. **Price Provenance & Staleness Protection**:
   - Financial quotes, option chains, and indicators must display origin provenance and freshness timestamps.
   - Stale data (>60s in active hours) triggers visual amber warning banners to prevent executing orders against cached prices.

### 2.4 W3C Design Tokens Community Group (DTCG) Standards

To ensure cross-surface consistency and eliminate arbitrary visual styling, all styles are derived from semantic design tokens organized in a strict 3-tier hierarchy:

```
Tier 1: Global Primitives
  color.palette.slate.900, color.palette.emerald.500, spacing.4 (16px), radius.md (6px)
       │
       ▼
Tier 2: Semantic Tokens
  color.surface.canvas, color.text.primary, color.status.success, spacing.container.pad
       │
       ▼
Tier 3: Component Tokens
  button.primary.bg, card.container.border, chip.action.hover, table.row.zebra
```

#### Core Token Rules:
- **Zero Raw Color Codes**: Hex codes (`#ffffff`, `#1e293b`), arbitrary RGB values, and naked spacing integers (`style={{ margin: 13 }}`) are forbidden in application pages and components.
- **Theme Equivalence**: Both Light and Dark modes share identical semantic token names. Switching themes updates token values without component-level branching.
- **Enforced via Static Analysis**: CI linting checks verify that all components consume tokens via approved utility classes or CSS variables.

## 3. Scaffolding Evolution: From Text-Splicing to AST Codemods

The platform's UI scaffold generation tool (`scripts/new-page.mjs`) automates the creation of conforming pages, test stubs, routes, and navigation items.

### 3.1 Comparison of Code Generation Strategies

| Dimension | Regex / String-Splicing CLI | AST-Based Codemods (`ts-morph`) | Declarative Schema Renderer |
| :--- | :--- | :--- | :--- |
| **Mechanism** | Regex line search and string insertion (`split('\n')`, `splice`) | Parses source code into TypeScript Abstract Syntax Tree (AST) | No code generation; reads JSON/Zod configuration at runtime |
| **Resilience** | Low; fragile to whitespace, formatting, and CRLF vs LF line endings | High; syntax-aware manipulation; immune to code layout or formatting changes | Complete; zero generated code to break, compile, or maintain |
| **Type Safety** | None; can generate syntax errors or unresolvable imports | Complete; verifies import specifiers and symbol existence | Complete; validated via Zod schema definitions |
| **Security Risk** | ReDoS or injection if dynamic regex patterns are improperly built | Zero injection risk; manipulates nodes deterministically | Zero injection risk; strictly bounded data model |
| **Maintenance** | Requires manual regex updates when file structure shifts | Updates node search criteria without affecting surrounding code | Single renderer codebase to test and maintain |

### 3.2 The AST Codemod Blueprint (`ts-morph`)

For files requiring programmatic modification (e.g., `src/client/routes.ts`, navigation registries), AST manipulation using `ts-morph` provides structural safety:

```typescript
import { Project, SyntaxKind, ObjectLiteralExpression } from "ts-morph";

export function registerConformingRoute(project: Project, routeId: string, componentPath: string): void {
  const routesFile = project.getSourceFileOrThrow("src/client/routes.ts");
  
  // 1. Add conforming component import safely
  routesFile.addImportDeclaration({
    moduleSpecifier: `./pages/${routeId}`,
    namedImports: [{ name: `${capitalize(routeId)}Page` }],
  });

  // 2. Locate routes array
  const routesArray = routesFile.getVariableDeclarationOrThrow("ROUTES")
    .getInitializerIfKindOrThrow(SyntaxKind.ArrayLiteralExpression);

  // 3. Prevent duplicate registration
  const exists = routesArray.getElements().some((element) => {
    if (element.isKind(SyntaxKind.ObjectLiteralExpression)) {
      const idProp = element.getProperty("id");
      return idProp?.getText().includes(`"${routeId}"`);
    }
    return false;
  });

  if (!exists) {
    routesArray.addElement(`{
      id: "${routeId}",
      path: "/${routeId}",
      component: ${capitalize(routeId)}Page,
      conforming: true,
    }`);
  }

  routesFile.formatText({ indentSize: 2 });
  routesFile.saveSync();
}
```

## 4. Complementary Approach: Declarative & Schema-Driven Views

While scaffolding generates physical source files, complex analytical and administrative views are more reliably served through **Declarative Schema-Driven UI**.

### 4.1 Concept & Architecture

Instead of writing custom JSX layout code for every new analytics view or diagnostic page, engineers define a typed schema (`PageDefinition`). A shared runtime renderer (`<DynamicPageRenderer />`) interprets the schema and renders conforming UI primitives.

```
+-----------------------------------+
|      Page Schema (JSON/Zod)       |
|  - Layout: Grid / Tabs            |
|  - Metrics: Cards / Sparklines    |
|  - Tables: Columns / Formats      |
|  - Actions: Triggers / Endpoints  |
+-----------------+-----------------+
                  |
                  v
+-----------------------------------+
|     DynamicPageRenderer           |
|  - Validates schema structure     |
|  - Applies WCAG 2.2 focus/labels  |
|  - Instantiates UI primitives     |
|  - Connects queries to DO/API     |
+-----------------+-----------------+
                  |
                  v
+-----------------------------------+
|     100% Conforming Interface     |
|     Zero Token Drift              |
+-----------------------------------+
```

### 4.2 Declarative Schema Specification

```typescript
import { z } from "zod";

export const MetricCardSchema = z.object({
  id: z.string(),
  label: z.string(),
  value: z.string().or(z.number()),
  changePercent: z.number().optional(),
  status: z.enum(["neutral", "success", "warning", "critical"]).default("neutral"),
  ariaDescription: z.string(),
});

export const DataGridColumnSchema = z.object({
  key: z.string(),
  header: z.string(),
  type: z.enum(["text", "number", "currency", "badge", "action"]),
  sortable: z.boolean().default(true),
});

export const PageSchema = z.object({
  id: z.string(),
  title: z.string(),
  subtitle: z.string().optional(),
  layout: z.enum(["dashboard", "detail", "split-view"]),
  metrics: z.array(MetricCardSchema).max(4).optional(),
  primaryGrid: z.object({
    endpoint: z.string(),
    columns: z.array(DataGridColumnSchema),
    rowSelection: z.boolean().default(false),
  }).optional(),
  actions: z.array(z.object({
    id: z.string(),
    label: z.string(),
    variant: z.enum(["primary", "secondary", "ghost"]),
    endpoint: z.string(),
    requireConfirmation: z.boolean().default(false),
  })).max(3).optional(),
});

export type PageDefinition = z.infer<typeof PageSchema>;
```

### 4.3 Key Benefits of Schema-Driven Views:
1. **Zero Design Drift**: Impossible for arbitrary CSS, rogue colors, or broken padding to enter the view.
2. **Instant Accessibility**: Focus trapping, ARIA roles, column headers, and live regions are implemented once in the renderer.
3. **Agent-Native Generation**: Autonomous AI agents can emit valid JSON schemas to generate custom operational dashboards on-the-fly without running compiler builds or git commits.

## 6. Component Primitive Hierarchy & Anti-Drift Guardrails

To prevent interface bloat and visual fragmentation, all views adhere strictly to the **Rule of Three** and the **Component Hierarchy**.

### 6.1 The Rule of Three (Visual & Behavioral Simplification)

No element family may exceed **3 distinct types/variants**:
- **Buttons**:
  1. `Primary` (high-emphasis background, semantic action trigger)
  2. `Secondary` (subtle border, secondary actions)
  3. `Ghost / Destructive` (transparent text-only or guarded red for dangerous actions)
- **Panels / Cards**:
  1. `Elevated` (standard workspace card with 1px border and soft shadow)
  2. `Subtle` (muted background for grouped metrics or secondary metadata)
  3. `Interactive` (clickable/hoverable card for strategy or instrument selection)
- **Badges / Status Indicators**:
  1. `Success / Active` (green palette token)
  2. `Warning / Pending` (amber palette token)
  3. `Critical / Halted` (red palette token)

### 6.2 Component Directory Structure

All components belong to the atomic structure under `src/client/components/ui/`:

```
src/client/components/ui/
├── button.tsx           # Conforming button primitives (Primary, Secondary, Ghost)
├── card.tsx             # Surface containers with standardized padding and borders
├── badge.tsx            # Status pills and categorical badges
├── dialog.tsx           # Accessible modal dialogues with focus trapping
├── input.tsx            # Form inputs with integrated label and error associations
├── table.tsx            # Data tables with keyboard navigation and sorting
├── metric.tsx           # Standardized KPI card with trend indicator
└── tabs.tsx             # Conforming ARIA-tab navigation strip
```

### 6.3 Anti-Drift Continuous Integration Checks

The design system's integrity is protected by automated tests in CI:
1. **Style Conformance Test**: Asserts that no `.tsx` or `.ts` files under `src/client/` contain inline `style={{...}}` properties.
2. **Color Palette Conformance**: Verifies that no arbitrary `#hex` or `rgb()` strings exist in page code.
3. **Component Re-export Conformance**: Ensures new pages import shared primitives from `src/client/components/ui/` rather than instantiating raw HTML buttons or inputs.
4. **Brand Neutrality Census (`tests/neutrality_census_3525.test.ts`)**: Ensures documentation and application code remain strictly provider-neutral without hardcoded third-party vendor names.

## 7. Dual-Surfacing Architecture: Conversational AI vs. Operational Workspace

The platform avoids the false dichotomy of "Chatbot vs. Traditional Dashboard." Instead, it implements a **Dual-Surfacing System**:

```
+---------------------------------------------------------------------------------+
|                                 DUAL SURFACING                                  |
+----------------------------------------+----------------------------------------+
|       Conversational AI Surface        |         Operational Workspace          |
|         (Stock Copilot Desk)           |         (Trading Desk & Grids)         |
+----------------------------------------+----------------------------------------+
| Role:                                  | Role:                                  |
| Discovery, intent parsing, continuous  | High-density analytics, monitoring,    |
| diagnosis, multi-turn reasoning.       | low-latency execution, verification.   |
|                                        |                                        |
| Core Mechanics:                        | Core Mechanics:                        |
| - Streaming thought processes          | - Multi-column responsive data grids   |
| - Interactive action chips             | - Real-time websocket price streams    |
| - Generative UI parameter cards        | - Multi-leg bracket order ticket       |
| - Tool attribution and proof slips     | - Strategy backtest performance matrix |
|                                        |                                        |
| Handoff:                               | Handoff:                               |
| One-click transition to full workspace | Deep-link to Copilot with preloaded    |
| ("Open strategy in Workspace ->")      | context ("Ask Copilot about this row") |
+----------------------------------------+----------------------------------------+
```

### 7.1 Cross-Surface Interaction Patterns:
1. **Chat-to-Workspace Handoff**: When a Copilot conversation yields a complex strategy or multi-symbol screen, the generative card displays an `Open in Workspace` link. Clicking navigates to `/workspace?strategyId=...`, populating the trading desk with the exact parameters formulated in chat.
2. **Workspace-to-Chat Handoff**: Every table row in the operational grid provides an `Ask Copilot` action. Triggering this opens the Copilot drawer with the symbol, current quote, and active indicators already injected into the conversational context.

## 8. Implementation Roadmap & Quality Checklist

For all future UI changes, features, and agentic workflows, follow this implementation checklist:

- [ ] **Standards Adherence**:
  - [ ] All clickable elements meet 24x24px minimum (44x44px for primary order buttons).
  - [ ] Visible `:focus-visible` ring on all interactive elements.
  - [ ] Screen reader announcements configured via `aria-live` appropriately.
- [ ] **Design System Integrity**:
  - [ ] Built exclusively from `src/client/components/ui/` primitives.
  - [ ] Adheres to the Rule of Three (maximum 3 variants per element family).
  - [ ] Zero raw hex codes or inline styles; all styles derive from semantic design tokens.
- [ ] **Agentic Transparency & Safety**:
  - [ ] High-consequence financial actions require explicit step-up confirmation.
  - [ ] Price data surfaces freshness timestamps and provenance indicators.
  - [ ] Copilot responses provide interactive action chips for next logical turns.
- [ ] **Automated Verification**:
  - [ ] Passes typecheck (`npm run typecheck`).
  - [ ] Passes UI test suite (`npm run test:ui`).
  - [ ] Passes brand neutrality census (`tests/neutrality_census_3525.test.ts`).
  - [ ] Passes zero-deletions gitops gate policy (§22).
