## Problem

"Which strategies are active?" has four answers today on the options side: 4 sandbox ids (`sma_crossover`, `rsi_reversal`, `mean_reversion`, `breakout` — only 2 real rules, no RSI computed), a 6-member backtest enum whose emitted code is SMA for all 6, a 73-id client library, and 75 claimed in OODA. The 73/74/75 counts are options-only and never included stock. A dedicated stock-patterns catalog also exists: `src/trading/setupCatalog.ts` holds 2 stock pattern families (`trend_breakout`, `pullback_reversion`) with the stock-only read model `src/workflows/stockPatternCatalog.ts` (version pinned "1"), surfaced by the Stock Hub Patterns view (`?tab=stock-hub&view=patterns`). No strategy-definition table exists anywhere; definitions live in code. Usage by id is partial and split: the track record is keyed by the 10-name OODA vocabulary, outcome tracking has no strategy-id field, and there is no usage-count table. Four stores answer "which strategies are active", two backtests exist (one never invoked), three engines answer one NLQ screen, and at least two ranking systems exist. The label systems (screener signal, RangeZone, ValueZone, dayAction, composite bias, grades, QuantRating, macdSignal) are first-class signal rules in the registry — see Formula registry; the examples are seeded from the 2026-11-26 inventory and are not a closed set.

## Principles (owner, 2026-11-26)

Reuse first, build platform-wide, no one-off solutions; reduce duplication to just one of everything — lossless/additive consolidation. Rank improvements by business value, technical effort, risk reduction, and user impact; map each optimization through reuse/enhancement/consolidation to the workflows, efficiencies, or outcomes it unlocks for end users. One engine, one scheduler, one ledger, one code base, one of everything.

## Target

One stock catalog, then one options catalog, then one pattern/study catalog on top (Thinkorswim, #6404 — a build, not a third strategy list). Canonical catalogs live server-side, versioned, in D1, served by one `CatalogService` (`get` / `list` / `resolve`) — created in P0; it does not exist on `main` today (0 hits). Every formula is one versioned rule definition in D1 (see Formula registry), and every registry, selection, and loop capability must become code reachable via UX and chat/MCP (see Must become code). The client is a view: a cached, version-stamped read view; the Builder keeps only local modeling of legs being edited (the Discovery thin-client pattern — server evaluates and ranks; panel file attribution unverified, see survey §3). ## Catalog model (D1)

Tables: `strategies` (id, kind stock|options, name, version, status, definition + params, gates, owner), `strategy_aliases` (every old id → exactly one canonical id, forever), `strategy_versions` (append-only), usage recorded per run (`strategy_id` + `strategy_version` + run ref on every screen, evaluation, backtest, and paper run). Seed from code definitions. Alias table first: nothing is deleted before the stock reconciliation (7 named entries / 5 distinct rules) and the options reconciliation (73/74/75, options-only) are recorded. P0 stock total: 7 named entries — 2 stock patterns, 4 sandbox strategy ids (2 real rules), 1 base breakout. Scope note (inventory sweep 2026-11-26): the scattered stock pattern-like material totals ≈44 consolidation units (≈120+ raw named items before dedup) — 5 patterns/setups, 3 executable strategies, ~19 indicators/primitives, 7 label systems, ~10 scoring/threshold config blocks (~60 tuned values). P0 covers the 7 entries (patterns/setups + strategies) only. Indicators stay as primitives the catalog references (they are not entries); labels stay as classifications emitted by evaluation; thresholds become catalog config attached to entries. Growth candidates if promoted later: 2 momentum-gate ideas, 8 presets starters, the ORB gate (needs a wired minute-bar caller; the adapter capability exists — Yahoo 1–90Min, Alpaca 1–59Min — with no production caller wired).

Status model: draft / active / disabled / deprecated / retired. A disabled entry is excluded from selection; existing runs keep their reference. Removal is soft-delete/deprecate only, with the alias retained, and blocked while usage-by-id shows the entry in use.

## Formula registry (amendment 2026-11-26)

Every formula/rule — indicator, pattern, signal, strategy, scoring rule — is **one catalog rule definition in D1 with a stable id**. No formula is defined in code; no parameter is a code constant. The computation functions stay in code (`technicals.ts` stays 20 pure `compute*` / `classify*` / `detect*` / `evaluate*` functions; the evaluator stays code); the catalog owns the rule *definition* — id, kind, parameters, data requirements, output contract — and references indicator keys rather than owning the arithmetic. The precedent is OODA's `researchRules.ts` (21 keys, bounds, version stamp).

**Rule kinds:** **indicator** (a computation over price/volume, no trade decision — RSI, MACD, VWAP, ATR, Bollinger); **pattern / setup** (a named configuration with entry/exit/guardrail semantics — `trend_breakout`, `pullback_reversion`, `baseBreakout`, ORB); **signal / label** (a classification emitted by evaluating indicators/patterns against thresholds); **strategy** (a named rule + position state + simulation, executable in sandbox/backtest); **scoring rule** (a formula that produces a score or rank — `screenScore`, `momentumScore`, the 6-vote composite, factor grades). The ≈44 scattered units map onto these kinds: the 5 patterns/setups and 3 executable strategies are rule definitions (the P0 7 entries are the first of these); the ~19 indicators are indicator rules; the 7 label systems are signal rules; the ~10 scoring/threshold config blocks become *parameters* attached to rule definitions, not separate rules.

**Labels as first-class signal rules.** The label systems are signal rules with the same treatment as every other rule — parameter schema (thresholds as versioned parameters), data-requirements block, output contract, downstream consumers: screener signal labels (RSI-gated: `OVERBOUGHT` when RSI > 70, `OVERSOLD_BOUNCE` when RSI < 35 — value set to be re-verified in P1; only `RANGE_BOUND` was re-verified in the 2026-11-26 sweep) **and** RangeZone labels (52-week range position — explicitly NOT RSI; the two overboughts are different labels from different inputs and must not be conflated); ValueZone labels and factor Value grades (P/E percentile + 52-week-low distance) for undervalued/overvalued; dayAction/sentiment (5 labels), composite bias (Bullish/Bearish/Neutral, 6-vote), Grade (A+…F), QuantRating (5 levels), macdSignal strings (display/classification only). What a label determines once applied is part of its output contract — e.g. `OVERBOUGHT` feeds the screener signal column and the overbought filter; ValueZone feeds the value grade and the `screenScore` value term. **These examples are seeded from the 2026-11-26 inventory and are NOT a closed set:** the complete label/signal vocabulary is defined by the competitive evaluation work — which lives in docs, not issues (verified 2026-11-26: 13 issue searches, 0 issues found). Core doc: `docs/architecture/application/screener.md` §12 Competitive Benchmark & Industry Excellence Gap Analysis + §13 SWOT & Remediation Roadmap; also `docs/architecture/business/brokerage-data-matrix.md`, `docs/architecture/enterprise/assessment/comprehensive-enterprise-strategy-and-capabilities-assessment.md` (Competitor Watch), `docs/architecture/enterprise/agentic-IROS.md` (Goldman Marquee comparison), `docs/architecture/code/screener-01.md` §6. The six §12 gaps have NO covering issue and would need creating, not moving: (1) factor grades engine — Seeking Alpha parity (5 factors; today only Value + Momentum graded), (2) fundamental growth grading + quarterly fundamentals feed — Navellier parity (8-point grading), (3) NLP earnings-call/transcript sentiment — AlphaSense parity, (4) dark pool & institutional flow — Forbes parity, (5) IV surface & Greeks analytics, IV Rank/Percentile — TradeStation/Barchart parity, (6) multi-leg strategy graph & tail-risk solver — quant-fund parity. Competitor-parity issues already in #6593: #6404 Thinkorswim, #6607 P3, #3929 Yahoo fundamentals, #3306 broker-neutral paper trading. Label-vocabulary consequence: the registry label set is completed from this work — factor-grade labels for all 5 factors, Navellier composite grades, IV Rank/Percentile, transcript/guidance sentiment labels; the four screener labels (overbought/oversold/undervalued/overvalued) are the screener's own, confirmed not extended by the competitive docs. P0 scope is unchanged: labels are signal rules in the registry, referenced by entries and emitted by evaluation — not additional P0 entries.

**Parameter schema and versioning.** Every rule carries parameters (`name`, `type`, `bounds`, `default`, `version`), grouped by role — computation, gate, risk, selection. Bounds are data, enforced by the UX and the evaluator; an out-of-bounds value is rejected, never clamped silently. **A parameter change creates a NEW version; history is never mutated.** Rule versions are append-only; every result records `rule_id` + `rule_version` + parameter values + data provenance, so a backtest, screen result, hunt level, paper trade, and calibration row all trace to the exact formula version that produced them. Who approves a parameter change is open (human investment authority TBD); until named, approval follows the draft → active human-approval path with the approver recorded.

**Data-requirements block.** Every rule declares `fields`, `barsMinimum`, `timeframe`, `provider`, `freshness`, and `failClosed` behaviour (missing or below-minimum data → the rule abstains and the job records the abstention; never a display default — the research view rendering a missing RSI as "50.0" is the named anti-pattern). The block is checked *before* a job runs, and the feed/scheduler jobs read a job's data needs as the union of its selected rules' blocks. Worked minima (2026-11-26 sweeps): RSI14 ≥ 15 bars, MACD ≥ 27 bars, Bollinger squeeze 144 closes for a true 125-day minimum, `trend_breakout` 50 closes + 20-day volume average, `sma_crossover` 20 closes, hunt levels min 5 bars. The ORB gate is recorded as **unmet** (wiring): it needs 1-minute bars aggregated to 15-minute buckets, and no production caller is wired to a minute-bar feed — whether to build the caller is an open decision, not a P0 item.

**Universe / feed mapping (verified 2026-11-26, `main`).** Providers: stock-screen providers are `etrade | yahoo | alpaca | public` (`STOCK_SCREEN_PROVIDERS`, `src/trading/screenerPipeline.ts:210-211`); the screening-provider registry (`src/trading/screeningProvider.ts`) holds 3 descriptors (`etrade-yahoo-stocks`, `dynamic-options`, `broker-neutral-stocks`) and resolves the first registered provider serving the asset class, else throws. Default stock screen provider is `alpaca`, mode `paper` (`config/vocabulary.json`). Universes (`src/trading/universes.ts`) are selectors over the live Nasdaq listings directory, never stored ticker arrays: TECH, NASDAQ100 (top 100 by market cap), SP100 (top 100), SP500 (top 500), RUSSELL2000 (market-cap ranks 1001–3000 — 2,000 selected, but only 200 quoted by default), ETF, LEV_ETF; `ALL` is a shard plan, not resolvable for a single run. The curated universe (`src/config/curatedStockUniverse.json`, 161 entries) is NOT a fallback for the live listings feed.

| Data requirement | Universes enabled | Feeds / providers enabling it |
|---|---|---|
| Daily bars (OHLCV) | All screener universes; curated 161-symbol universe for Yahoo mode | Yahoo only in the live history path (`platformHistory.ts`, `1D`, last 60 bars of a 6mo window); Alpaca/Public declare `historicalBars` at adapter level but are not the routed history provider; E*TRADE has no `historicalBars` (quotes + chains only) |
| Live quotes | All universes; membership from live Nasdaq listings | E*TRADE, Yahoo, Alpaca, Public via the provider binders; E*TRADE + Yahoo gap-fill composition in `live-quotes` mode |
| Volume | Rides the daily bar | Daily bars (Yahoo / Alpaca / Public) |
| Options chains | Symbol-driven, not universe-driven | E*TRADE, Alpaca, Public only; Yahoo has none; a broker without a chain source fails closed (`provider_unsupported`) |
| Minute / intraday bars | None wired | Capability exists (Yahoo 1–90Min, Alpaca 1–59Min, Public intraday aggregations; added #1654 slice 8) — no production caller; ORB unmet until a caller is wired |

Two flagged items, not asserted as bugs: `screenerConfig.yahoo.historyRange "3mo"` is possibly stale against the platform path's 6mo window (remaining consumers unverified); `config/vocabulary.json` `providerDatasets` lists no `public×historicalBars` and no `alpaca×historicalBars` / `alpaca×news` rows though the adapters declare those capabilities (follow-up check for feed jobs).

**Output / thesis contract.** Every rule declares `outputType` (`value` / `match` + strength + guardrails passed / `label` / `enter-exit` / `score`), a `thesisFragment` (the human-readable claim with evidence slots filled from the rule's own evaluation — e.g. `trend_breakout` → "Bullish breakout thesis: {symbol} closed above its rising 50-day SMA with volume {volumeRatio}× its 20-day average (guardrail 1.2×)"), `downstream` consumers, and `trace` fields (`rule_id` + `rule_version` + parameters + data provenance). Same inputs + same version → same outputs (replay parity).

**Selection model.** A job — screen run, opportunity hunt, copilot cycle, goal screen, NLQ screen — references a set of catalog ids: one, some, or all. Selection is a property of the *job*, not of the formula; it is resolved at runtime through the CatalogService port against the rule versions active at that moment and recorded on the run (ids *and* versions, so a result replays exactly). Channels, UX and chat/MCP first: UX (screen criteria panel, copilot panel, Patterns view, `?tab=strategy-catalog` in P4), chat (`stock_copilot_control{strategies}`), MCP (`copilot.strategies.set`, `catalog.list` / `catalog.get`, `run_stock_screen`, `stock_copilot_evaluate`), REST (`GET /api/catalog/strategies`, new in P1), scheduled invocation by reference (the hunt goal `search.opportunity_hunt` selects by catalog id, so disabling a rule removes it from the hunt without a code change). Unknown ids are rejected with a named error, never silently dropped. The `mas_settings` G-7 block is the known obstacle to moving the copilot selection into this model and is addressed in P1, not worked around.

## Must become code

Every registry, selection, and loop capability in this amendment MUST be reachable via UX and chat/MCP — a capability that exists only in these docs does not count as delivered: P0 delivers the registry + CatalogService port; P1 delivers selection through the channels above for all 13 consumers; P4 delivers parameter and label editing in lifecycle UX (bounds enforced, new version on change, approval path, audit); the autonomous loop is delivered through #3675 (see below). Registry KPIs: % of the ≈44 scattered units externalized as registry rules or parameters; % of jobs whose selection resolves through the catalog (target 100% of the 13 P1 consumers); % of results carrying `rule_id` + `rule_version` + parameters + data provenance (target 100%); replay parity on pinned cases (target 100%); unknown-id selections rejected with a named error (target 0 silent drops).

## Autonomous copilot loop over MCP (amendment 2026-11-26)

The loop is **OODA applied to stocks** — the loop discipline, not a new module. Each stage maps to machinery that already exists, plus the gaps the catalog closes:

| OODA stage | What it is for stocks | Existing machinery | What the catalog / this amendment adds |
|---|---|---|---|
| **Observe** | Gather the market state the loop reasons over | Screener runs (manual + scheduled), technicals feed jobs (persisted Yahoo/NASDAQ100 daily bars), quotes via the provider registry | Jobs declare their data needs from the rules they select (data-requirements block), so the feed job fetches what the loop needs before it runs |
| **Orient** | Evaluate patterns, score, rank, calibrate | `evaluatePatternSignalAt` / `evaluateLatestPatternSignal`, `screenScore` / 6-vote composite / factor grades, `RecommendationKernel`, calibration report | Evaluation reads rules from the catalog (not direct import); every score traces to a rule version; calibration is keyed by rule id + version, so Orient learns per rule instead of per name |
| **Decide** | Which signals become orders, under risk gates | Copilot policy (exit-plan policy, stop/TP), learnings policy (`riskBlockAt: 2`, `sessionLimitAt: 2`), autopilot's policy-verdict gate as the pattern for a gate (not the decision-maker) | The Decide policy is itself a set of catalog rules (gates + risk parameters) — the policy is data, versioned and auditable, not a code branch |
| **Act** | Place the order | Base-breakout MCP tool (`alpaca_execute_order`, `entryMode: "baseBreakout"`, `dry_run` parameter); ladder state via DO adapter | Act runs on **Alpaca paper only**, through the human-in-the-loop preview/approval gate — see boundaries below |

**MCP as the control plane.** One tool per stage, all bound to the same engine and the same catalog: Observe — `run_stock_screen` (a screen job carrying a selection); Orient — `stock_copilot_evaluate` (an evaluation job carrying a selection) and `catalog.get` (the rule being evaluated); Decide — `stock_copilot_control` (selection + pause/resume) and the policy-gate read; Act — the order tool with `dry_run` and the HITL preview/approval step. A human driving the loop from chat uses the same tools the loop itself uses — there is no separate "autonomous" path and "manual" path. **Evaluation is built into the loop, not bolted on:** every loop run writes to the runs ledger (`mas_async_jobs`) and to outcome tracking by catalog id, feeding calibration. The loop is validated by the same machinery as the catalog: walk-forward backtest (`screenBacktest.ts`, folds 3, holding 10 bars), the sandbox backtest wired in as an invocation path (#5213), and replay parity.

**Boundaries — stated explicitly, not implied:** **autonomous through Decide; Act on orders stays human-gated.** The loop runs itself from Observe through Decide. An order — even a paper order — is proposed, previewed, and approved by a human before it is placed (the #3675 design: paper-first, human-in-the-loop preview/approval gate; this amendment does not weaken it). **Paper only:** Alpaca paper mode only. Live trading is out of scope entirely and needs a human investment authority decision; that authority is still TBD and is not invented here. **No second loop:** #3675 [Epic] Realtime RSI is the existing vehicle for the real-time/autonomous loop (S1 scoring loop and S2 ticker are squarely CIO; S3 orders and S4 portfolio touch order placement and portfolio management). This amendment's loop reuses and consolidates with #3675 — it does not build a parallel loop. One engine, one scheduler (ScheduledAgent), one ledger (runs ledger). The #3675 triage decides the epic's scope; the loop design here is the design the triage applies. **The loop does not approve itself:** it never approves its own strategy or model promotion, never changes risk gates or scoring weights on its own authority, and never presents backtest/paper results as realized.

## Screen vs hunt — recorded decision: NOT combined (amendment 2026-11-26)

**The stock screener and the opportunity hunt are NOT combined. One evaluation engine, two jobs.** At the evaluation layer it is just code evaluating formulas — and that layer is exactly what gets unified: after P1, both jobs call the same evaluator through the same CatalogService port, and the hunt stops re-running evaluation itself. But the jobs stay separate because they have different contracts: the **screener is a query** over a universe (which symbols match these criteria right now? batch, on demand or scheduled, output a ranked list; consumers NLQ, goal screens, copilot, research); the **hunt is a monitor** over already-evaluated signals (which of them have actionable entry levels *now*? it consumes screener/copilot output and adds entry band, stop, take-profit; its own cadence, the `0 7 * * *` scheduled goal, from persisted feed-job bars; it produces a report). Merging would collapse a pipeline stage and lose the calibration seam (screen results carry catalog ids; hunt levels derive from them), and would force one contract onto two different cadences, inputs, and consumer sets. The two jobs only *look* combinable today because the hunt re-runs evaluation itself by direct import instead of consuming screener output — that is the fragmentation P1 fixes. One of everything at the engine level, distinct workflows above it.

## Storage boundary — D1 is the system of record

D1 `AGENT_DB` (`agentdb`) is already bound in `wrangler.jsonc` (~130 `agent_*` tables in `drizzleSchema.ts`); no strategy table in D1 today. New Drizzle migration following the IV-history precedent (#2337: D1 adapter production when bound, env rollback lever, started empty with no backfill — the catalog differs by seeding from code, not starting empty). Port + D1 adapter following `d1IvHistoryAdapter.ts`, env rollback lever per store (`<STORE>_D1_ENABLED=false` back to the DO adapter).

**D1 is the system of record for all durable application data.** DO holds no system-of-record data: what stays in DO is runtime state only (chat store, hibernated sockets, alarms), which is transient by definition, never a record. Sessions/tokens/keys migrate last (D-I step 5). The weights/policy cluster stays out of the catalog tables by design only until the promotion unit is redesigned (ADR 0040): it references catalog ids by string; it is not absorbed. Tenancy: D1 is shared/global by design; per-login isolation by construction becomes tenant-scoped columns + query discipline on every moved table — catalog definitions are platform-wide, per-user selections stay tenant-scoped. Catalog ↔ weights consistency is eventual, not atomic (no cross-store transaction exists; ADR 0033).

## Compliance summary

- **Reuse:** the port/adapter pattern (IV-history D1 adapter precedent — `CatalogService` itself is created in P0, not reused; 0 hits on `main` today), the `researchRules.ts` externalization pattern, the Discovery thin-client pattern, existing DO SQLite adapters as the migration source. Reuse order (gitops §7): reuse, enhance, optimize, consolidate, extend.
- **Tech stack (libraries first):** `docs/technology/tech-stack.md`; ADR 0034 D4 — best-fit FOSS first, custom code only where no best-fit FOSS piece exists, and an existing working repo capability always wins over both.
