## Problem

"Which strategies are active?" has four answers today on the options side: 4 sandbox ids (`sma_crossover`, `rsi_reversal`, `mean_reversion`, `breakout` — only 2 real rules, no RSI computed), a 6-member backtest enum whose emitted code is SMA for all 6, a 73-id client library, and 75 claimed in OODA. The 73/74/75 counts are options-only and never included stock. A dedicated stock-patterns catalog also exists: `src/trading/setupCatalog.ts` holds 2 stock pattern families (`trend_breakout`, `pullback_reversion`) with the stock-only read model `src/workflows/stockPatternCatalog.ts` (version pinned "1"), surfaced by the Stock Hub Patterns view (`?tab=stock-hub&view=patterns`). No strategy-definition table exists anywhere; definitions live in code. Usage by id is partial and split: the track record is keyed by the 10-name OODA vocabulary, outcome tracking has no strategy-id field, and there is no usage-count table. Four stores answer "which strategies are active", two backtests exist (one never invoked), three engines answer one NLQ screen, and at least two ranking systems exist.

## Principles (owner, 2026-11-26)

Reuse first, build platform-wide, no one-off solutions; reduce duplication to just one of everything — lossless/additive consolidation. Rank improvements by business value, technical effort, risk reduction, and user impact; map each optimization through reuse/enhancement/consolidation to the workflows, efficiencies, or outcomes it unlocks for end users. One engine, one scheduler, one ledger, one code base, one of everything.

## Target

One stock catalog, then one options catalog, then one pattern/study catalog on top (Thinkorswim, #6404 — a build, not a third strategy list). Canonical catalogs live server-side, versioned, in D1, served by one `CatalogService` (`get` / `list` / `resolve`) — created in P0; it does not exist on `main` today (0 hits). The client is a view: a cached, version-stamped read view; the Builder keeps only local modeling of legs being edited (the Discovery thin-client pattern — server evaluates and ranks; panel file attribution unverified, see survey §3). One evaluator per kind, one ranker (`RecommendationKernel`), one screen engine (including channel NLQ — #6271 binds `stockScreenPort`), one backtest (walk-forward `screenBacktest`; the sandbox run is wired in as its invocation path, #5213, not a parallel backtest).

## Catalog model (D1)

Tables: `strategies` (id, kind stock|options, name, version, status, definition + params, gates, owner), `strategy_aliases` (every old id → exactly one canonical id, forever), `strategy_versions` (append-only), usage recorded per run (`strategy_id` + `strategy_version` + run ref on every screen, evaluation, backtest, and paper run). Seed from code definitions. Alias table first: nothing is deleted before the stock reconciliation (7 named entries / 5 distinct rules) and the options reconciliation (73/74/75, options-only) are recorded. P0 stock total: 7 named entries — 2 stock patterns, 4 sandbox strategy ids (2 real rules), 1 base breakout. Scope note (inventory sweep 2026-11-26): the scattered stock pattern-like material totals ≈44 consolidation units (≈120+ raw named items before dedup) — 5 patterns/setups, 3 executable strategies, ~19 indicators/primitives, 7 label systems, ~10 scoring/threshold config blocks (~60 tuned values). P0 covers the 7 entries (patterns/setups + strategies) only. Indicators stay as primitives the catalog references (they are not entries); labels stay as classifications emitted by evaluation; thresholds become catalog config attached to entries. Growth candidates if promoted later: 2 momentum-gate ideas, 8 presets starters, the ORB gate (needs a minute-bar feed and a production caller).

Status model: draft / active / disabled / deprecated / retired. A disabled entry is excluded from selection; existing runs keep their reference. Removal is soft-delete/deprecate only, with the alias retained, and blocked while usage-by-id shows the entry in use.

## Consumers, in migration order

Stock first: copilot loop → on-demand evaluation → stock screener → NLQ screens → opportunity-hunt (its thresholds move with it) → Patterns view (enhanced/reused — see below) → base-breakout MCP → sandbox code-gen taxonomy → sandbox backtest → walk-forward backtest → goal operations → copilot panel → calibration/outcomes (last). P1 has 13 consumers in sequence; see plan §2 for the full list. Goal screen vs scheduled goals (verified separate, 2026-11-26): the goal screen (`?tab=goal-screen`, `GoalScreenPanel`, `POST /api/screening/goal-screen` → A2A `screener.run_goal_screen`, stock leg then options leg) is a screen run with `source:"goal"` and belongs to the stock-screener consumer (P1 step #3) — its goal taxonomy structures are options-only and the stock leg carries only the 3 momentum filter values; no `goalId` is involved. Scheduled goals (`ScheduledGoal` entities — id/cron/operation/budget/enabled, executed by `ScheduledAgent`) are P1 step #11 "goal operations": they only invoke operations and follow the operations they invoke. No built-in scheduled goal invokes a goal screen. Only when every stock consumer reads the catalog and old sources are switched off do options start: OODA (vocabulary extended 10 → 74) → options screener → Discovery → recommendation kernel. Autopilot needs no migration (verified: policy verdict gate, no strategy content). Goal workflows hardcode nothing.

## Stock patterns — reuse, not rebuild

P0 enhances and reuses the Stock Hub Patterns view (https://agent.openaimp.com/?tab=stock-hub&view=patterns): the view, the `listStockPatterns` / `stockPatternById` read-model shape, and the Apply-to-New-Screen flow (`patternRef` on the run) stay; the data source moves from hardcoded `setupCatalog.ts` (version pinned "1") to D1 via CatalogService; the add/update path v1 explicitly lacks is added; the `pairedStrategies` vocabulary leak (client-only `bull_call_spread` referenced from the setup catalog) is fixed. P0 does NOT build a stock-pattern catalog from scratch — one already exists. Open scoping question (decided during P0): `setupCatalog.ts` also holds 2 options families (`defined_risk_spread`, `pmcc`); P0 covers the stock families — whether it moves the whole file or only its stock families is decided during P0, and the options families naturally belong to P2. P0 inventory item: `GET /api/trading/setup-catalog` (fetched by `src/client/SetupCatalogPanel.tsx:30`) is a server setup-catalog endpoint whose server source file was not established; P0 inventories it and decides whether it is a separate catalog to absorb, a view over `patternSignals`, or the seed for the patterns side of the stock catalog.

## Storage boundary — D1 is the system of record

D1 `AGENT_DB` (`agentdb`) is already bound in `wrangler.jsonc` (~130 `agent_*` tables in `drizzleSchema.ts`); no strategy table in D1 today. New Drizzle migration following the IV-history precedent (#2337: D1 adapter production when bound, env rollback lever, started empty with no backfill — the catalog differs by seeding from code, not starting empty). Port + D1 adapter following `d1IvHistoryAdapter.ts`, env rollback lever per store (`<STORE>_D1_ENABLED=false` back to the DO adapter).

**D1 is the system of record for all durable application data.** DO holds no system-of-record data: what stays in DO is runtime state only (chat store, hibernated sockets, alarms), which is transient by definition, never a record. Sessions/tokens/keys migrate last (D-I step 5). The weights/policy cluster stays out of the catalog tables by design only until the promotion unit is redesigned (ADR 0040): it references catalog ids by string; it is not absorbed. Tenancy: D1 is shared/global by design; per-login isolation by construction becomes tenant-scoped columns + query discipline on every moved table — catalog definitions are platform-wide, per-user selections stay tenant-scoped. Catalog ↔ weights consistency is eventual, not atomic (no cross-store transaction exists; ADR 0033).

## Lifecycle (Phase 4, UX at `?tab=strategy-catalog`)

Browse/search/compare → add (draft, with owner) → update (new version; old version retained and resolvable) → enable/disable (status flag) → remove (soft-delete/deprecate only, alias retained, blocked while in use) → clone → promote draft → active (human approval — recommend-only authority). Every change audited (who, when, version). One new page, `?tab=strategy-catalog`, tabs `view=stock` / `view=options`, in the Intelligence section of the left nav between Stock Hub (navOrder 5) and Options Screener (navOrder 6). Existing surfaces link to it rather than duplicating it. Everything is externalized, configurable, and manageable through UX/Chat with full lifecycle.

## Compliance summary

- **Reuse:** the port/adapter pattern (IV-history D1 adapter precedent — `CatalogService` itself is created in P0, not reused; 0 hits on `main` today), the `researchRules.ts` externalization pattern, the Discovery thin-client pattern, existing DO SQLite adapters as the migration source. Reuse order (gitops §7): reuse, enhance, optimize, consolidate, extend.
- **Tech stack (libraries first):** `docs/technology/tech-stack.md`; ADR 0034 D4 — best-fit FOSS first, custom code only where no best-fit FOSS piece exists, and an existing working repo capability always wins over both. No new scheduler, ledger, or catalog store — ScheduledAgent, runs ledger, and D1 `AGENT_DB` already exist.
- **Security:** IAAA; RBAC (default-deny, `docs/architecture/security/authz.md` §2). TBAC is a gap — no task-based access control model exists in the repo; to be defined in Phase 4 or restated as RBAC-only. Do not claim TBAC compliance until it exists.
- **One of everything:** one scheduler (ScheduledAgent), one ledger (runs ledger, `mas_async_jobs`), one engine, one catalog per kind, one store for durable data (D1). Acceptance test from the lifecycle doc: "what existing one thing does this invoke?"
