Reading the number: most of the 211 are not "contexts" in the identity/config sense. 83 of them (57 route + 26 ports) are dependency-injection bags — one per route or extracted module — and 77 are config objects. The identity/execution core is 17 definitions covering about 10 logical contexts. The problem is not one number; it is three separate proliferations (identity, DI bags, config) with no owner and no census.

The #3122 addition is a narrow schedule-tool adapter port, not a second general MCP context. `AgentScheduleToolContext` (`src/agents/mcpAdapter.ts:47`) carries only the environment, owner-login accessor, schedule action executor, loop-origin accessor, and goals-only flag. Reusing the broader `McpToolContext` would inject unrelated command, database, session, and permission dependencies into the schedule capability. The context pin records it as canonical; the current app-created total is 211.

### Counting rule (so the number can be re-derived)
A definition is a named `type`/`interface` whose name contains `Context`, or a named config/port/file-backed object that functions as one (`Env`, `ResolvedEnvironment`, `EtapiConfig`, `OtelFileConfig`, `FeatureFlagPort`, `PriceCatalogue`, the 25 `*Modes` families). A usage is not a definition. A structural mirror counts as its own definition (it is a separate declaration that can drift). Inputs/results (`Resolve*Input`, `*Result` unions, `*DenyCode` unions) are counted only where listed in the services/security rows; elsewhere they are excluded. `environment.config.json` and wrangler vars+bindings count as one entry each in the 77. The 2 unitemized Tier A shapes: the execution slice reported 17 but itemized 15 by name; the 2 are companion shapes it did not list — flagged here, not assumed.

### 1.3 Route contexts (56 shapes + 1 alias)

## 2. RCA — why contexts proliferated (one RCA for the set)

**One paragraph.** Contexts proliferated because no one owned "context" as a platform concept: each slice defined the context it needed locally — routes cannot import the orchestrator, so they mirrored `ScreenerExecutionContext` instead of importing it; identity and configuration were never unified — a legacy per-instance login store grew alongside a validated per-operation context with no mapping between them, and the mode axis split into three vocabularies (`TEST`/`PROD`, `live`/`paper`, `sandbox`/`live`); configuration split across three homes (wrangler vars, `environment.config.json`, the `Env` type) with no single record of the cascade in ADD.md and no census or pin to stop new definitions; dependency-injection-by-context-bag became the default extraction idiom, so every extracted module and every route acquired its own `*Context` type carrying the same `env`/`audit`/`getOrm` seams; and the tenant layer was never decided, so tenant identity is carried ad hoc (plain `tenantId` fields, string parameters, stored selections, JSON strings in env) instead of in one place. The 64-var Free cap did not cause the proliferation — it exposed it: the same absence of ownership that let contexts multiply let vars multiply, until the deploy failed.

**Root causes (each traces to evidence in §1):**
1. **No owner, no census, no pin.** Nothing in the repo records how many contexts exist or forbids a new one. Every slice that needed a context defined one. (Evidence: 209 definitions; `docs/architecture/survey/compliance.md` R-CFG: the cascade pattern is "stated in code, not in ADD.md"; ADD.md contains no cascade at all.)
2. **The "routes do not import the orchestrator" idiom.** Stated in the mirror comments themselves (`copilotChannels.ts:129`, `stockCopilot.ts:122`). A real dependency rule, applied by copy-paste instead of by a shared type: 5 mirrors of one 2-field shape, plus 2 inline shadows, one drifted. The canonical type exists and is importable from `scheduleMaintenance.ts` — the routes mirror it anyway, and `orchestrator.ts:285` mirrors its own extracted type.
3. **Identity was built twice, never unified.** `ScreenerExecutionContext` (legacy, per-DO-instance login store, written on every authenticated request, fallback for legacy schedules) and `ExecutionContext` (#1078, validated, per-operation, PDP-checked, never a login) do the same conceptual job with disjoint fields and incompatible `environment` values, and no code converts one into the other. The mode axis then split a third way (`live`/`paper` in `RunBrokerContext`, `sandbox`/`live` in `ExecutionContext`, `TEST`/`PROD` in the screener context), and `ShardChainContext` carries both `environment` and `mode` because no single vocabulary won.
4. **Configuration split across three homes with no single record.** The same setting lives in wrangler vars, in `environment.config.json`, in the `Env` type, in per-domain resolvers, or in two of those — with drift in every direction: 199 `Env` fields never read; 25 `env.*` names read but undeclared; 14 wrangler vars undeclared in `Env`; the file's `payments` section written but unread; `stockScreener` empty; the monetization default contradicted three ways (code `false`, comment "ON", wrangler `1`); AI model in three places; Alpaca credentials in three name sets. Each resolver (environment, etapi, OTEL, flags) states its own precedence; the only full statement of the cascade lives in OTEL code, and the docs disagree with each other (OBSERVABILITY.md 6-level vs message-catalog 4-level vs SYSTEM_CONFIG_TIERS 5-tier, stale).
5. **DI-by-context-bag as the default extraction idiom.** When the orchestrator was split into modules, each module got a `*Context` interface carrying the same seams (`env`, `agentCtx`, `audit`, `getOrm`, `readSettingRaw`); when routes were extracted, each got its own `*RouteContext`. 83 bags (57 route + 26 ports) exist because the bag is how a module receives its dependencies — there is no shared "what a handler receives" type, and `RouteRequestDeps` is a Deps, not a Context.
6. **The tenant layer was never decided.** Tenant identity is a plain `tenantId: string` in seed contexts, a `currentTenantSource` in `PlatformIdentity`, stored selections in `TenantProviderContext`, JSON strings in env (`TENANT_SLACK_CHANNELS_JSON`, `TENANT_WEBHOOK_URLS_JSON`), and a default `"primary"` in comments. No layer in any cascade is "tenant" — OTEL has a `runtime` level that is per-tenant in practice, but that is OTEL-only.
7. **The cap was a lagging indicator, not a cause.** Vars grew one slice at a time (a flag here, a TTL there, a polling interval there) with no owner and no count pin, exactly like contexts. #6491's pin test is the first count guard on either.

**What the RCA is not claiming.** The proliferation is not carelessness by any one slice: the mirrors, the bags, and the per-domain resolvers each solved a real local problem (dependency direction, extraction, per-domain precedence). The failure is at the platform level — no one was responsible for the whole, so local solutions accumulated into 209 definitions.

## 3. Fix plan — one of everything

### 3.1 Headline recommendation: the config-file route, not the JSON var

**Recommend the config-file route as the end state: move the 52 text vars into `environment.config.json`, resolve one typed `UniversalEnvContext` once per request, and do NOT build the JSON-var hydration.** The JSON var is the minimal deploy unblock; the file route is the platform-wide fix, and building the JSON var first means doing the migration twice (hydration code written, then thrown away when the file route lands).

Reasons, each grounded in §1:
1. **It unblocks the deploy by itself.** File route: 0 text vars + 40 secrets = **40 < 64** (24 slots of headroom). JSON route: 1 + 40 = 41. Both fit; the file route fits with more room and no new serialization.
2. **Nothing is lost on changeability.** Wrangler vars need a redeploy to change, exactly like the config file (verified: vars are deployed with the Worker). The only things that genuinely need to stay in env are secrets, bindings, the deploy-injected `CF_DEPLOY_VERSION`, and anything an operator must change from the dashboard without a redeploy. The file route keeps all of those in env.
3. **The file already exists and is already the file layer.** `environment.config.json` is imported by `src/config/environment.ts` today; the cascade (env → process.env → file → builtin) already exists in code. The file route extends an existing mechanism; the JSON var invents a new one (a serialized blob + hydration + an expansion that must match the pre-consolidation values exactly).
4. **The migration is smaller than it looks.** Only **32 direct `env.<VAR>` reads in 16 files** touch the 52 text vars; 37 of the 52 have zero direct reads — they already go through resolvers/adapters (`FeatureFlagPort`, `readSettingRaw`, `getEtapiConfig`, OTEL modes) that read file/env themselves. The read-site work is re-pointing those resolvers at the resolved context, not rewriting 788 `env.*` reads (most of which are bindings and credentials, untouched by this change).
5. **The JSON var preserves the proliferation it is meant to fix.** It keeps every `env.*` reader, every resolver, and every drift (199 unread `Env` fields, 25 undeclared reads, 14 undeclared vars) in place, and adds a hydration step. The file route is the one that produces the single typed context the owner asked for.
6. **Reuse before new code.** The file route reuses: `environment.config.json` (exists), `resolveEnvironmentConfig` (exists, extended — not replaced), the OTEL 7-level cascade statement (exists, adopted as the one cascade), `ResolvedEnvironment` (exists, extended into the universal context), the `*Modes` resolver pattern (exists, converged onto the one cascade). The JSON var reuses nothing except the idea — and the one genuine precedent for packing (deploy sync collapsing five E*TRADE key aliases into one Worker secret) is a secrets-side precedent, not a config-side one.

**When the JSON var would still be right:** only if the owner wants the deploy unblocked before the platform-wide work can land, and accepts paying for the migration twice. If so, sequence it as an interim slice with a recorded sunset (the hydration code is deleted when the file route lands), not as the end state. This plan assumes the owner prefers one migration; the fork is listed under owner decisions (§3.5).

### 3.2 The target shape (one of everything)

- **One universal env context.** A single typed `UniversalEnvContext`, resolved once per request (or once per Worker isolate init for the platform-global parts), carried the way `ScreenerExecutionContext` is carried today (resolved once, accessed via an accessor) and the way `ExecutionContext` is carried at the API/MCP boundaries (resolved once per request, WeakMap-scoped, never shared across requests). It extends the `ResolvedEnvironment` shape (name/label/isLive/etrade/payments/serviceUserLogin/agentSchedule) with the etapi config, the OTEL/file config, and the feature-flag evaluation context — one object, one resolution, one recorded resolution source per setting (reuse the `OtelResolutionSource` vocabulary: `run | session | user | runtime | env | file | builtin`).
- **One execution context, composed — not merged.** `ExecutionContext` stays the identity context (who, which tenant, which mode, PDP-validated). The universal env context is the config context (what the settings are for that identity/mode/tenant). Composition point: `resolvePlatformContext` (#6151) already returns `{ context: ExecutionContext; broker; screenProvider; tier; runBroker }` — the universal env context joins that result, so one call yields identity + config together. The API boundary (#6172) and MCP boundary (#6173) are the two places the composition happens; the DO route shell is the third.
- **One cascade.** Adopt the OTEL 7-level statement as the single cascade for all config: **run > session > user > runtime > env > file > built-in safe default**, recorded in ADD.md (it is currently "stated in code, not in ADD.md"). The `environment.ts` 3-level comment is corrected to match. The `runtime` level is the tenant-override level (see §3.5 — home is an owner decision).
- **One mode vocabulary.** `TEST`/`PROD` (screener), `live`/`paper` (run broker), `sandbox`/`live` (validated context) become one vocabulary with one mapping, recorded in ADD.md. `ShardChainContext` stops carrying both `environment` and `mode`.
- **One route/handler shape.** Route contexts and ports contexts take the two contexts (`ExecutionContext` + `UniversalEnvContext`) plus narrow seams, instead of each defining its own bag. This is the largest phase and the last one (§3.3, Phase 5).
