## 8. Taxonomy — indicators vs patterns vs signals vs strategies

Definitions, corrected against the code where the code forces it:

- **Indicator** — a computation over price/volume with no trade decision by itself. Examples: **RSI** (momentum oscillator over closes; RSI14 in `marketDataResearch.ts:1700`, *not* in `technicals.ts` — it is imported and only gated/packaged by `computeTechnicals`, which requires ≥15 bars, else null), **MACD** (EMA12−EMA26; `marketDataResearch.ts:1722` — and its "signal line" is **not a real 9-period EMA, it is `macdLine × 0.82`**; `computeTechnicals` requires ≥27 bars), **VWAP** (there is **no generic VWAP** in `technicals.ts` — only anchored VWAP, Σ(close×vol)/Σvol from the 52-week-low anchor, `technicals.ts:236`, plus a session VWAP inside `computeVwapHold` using typical price; the `vwap` on `ETradeQuote` is a provider snapshot field), **ATR(14)** (Wilder, `technicals.ts:285`), **Bollinger** (period 20, σ 2.0). None of these enters, exits, or sizes anything on its own.
- **Pattern / setup** — a named, recognizable configuration of price/indicators with entry/exit/guardrail semantics. Examples: **`trend_breakout`** (setup catalog: price above rising 50-day SMA, volume above 20-day average, guardrail `volumeRatioMin: 1.2`), **`pullback_reversion`** (setup catalog, `maxRsi: 30`), **baseBreakout** (`baseBreakout.ts`: 20-bar coiling base + ladder order plan), **ORB breakout** (`evaluateOrbBreakout`, `technicals.ts:833` — a real composed gate: trigger + RVOL ≥1.5 + VWAP hold, but **no production caller wired — minute-bar capability exists at the adapter level, the gap is wiring, not capability** (corrected 2026-11-26, see §15)). The word "breakout" alone is three different things in this codebase: (a) sandbox id `"breakout"` in `patternSignals.ts` — **no breakout computation at all**, it shares the dip rule; (b) `trend_breakout` in the setup catalog — declarative setup, only executable mapping is the `bullish_breakout` momentum filter; (c) ORB breakout — real gate, unwired.
- **Signal / label** — a classification or trigger emitted by *evaluating* indicators/patterns against thresholds. Examples: screener `signal` (`OVERBOUGHT` when effective RSI > 70, `screener.ts:823-828`), `RangeZone "overbought"` (52-week range position — **explicitly NOT RSI**), the 7-string `macdSignal` (display/classification only; `screeningIndicators.ts:193-194` warns it must never be coerced into a vote). Three distinct labels, do not conflate: screener signal, `rsiFilter = "overbought"` (a filter demanding RSI > 70), and RangeZone overbought.
- **Strategy** — a named rule + position state + simulation, executable in sandbox/backtest. **Correction to the earlier framing:** `sma_crossover` in `patternSignals.ts:14-17, 135-144` holds only a per-bar enter/exit rule (fast SMA 5 vs slow SMA 20; enter long flat when fast>slow, exit when fast<slow). **There is no sizing, no stop, no risk rule in the file.** The executable strategy is the rule *plus* the simulation around it (long-only, one position, in the sandbox loop / copilot cycle).
- **Config / thresholds and scoring** — separate dimensions, not patterns: `opportunityHuntLevels.ts` (±0.5% entry band; SMA stop 5%/TP 10%; family stop/TP 3%), `screenerConfig.ts` (gap thresholds, `rangeOverbought: 0.9`, `rsiMinBars: 15, macdMinBars: 27`), `screenScore` 0–100 heuristic, 6-vote composite. **Three different "momentum" formulas** exist: factor-grades momentum, `rawMomentumSignal` in `factorGrades`, and screener `momentumScore` — they disagree and are counted separately.

**Is `technicals.ts` a set of patterns? No — confirmed.** `src/trading/technicals.ts` (991 lines) is pure `compute*` / `classify*` / `detect*` / `evaluate*` functions over caller-supplied bars ("Nothing here fetches", header :1-16). No named setup, no strategy id, no sizing, no feed, no schedule. Patterns are built **on top of** these primitives.

### 11c. Deduplication logic

Rules applied, in order:
1. **Same id, same rule → count once.** `sma_crossover` appears in S1, S2 (enum + code-gen + quant map), S3, S8/S9 defaults, S10 levels — 1 rule.
2. **Different ids, same rule → count once.** S1 `rsi_reversal`/`mean_reversion`/`breakout` = 1 shared dip rule; S2 `volatility_breakout`/`custom` fall through to the SMA default in both code-gen and quant mapping — 0 new rules.
3. **Projection ≠ new definition.** S0b is a pure filter+mapping of S0 (2 stock families); S9/S3 are thin wrappers over S1; S15 composes S11/S12/S14/S6. Count 0 new.
4. **Same name, different formula → count separately.** Three distinct "momentum" formulas: S11 `momentumScore=50+change%×5`; S12 `screenScore` (same base + intraday/52w/value terms); S14 `rawMomentumSignal=0.5+change%/10 ± range/intraday`. Likewise `dayAction` vs `sentiment` (S12) are one label set under two names — count once; `signal` (S11, 4 labels, RSI-gated) vs `rangeZone` (S12, 3 labels, 52w-position-gated) vs `dayAction` (5 labels, change%-gated) are three different label systems — count separately.
5. **Vocabulary reuse ≠ new pattern.** The 3 momentum filter values (`bullish_breakout`/`bearish_pullback`/`high_relative_volume`) appear in S11, S17, S16 and as S0b's mapping target — 1 vocabulary, counted once (in Patterns/setups). `bullish_breakout` as a momentum value is NOT the same thing as S1 `breakout` or S5 base-breakout or S0 `trend_breakout` — four different things sharing the word "breakout"; kept separate.
6. **Options references in stock files are not counted as stock.** S0 pairedStrategies (5 distinct options ids, incl. client-only `bull_call_spread` — verified in setupCatalog.ts: trend_breakout pairs [long_call, call_debit_spread, bull_call_spread]; pullback pairs [cash_secured_put, put_credit_spread, long_call]); S16 structures (9 options ids); S18/S19 (options). Excluded from stock totals, listed for the cross-reference audit.
7. **Config values count as threshold configs, not patterns.** S13, S10 levels, S7 risk policy, S23 thresholds are counted in the scoring/threshold dimension, not as patterns/strategies.

Cross-checks that must hold: 4 sandbox ids = 2 rules (S1 header says so verbatim); 6 backtest enum members = 1 code rule + 4 prose rule-texts (S2); 2 setup-catalog stock families = 2 read-model patterns (S0b); screener labels (S11) vs patternSignals (S1) overlap only by name (`breakout` word) — no shared implementation; `screenScore` ≠ `momentumScore` ≠ factor momentum (three formulas, rule 4).

### 12c. A third distinct surface

The Stock Hub "Schedule this screen" capture creates a *schedule* via `POST /api/schedules/create` (StockHub.tsx:683, `buildMarketScreenCaptureSubmission`), a different surface (`/api/schedules/*`, `ScheduleListItem` with callback/type/cron/interval/payload/paused) from the goals surface (`/api/schedule/goals`). Conflating the two would double-count. The new-screen capture creates a paused schedule that re-runs the screen's criteria; a scheduled *goal* invokes a named catalog operation. Both are "scheduled", neither is a "goal screen".

### 12d. Conflation check

**No conflation found in the code read:** `GoalScreenPanel` never references `ScheduledGoal`/`/api/schedule/goals`; `jobsApi.ts` goal functions never reference `goal-screen`/`goalKind`; `StockHub.tsx` never references `goal-screen` as a view (its 7 tabs contain no goal entry) and its schedule capture uses `/api/schedules/create`, not the goals API. The only near-miss is naming: the options-hub description in nav-config ("…goal screens, reports, schedules…") lists goal screens and schedules side by side, and `OpportunityHuntPanel` calls the hunt's seeded goal "the scheduled goal" while its on-demand run writes no ledger row — both are accurate if read literally, misleading if skimmed. The P1 consumer list's "Goal operations (#11)" refers to §12b (scheduled goals invoking operations), NOT to the goal-screen route (§12a). **Relation between the two:** NONE structurally. The only bridge is incidental: a scheduled goal COULD invoke an operation that runs a goal screen, but no built-in scheduled goal does so (the 9 built-ins contain no goal-screen operation), and the code paths are separate (`goalStockSpecFromPlan` vs `ScheduledAgent.onCron`). `goalStockScreenSpec.ts` explicitly states "It is NOT an execution reroute today: goal execution stays in goalDrivenScreen + goal dispatch".
