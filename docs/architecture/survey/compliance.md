# CBO commercial/platform HTTP routes — AOP + ADD.md compliance assessment

- **Basis:** code on `origin/main` at `cd094b6f28877dcb3f6e6b74e2b53ff0484fffc4` (2026-11-18 05:34 EST), read via `git archive` snapshot; clone `~/cfagent-2297-v5` not modified (fetch only). All `file:line` below are paths on that tip.
- **Method:** read-only source inspection. Route inventory discovered by grepping dispatch (`endsWith`/`startsWith`) in `src/agents/routes/` and `src/server/routes/`, plus the `COMMERCIAL_ROUTES` catalog. No runtime, log, or live-traffic verification — verdicts are about the code as written. "Not verified" is used where the code read cannot settle the question.
- **Scope:** `/platform/*`, `/payments/*`, `/commercial/*`, assurance, referral/offer/billing-policy/usage-billing routes. Excluded per brief: trading/order, brokerage market-data, research/job-pipeline, stock-copilot routes. `paidStockScreenSeam.ts` is not a route file (a shared seam called by screen routes) and is assessed briefly in §12. The Worker dispatcher (`src/server/routes/platform.ts`, `src/server/routes/core.ts`) is assessed in §11 because the session gate lives there.
- **Verdicts:** `compliant` / `partial` / `gap` / `not verified`. A `partial` means the mechanism exists in the group but is inconsistently applied or has a named hole; the gap line says exactly which.

## 0. Headline finding: ADD.md does not define AOP

`docs/architecture/ADD.md` is a container document only ("This file holds the section structure and links to the individual architecture docs. It duplicates nothing — it links.", `docs/architecture/ADD.md:3-5`). AOP appears exactly once, as one bullet in a standards list:

> "AOP (Exception Handling, Coded Messages, Logging, Externalized Configuration, Security, Transaction Management, etc)" — `docs/architecture/ADD.md:111`

There is no AOP definition, no per-aspect rule, and no conformance test named in ADD.md. The assessable rules therefore live in the ADRs and standards doc ADD.md links to, plus the aspect modules in `src/aspects/` and `src/outcomes/`. That indirection is itself gap G-12 below: a builder cannot assess AOP compliance from ADD.md alone. Every verdict below cites the concrete rule it was judged against.

## 1. Rules assessed against (quoted)

**R-EXC — Exception handling.** No single written rule exists. The operative precedents in code are: (a) `src/outcomes/outcomeAspects.ts:261` `BusinessError` (typed, coded error carrying an outcome code); (b) `src/aspects/loggingAspect.ts` header (error handling decoupled from domain logic via aspects); (c) the CodeQL rule stated in `src/agents/routes/paymentAssuranceLive.ts:104-106`: "exception details never reach the caller. The real error is logged server-side… responses carry a generic message only." Assessed as: typed/coded errors, a catch boundary per route, and no raw internal detail in responses.

**R-MSG — Coded messages.** `src/outcomes/outcomeCatalog.json` header: "the single outcome catalog for job runs — success AND failure… businessMessage goes to UI and channels; technicalDetail goes to logs only." Resolver: `codedMessage`/`resolveOutcome` in `src/outcomes/outcomeAspects.ts`; translation-point precedent `src/agents/routes/brokerCodedError.ts:1-22` ("The business message always comes from the single outcome catalog via `BusinessError` — there is no second resolver and no second catalog here. The raw upstream body… never appears in the response."). Assessed as: user/operator-facing messages carry a catalog code resolved through the single resolver, never hand-written literals or raw store/upstream text.

**R-LOG — Logging.** `docs/architecture/standards/standards.md:48` (§2.2): "Structured Logging: All execution logs must be formatted as JSON with mandatory contextual attributes (`trace_id`, `tenant_id`, `actor_id`, `agent_id`, `timestamp_iso8601`, `severity`, `component`)." Implementation: `src/observability/structuredLogger.ts:1-13` ("the ONE seam through which execution code emits structured logs", issue #3515 S2/S3). Assessed as: structured logger used per request (entry/outcome/failure), not `console.*`, not silence.

**R-CFG — Externalized configuration.** Stated in code, not in ADD.md: `src/config/commercialDefaults.ts:1-8` ("Every pagination default the commercial surfaces enforce lives in `config/commercial-defaults.json`; no module hardcodes a limit"); prices in the price catalogue (`src/data/priceCataloguePorts.ts`, `PROPOSED_SEED_PRICES` at :58, approval-gated via `getApprovedPrice`); policies as operator data (`src/data/billingPolicyPorts.ts:162`, `src/data/refundPorts.ts:208` PROPOSED seeds); mode switches resolved run > session > user > env > built-in (`src/config/agenticPaymentsModes.ts`, `src/config/paymentsFlowModes.ts`); flags via `FeatureFlagPort`, never raw env reads (stated at `src/agents/routes/paymentAssuranceLive.ts:33-36`). Assessed as: defaults/thresholds/prices/policies come from operator data, env, or ports — not handler literals.

**R-SEC — Security.** `docs/architecture/standards/standards.md:73-75` (§4.1): authorization "must not rely on simple flags… evaluated by a central PDP using structured tenant/membership context" and "Every privilege escalation, financial transaction, configuration update… must generate an immutable, tamper-evident audit trail log." Plus the standing session-scope correction (recorded in module headers, e.g. `src/agents/routes/platformAccounts.ts:33-41`): identity always derives from the verified session (`x-user-login` set by `server.ts`); "no endpoint reads a client-supplied tenantId for scoping, ever." Plus `standards.md:158` (MCP/tool "schema validation via Zod/JSON Schema") and §6.4 input/output guardrails. Assessed as: operator/session gates, no client-supplied tenant scoping, input validation, audit writes, webhook signature verification.

**R-TXN — Transaction management.** `docs/architecture/adr/data/0002-data-foundation-layer.md`, "Transaction model": "Per-store ORM transactions for operations inside one store: D1 single statements (atomic by themselves), D1 `batch()` for multi-statement atomicity on D1… Cross-store consistency via idempotent projection writes + reconciliation (R5)"; "`db.transaction()` on D1 is implemented as sequential BEGIN/COMMIT statements, not as a single batch… Slice 0 therefore never relies on `db.transaction()` for atomicity on D1." And R5 (`adr/0002:78-88`): "A projection failure never fails the execution transition — it is recorded and reconciled." ADR 0033 R-1/R-6/R-7 add: idempotent projection writes, "a failed projection is recorded, never dropped", DO-first ordering with reconcile backstop. The D1 batch mechanism exists: `D1BatchTransactionBackend` / `withTransaction` in `src/aspects/transactionAspect.ts:30-37,334-393` ("statements are prepared and BUFFERED… then applied by ONE batch() call… D1's batch contract is all-or-nothing"). Assessed as: single-store multi-writes atomic via `batch()` (or honestly single-statement + idempotent + reconciled); partial failure recorded/reconciled, never silent.

**R-ADD — ADD.md / port-first / layering / API-first.** ADR 0002 R1 (`docs/architecture/adr/data/0002-data-foundation-layer.md:27-37`): "Domain code depends only on interfaces in `src/data/*` port modules… No domain file imports a store client, references `env.AGENT_DB`, or writes SQL. The composition root (`src/data/createGovernancePorts.ts`) wires `env.AGENT_DB` → adapter → ports." R2 (:39-49): "All query-builder code lives in adapter modules." ADR 0032 (:65-66): "Drizzle ORM is the standard for data access… adapters use typed Drizzle behind the port"; "raw SQL behind ports" (ADR 0022 D-B, cited at ADR 0032:81-84). `standards.md:175` (§7.1): "Hexagonal / Ports and Adapters Architecture: Core business logic… completely decoupled from infrastructure concerns… via abstract interfaces (ports) and concrete implementations (adapters)." API-first: `docs/architecture/application/api-mcp.md:5` calls the system "API-first"; the concrete in-repo mechanism is the single-source path catalog `src/data/commercialUrlCatalog.ts:1-23` ("Every commercial route is defined ONCE here… Consumers derive paths from this module, never from a literal string… A hardcoded commercial path literal anywhere else in `src/` fails `tests/commercial_url_catalog_2846.test.ts`") and the OpenAPI drift note at `api-mcp.md:73` (spec "does not automatically inspect or validate against all runtime routes"). Assessed as: handlers depend only on `src/data/*` ports built by `create*` composition roots; routes → services → ports → adapters with no shortcuts; route + schema defined once and shared with the client.

## 3. G1 — Commercial + agentic payments (`src/agents/routes/agenticPayments.ts`)

The file is 8,969 lines holding ~70 endpoints. Verdicts below are for the file as a whole; sub-family divergences are called out.

1. **Exception handling — PARTIAL.** [Rule R-EXC.] Every branch is wrapped in `try/catch` (254 `try {`, 329 `catch` in the file). Many catches return the coded generic 500, e.g. `:495`, `:596`, `:1154` (`{ code: "FAILURE_UNEXPECTED_ERROR", error: codedMessage("FAILURE_UNEXPECTED_ERROR") }`, 500). But 36 sites return `error: message` where `message` is the caught error's text, e.g. the account-upsert catch at `:1374-1377`, credits catch at `:1401`, allowance catch at `:1469` — each classifying 400 vs 500 by regex over the message text (`/requires|Invalid|must be/.test(message)`). Raw store/validation text therefore reaches the client on those paths, and the 400/500 decision depends on message wording. No route in this file throws typed `BusinessError` outward; `BusinessError` is imported (`:228`) but the dominant pattern is catch-and-respond. **Gap:** replace message-text passthrough + regex classification with catalog-coded responses (reuse `codedOutcomeResponse` at `:446-453` / `usageBillingCoded` at `:460-467`); log the raw error server-side via the existing `structuredLog` (`:347-349`).
2. **Coded messages — PARTIAL.** [Rule R-MSG.] This is the most-coded group in scope: 368 `Response.json({ code: …` sites, 117 `codedMessage(` calls, dedicated helpers `codedOutcomeResponse` (`:446`) and `usageBillingCoded` (`:460`), and catalog codes for the commercial/billing/usage families exist (`FAILURE_COMMERCIAL_*`, `FAILURE_BILLING_*`, `FAILURE_USAGE_BILLING_*` in `outcomeCatalog.json`). But 172 `Response.json({ error: …` sites carry no code at all, concentrated in whole sub-families: bundles (`:2394-2527`, e.g. `{ error: "Forbidden: store operator required." }`), bundle/subscription checkout+purchase (`:2545-2862`), runs-pack checkout/confirm (`:3723-3812`, e.g. `{ error: "versionId is required." }`), referral-code admin (`:4235-4390`, `{ error: "Forbidden: operator only." }`). Even coded sites often pair a code with a hand-written `error:` string instead of the catalog message, e.g. `:1080` (`FAILURE_COMMERCIAL_FORBIDDEN` + "monetization flag is OFF; subscription purchase is disabled."), `:1129`, `:1293`. So the catalog is the mechanism for roughly two-thirds of responses and absent for the rest, with no per-family rule visible. **Gap:** extend the existing coded helpers to the bundles/checkout/runs-pack/referral families; resolve `error:` through `codedMessage(code)` instead of literals.
3. **Logging — PARTIAL.** [Rule R-LOG.] The module logger exists (`structuredLog`, `:343-349`, #3515 S3 seam) but is called at only 6 sites, all `structuredLog.error` for narrow failures: invalid mode config (`:414`), paid-submission record failure (`:1835`, `:1999`), redemption journal skip (`:1871`), referral auto-earn failure (`:2057`), product-row ensure failure (`:2289`). There is no per-request entry/outcome logging, no success logging, and no logging for the great majority of failures (the 250+ catches are silent except for `ctx.audit` calls on some paths). No `console.*` in the file (good). **Gap:** add entry/outcome/failure structured events on the existing logger; at minimum log every 500 catch (the 36 raw-passthrough catches currently emit nothing observable).
4. **Externalized configuration — COMPLIANT (with two noted exceptions).** [Rule R-CFG.] Prices resolve through the catalogue + approval state (never literals in the handler); the only price literals found are in comments and in the port seed `PROPOSED_SEED_PRICES` (`src/data/priceCataloguePorts.ts:58-63`). Billing/refund/offer rules come from operator policy stores (billing policy read at `:5244+`; offer cooldown from `rules.dismissCooldownDays`, `:6696`). Mode switches resolve run > session > user > env > built-in with fail-closed + audit on invalid values (`resolveAgenticRouteMode`, `:397-426`). Flags go through `FeatureFlagPort` (`requireMonetization` helpers, e.g. `:1080-1090`). Pagination uses `COMMERCIAL_DEFAULTS` (`:8330`). Exceptions: (a) the ledger-payments `limit` clamp hardcodes a 500 cap at `:8330` (`Math.min(500, …)`) alongside the externalized default — minor; (b) `ensure*Schema` calls (105 `ensure…Schema` mentions) mean DDL runs on the request path, which is a layering concern (see §3.7), not a config literal. No handler price/threshold constants were found.
5. **Security — PARTIAL.** [Rule R-SEC.] Strengths, all verified: the effective-operator gate is defined once per request (`envOperatorLogins` + preloaded store list, `:852-878`; `isStoreOperator` at `:875-878`; empty = deny all) and applied at ~50 money/admin sites; identity is the verified `x-user-login` (`commercialLogin`, `:840-843`); the submit route explicitly never reads a client-supplied `tenantId` (`:1705-1711`, resolved identity wins); account upsert keeps the target row's tenant for grant writes (`:1319-1332`); the billing webhook verifies the Stripe HMAC over the raw body before parsing (`:5141-5153`); the payments webhook in G6 is likewise HMAC-verified. Audit events (`ctx.audit("commercial.…")`) are emitted on money writes (upsert `:1350`, referral earn/attribute, billing webhook flag-off). Holes: (a) **the three ledger write-throughs have no authorization check at all in the handler** — `POST …/ledger/record` (`:508-609`), `record-cfpay` (`:610-681`), `record-native` (`:682-763`) never read `x-user-login` or `isStoreOperator` and trust body `userId`/`tenantId`/`priceUSD` (e.g. `:623-627`, `:697-711`). The Worker dispatcher requires a signed-in session for these prefixes (see §11), so the exposure is any-authenticated-user, not anonymous — but any signed-in caller can post ledger rows naming another user's id, and nothing compares body identity to session identity. **This is the most consequential gap in this assessment (G-1).** (b) Lifecycle preference read/write takes `tenantId` from query/body and uses it as the store key after checking only `userId` against the login (`:8688-8730`): a user can read/write their own preferences under an arbitrary tenant id; the tenant is never verified against the stored account. Operator-gated referral/lifecycle admin routes that take body `tenantId` (`:8457-8467`, `:8498-8508`) are acceptable as admin-target parameters, but the self-service lifecycle routes are not operator-gated. (c) **No schema validation anywhere in the file**: zero zod imports, zero `safeParse`; every body is `(await request.json().catch(() => ({})))` cast to a typed shape, then manual `typeof` checks (e.g. `:521-526`, `:623-627`). A malformed body degrades to `{}` and is then validated field-by-field — workable, but each of ~70 endpoints re-implements its own checks, and unknown/extra fields are silently ignored everywhere. (d) The operator-gate store-list failure degrades to env-only inside a bare `catch {}` (`:866-872`) with no log and no audit — a store outage silently narrows (or, for env-listed callers, preserves) access with no observable trace. (e) Audit is after-write and best-effort throughout; there is no audit-before-write on money paths (documented posture in sibling modules; no gate in this file blocks a write on audit failure). **Gaps:** gate the ledger record routes (reuse `isStoreOperator`/`commercialLogin` + body-vs-session identity match, or a service-identity check if they are internal-only — then enforce that at the dispatcher); verify lifecycle `tenantId` against the resolved identity; introduce one shared request-validation helper (reuse the `validateProfileInput` pattern from G3 or `validateStrictAuditWrite` from G11 — do not invent a second catalog); log/audit operator-list load failures.
6. **Transaction management — GAP (multi-write atomicity); PARTIAL (single-write + reconcile discipline).** [Rule R-TXN.] Zero uses of `withTransaction`, `transactionRunner`, or `batch(` in the file. Multi-write flows are sequential port calls with no atomicity: subscription purchase verifies payment, then `activateSubscription` (`src/services/subscriptionActivation.ts:187+`) performs `subs.createSubscription` + `store.upsertAccount` as two separate D1 statements — a crash between them leaves a subscription with no account row (or vice versa), with only the `findByPaymentRef` replay guard (`:187-191` in that file) as backstop. The submit flow records the paid submission, starts the workflow, then posts the journal entry, each in its own `try/catch` with loud-log + audit on failure (`:1835-1871`, `:1999-2057`) — i.e. the ADR 0002 R5 "record and reconcile" posture, honestly implemented, but not atomicity. Journal posts themselves are per-entry single INSERTs in a loop (`src/data/d1JournalAdapter.ts:124-160`), and that adapter's header admits: "A crash between the two statements of one post leaves a partial set, which `reconcileJournal` reports (never silently corrects)." The D1 batch mechanism that would make these atomic exists and is used by exactly one adapter in the repo (`src/data/d1ProviderConfigAdapter.ts:347`, `withTransaction(d1BatchTransactionBackend…)`). **Gap:** route the journal post and the activate-subscription write pair through the existing D1 batch leg (`src/aspects/transactionAspect.ts:354-393`); keep the loud-log + reconcile posture for genuinely cross-store steps (workflow start + D1 write), which no batch can cover (ADR 0002's stated non-goal, ADR 0033 "decided non-goal").
7. **ADD.md / port-first / layering / API-first — PARTIAL.** [Rule R-ADD.] Port-first is mostly honored: ~92 `create*Adapter` construction sites, all through `src/data/create*Ports` composition roots, and the commercial family is the best-covered. But there are three shortcut classes: (a) **direct ORM use in the handler** — `orm.transactions.findMany()/create()` for the ledger write-throughs and revenue reads (`:532-549`, `:633-654`, `:790-795`) and `orm.transactions.create` in the bundle-purchase flow (`:2807`, plus `:5092`, `:5383`), plus `orm.getSql()` passed into `ensureUsageEventsTable` (`:1251-1256`). The DO `mas_transactions` table is written from the route layer, bypassing the port layer (the native-ledger port exists for the D1 side — `record-native` uses it at `:725`). (b) **Reach-through to adapter internals** — `ensureStoreOperatorsSchema(storeAdapter.db)` (`:893`), `ensureSubscriptionSchema(subs.db)`, `ensureBillingPolicySchema(policy.db)` (`:5184-5185`), and 105 `ensure*Schema` mentions: the handler reaches through the port to `.db` and runs DDL on the request path. (c) **No service layer for most families** — pricing, referral, offer, refund, and product-version logic lives inline in the 8,969-line handler; the exceptions that prove the pattern exists are `activateSubscription` (`src/services/subscriptionActivation.ts`), `recordFirstPaidRunEarning`, `resolvePlatformIdentity`, and the payment-workflow submission helpers. Layering verdict: routes → ports directly (acceptable per ADR 0002 for thin handlers) but routes → ORM/SQL-adjacent calls directly is not. API-first is **compliant for paths, gap for schemas**: paths are defined once in `commercialUrlCatalog.ts` and matched via `COMMERCIAL_ROUTE_SUFFIXES`, with clients deriving from `COMMERCIAL_API_BASE`/`commercialPath` (e.g. `src/client/commercialApi.ts:20-21`, `usageBillingApi.ts:18-24`) and a test pinning no stray literals — but request/response shapes are defined nowhere shared: no zod schema, no shared TS type between handler casts and client parsers, and `src/security/openapiSpec.ts` contains zero commercial/platform paths (the drift gap `api-mcp.md:73` warns about). **Gaps:** move the `orm.transactions` writes behind the existing ledger ports; stop reaching through `.db` for `ensureSchema` (schema ensure belongs in the adapter factory or migration path); extract per-family services reusing the existing service modules; define shared request/response schemas once (extend the catalog pattern — paths already have it, schemas do not).

## 4. G2 — Platform tenants (`src/agents/routes/platformTenants.ts`)

1. **Exception handling — GAP.** [Rule R-EXC.] One outer `try/catch` (`:260-393`); the catch at `:390-391` returns `err.message` verbatim with 500 (`jsonError(err instanceof Error ? err.message : "Tenant administration failed.", 500)`). Store/adapter internals can reach the client. The operator-list load failure is swallowed in a bare `catch {}` (`:152-160`) with no log. No typed errors. **Gap:** coded generic 500 + server-side log (reuse the G9 `logError` pattern, `paymentAssuranceLive.ts:104-112`).
2. **Coded messages — GAP.** [Rule R-MSG.] All responses use the local `jsonError(error, status)` helper (`:103-105`) returning `{ error: <raw string> }` with no code — e.g. `:147`, `:163`, `:257`, `:280`. Zero catalog codes, zero `codedMessage`/`BusinessError` in the file. **Gap:** reuse the outcome catalog + `codedOutcomeResponse` pattern from G1 (`agenticPayments.ts:446`).
3. **Logging — GAP.** [Rule R-LOG.] Zero logger calls, zero `console.*`, zero `structuredLog` in the file. No entry, outcome, or failure logging; failures are observable only via the audit funnel (best-effort, after-write) and the client-visible error string. **Gap:** add the #3515 module logger (reuse the 3-line seam from G1 `:343-349`) with entry/outcome/error events.
4. **Externalized configuration — COMPLIANT.** [Rule R-CFG.] The header states the rule and the code follows it (`:42-48`): create writes a settings row "with store defaults… the adapters' absent-row defaults, never code constants in this module." Defaults live in the port module (`DEFAULT_TENANT_AUTO_REFRESH`, `DEFAULT_TENANT_PROVIDERS` in `src/data/commercialPorts.ts:160-175`) and are applied by adapters. The only literal is the `TENANT_CREATION_MODE = "settings_row_only"` design constant (`:113`) and the 512-char id shape bound (`:116-123`, a validation bound, shared with `tenantQueueMapping`). Operator list from env + store (`:129-138`). No prices/thresholds in the handler.
5. **Security — PARTIAL (strong gate, weak validation/audit).** [Rule R-SEC.] Gate is correct and consistent: verified `x-user-login` required (401), effective operators = env UNION store list, empty = deny all (`resolveOperator`, `:141-166`); tenant id in path/body is an administration target, never scope (`:19-27`); reserved `login:` prefix refused (`:282-284`); unknown tenant is 404 (`:318-319`). Validation is manual but careful: `isTenantIdShaped` (`:116-123`), per-field type checks for the settings PATCH (`:343-377`), unknown-field rejection by omission (only known fields are read). No zod/schema (same repo-wide gap as G1). But earnings/commission arithmetic lives in `src/config/adsRevenueModes.ts` helpers (`externalAdClickEarnings`, `externalAdImpressionEarnings`, `:44-46`) — **not verified** whether rates are operator data or code constants (the config module was not read for this assessment). **Verdict `partial`, with the earnings-rate question `not verified` (reason: config module not read).**

### G11 — Audit (`audit.ts`)

1. **Exception handling — GAP.** [Rule R-EXC.] Every branch catches and returns `err.message` verbatim with 500 (`:184`, `:205`, `:247`, `:275`, `:320`). The read-time resolver correctly never fails a read (`resolveAuditAspects` catch → null, `:133-137`), but the route catches leak. **Gap:** generic 500s + log.
2. **Coded messages — PARTIAL.** [Rule R-MSG.] Unique in scope: the read path resolves stored payloads through the single outcome catalog at read time (`resolveAuditAspects`, `:115-140`, via `resolveOutcome`/`codedMessage`, "never a second resolver", `:101-106`) and returns `resolvedAspects` with the `[CODE] message` variant. But route-level errors (500s, 400 validation) are uncoded raw strings. **Gap:** code the route errors; the read-time resolution is already the pattern to reuse elsewhere.
3. **Logging — GAP.** [Rule R-LOG.] Zero logger calls. (The module *is* the audit trail, so the absence of structured logging is partly mitigated — but a failed audit read/write leaves no structured record, only the HTTP response.) **Gap:** log failures on the #3515 seam.
4. **Externalized configuration — PARTIAL.** [Rule R-CFG.] The audit-write mode switch is properly scoped (run > session > user > env > legacy, `:255-267`) with strict validation in every mode for `/audit/event`. But the list endpoint hardcodes its pagination bounds (`limit` default 50, clamp 1..100, `:228-229`; 1000 for filtered queries, `:236`) — the same values `COMMERCIAL_DEFAULTS` externalized for receipts/transactions, duplicated here as literals. **Gap (minor):** reuse `COMMERCIAL_DEFAULTS` (or extend it with audit bounds) instead of literals.
5. **Security — PARTIAL.** [Rule R-SEC.] Good: session-scoped reads (detail + list filter by `sessionId`, unknown/other-session id → same 404, `:195-205`, `:243-245`); `/audit/event` always strict-validated via the shared `validateStrictAuditWrite` (`:315-319`); write-mode switch can never loosen `/audit/event` (`:308-314`). Hole: `POST /audit` in legacy mode (the default) is **unvalidated by design** — `type`/`agent`/`payload` taken straight from the body (`:270-274`), with strict validation only when the mode switch selects it. Any signed-in session can write arbitrary audit rows (type/agent spoofing) through the legacy spelling. Whether legacy mode is still the live default was **not verified** (env/switch state is runtime, not code). **Gap:** record the live default; if legacy is live, the fix direction is to make strict the default (reuse `validateStrictAuditWrite` — already wired in-file) — owner decision, since the legacy contract is pinned by tests.
6. **Transaction management — COMPLIANT.** [Rule R-TXN.] Each write is one `mas_events` row via the single-owner `recordAudit()` (`:55-61`); no multi-write boundary in the handler. Chain verification reads a single settings row. No gap at the route layer (chain-append atomicity lives below and was not assessed).
7. **ADD.md — GAP.** [Rule R-ADD.] Direct `DatabaseORM` + `SqlStorage` use (`:28`, `:199`, `:232`), `runRestTool` delegation, and `settingReadFromSql` — no `src/data/*` port in the file. Same pre-port-first class as G6/G10. **Gap:** behind the audit ports that exist elsewhere (`src/data/auditLogPorts.ts`, `createAuditPorts.ts`) — reuse, don't build.

## 11. G12 — Dispatcher (`src/server/routes/platform.ts`, `src/server/routes/core.ts`, `src/server.ts`)

Assessed only for the aspects the dispatcher owns (security gate, API-first routing); other aspects are not applicable.

- **Security — COMPLIANT (authentication + identity minting).** [Rule R-SEC.] The generic `/api/*` fallthrough in `core.ts` requires authentication and mints identity server-side: caller `x-user-login` is deleted and re-set from the verified session (`core.ts:210-212`, `return new Response("Unauthorized", 401)` without a login at `core.ts:204` approx. — verified in the `sed` read at relative lines 10/16-18). The commercial prefixes get explicit branches in `platform.ts`: `/api/payments/agentic/*` + `/payments/agentic/commercial/*` require auth and forward with the session login (`platform.ts:472-479`); `/api/premium/*` forwards with the session login when signed in and *deletes* the header when anonymous (`:502-512`, preserving the verified-payer model); the payments webhook branch is separate (`:527`). No handler in scope needs to distrust `x-user-login` — the dispatcher is the single minting point, and every handler's trust in it is justified by this code. **Residual (not a dispatcher gap):** the dispatcher authenticates but does not authorize — operator checks live in handlers, which is why the G1 ledger routes' missing handler check matters (G-1). The dispatcher cannot compensate for it without a route→role table, which does not exist (see API-first below).
- **API-first — GAP.** [Rule R-ADD.] Routing is a sequential chain of `startsWith`/`endsWith` branches across `server.ts` → `platform.ts` → `core.ts` → `routeRequest.ts` → per-file `endsWith` chains, with path literals duplicated at each level (mitigated only for the commercial family by `commercialUrlCatalog.ts`, which the dispatcher does use: `COMMERCIAL_BARE_PREFIX`/`PAYMENTS_API_PREFIX`, `platform.ts:39,442,472`). There is no route table, no route→method→schema registry, and no generated OpenAPI coverage for the CBO families. **Gap:** a single route registry (paths + methods + auth requirement) that dispatcher, handlers, and OpenAPI generation all derive from — this is the one genuinely new mechanism in the gap list, and it is also the fix that would make G-1 structurally impossible (an authorization requirement declared per route, enforced at dispatch).
