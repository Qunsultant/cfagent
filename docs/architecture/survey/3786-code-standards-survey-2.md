# Standards survey 2 — supplementary harvest (API, MCP, coding, naming, design, structure, file organization, AOP, agentic-SaaS completeness) + the touch-conformance mechanism

- **Base:** `origin/main` = `9925ead846c163e4fd2f91a8e035230e6f2481cb` (Qunsultant/cfagent).
- **Method:** read-only survey of a detached worktree at that SHA (removed after use). Every rule was read in its source document, config, script, or pin at that base; counts quoted as "today" are fresh greps/measurements over `src/` at that base. No GitHub writes; nothing in the repo was modified.
- **Purpose:** supplement to `SURVEY.md` (63 rules, areas A–H). The user expanded the scope: API standards, MCP standards, general coding standards, naming standards, SOLID/GRASP/GoF/15-factor, directory-structure standards, one-class-per-file and file-size standards, AOP implementation standards — plus the **touch-conformance directive** (Area 8): no grandfathering; code brought into conformance in the same PR that touches it. Area 10 is the agentic-SaaS completeness check: standard families an agentic SaaS must have, verified against what cfagent actually has.
- **Status legend:** **ENFORCED** = a named pin / CI check / script fails when the rule is broken. **DOCUMENTED-ONLY** = stated in a repo document, no machine enforcement. **PRACTISED-UNDOCUMENTED** = the practice exists and is relied on, but no repo document states it. **GAP** = an implied standard with no home at all today. **PROPOSED** = a standard (or a sharper definition of a harvested one) the platform has not adopted — a user decision at the discussion gate, *not* a harvested rule; sharper definitions are marked **PROPOSED-DEFINITION**. Rows marked **xref** point at a SURVEY.md rule and are excluded from this survey's counts.
- **The two-part deliverable (user correction, 2026-11-08):** the programme is (1) DEFINE the standards, (2) MEASURE CONFORMANCE against those definitions on the current tree. Accordingly, every area below states each standard as a measurable definition (in the rule text, or in a definitions supplement where the harvested form was ambiguous) and gives a conformance measurement with its method — conforming/violating counts, worst offenders by name — or, where a pin already maintains the measurement, the pin's baseline cited as the measurement. Where measurement is not mechanical (Area 5), the survey says so plainly and proposes the proxy instead of a count. **This definition+measurement pair, per area, is the approval unit for the user's discussion gate, before any doc ships.** The same requirement applies by reference to SURVEY.md's areas A–H: their rules are already stated precisely enough to measure in most cases (the pins are the definitions' teeth), and each A–H standard's measurement is its pin baseline or census figure as recorded there; any A–H rule whose definition proves ambiguous at doc-writing time comes back as a PROPOSED-DEFINITION in the draft, not as silent editorial licence.

## Area 8 — The touch-conformance mechanism (user directive, 2026-11-08)

**The directive:** no grandfathering. Untouched code keeps its census baseline; the moment a change touches code, the touched scope must conform to the standard *in the same PR*. This area surveys what already implements pieces of that idea, then specifies the mechanism as a proposal.

### What already exists (measured at base)

1. **Pin rule 1 — same-PR pin updates** (gitops §7, "The pin rule" item 1): a change that alters a pinned surface MUST update the corresponding pin in the same PR; "a pin updated later, in a cleanup PR, means the surface changed unpinned — that gap is where drift accumulates." This is touch-conformance for *pinned surfaces*, stated as policy.
2. **Policy Gate diff-scoped checks** (`scripts/ci/policy_gate.py`, `evaluate_policy(base, head)` computes `touched_files` from `git diff base...head` and scopes its checks to the PR): the docs-scope guard, the stale-base reversion guard, the test-deletion guard, and deprecation checks (i)/(j) (SURVEY.md H1/H2) all evaluate **only what the PR touches** — the diff-scoped enforcement home already exists and is a required check.
3. **The console ratchet's per-file lock** (`tests/console_migration_ratchet_3515.test.ts`, xref C4): ceilings are per file, and a file that reaches zero `console.*` is *locked at zero* — a per-file, stateful ratchet: improvement is permanent, regression in that file is impossible. This is the closest existing analogue to "touched scope conforms, and stays conformed."
4. **Shrink-only censuses generally** (#3525 neutrality, #1976 data census): baselines name existing violations; new violations fail. They are tree-scoped, not touch-scoped — a PR that touches a baselined file for an unrelated reason is *not* today required to clear that file's baseline rows.
5. **`scripts/verify-before-merge.sh`** (§17.4/§18.1): diff-adjacent discipline — refuses a stale base, runs typecheck + migration-pin lint + full suite on the exact head. Not a conformance mechanism, but the pre-merge battery a touch check would join.

### Proposal: how touch-conformance is mechanized (for the user's ruling)

- **Unit of touch = the whole touched file** (any file in the PR diff), plus **any pin surface the change moves** (a route added in file A that changes the inventory pinned in test B touches B's surface too). Directory-level touch is explicitly *not* proposed — it would make every drive-by fix a decomposition project.
- **Diff-scoped census evaluation:** each census pin gains a touch mode — for every file in the PR diff, that file's baseline entries are *void*: the file must pass the standard outright (zero counted violations of that family), while untouched files keep their baselines. Implementation shape: the pin test reads an env/CI-provided changed-file list (the Policy Gate already computes `touched_files` from the same diff — the census pins can consume the same list), so no new infrastructure category is needed.
- **Order of application per family:** (a) families whose measurement is per-file mechanical go first — console (already locked-at-zero; extend to void-on-touch), neutrality rows, naked-SQL rows, `any` counts (once L4 is baselined), class-per-file and size budgets (once P1/P4 are baselined); (b) shape families next (resolver census under #3786); (c) non-mechanical families (design principles, N-area) discharge touch-conformance through the PR body's conformance line + the per-slice review artefact, not a test.
- **PR-body line:** the §9 body gains a `Touch conformance:` line naming the standards whose touched scope was brought into conformance, or "no baselined file touched." Policy Gate can check the line's *presence* (the H5 pattern: presence is checkable, quality is review).
- **Characterization-first guard:** refactoring a baselined file to conform must not change its behaviour — where the file's behaviour is under-pinned, characterization pins land *before* the conformance edit in the same PR (the established Red-first discipline), and the PR body says so.

### Tensions, named honestly

1. **Scope explosion vs one-issue-one-PR.** Touching `scheduledTasks.ts` (5,212 lines) for a one-line fix cannot mean "decompose it now." Mitigation built into the proposal: touch-conformance applies to *counted violations of the standard in that file* (clear the file's census rows for the families in force), not to every conceivable improvement; decomposition-size standards (P4) conform by *budget assignment*, not by splitting on touch.
2. **Behaviour risk in refactor-on-touch.** Clearing a file's rows (e.g. removing its `any`s, folding its duplicate resolver) can change behaviour in exactly the files that are oldest and least pinned. The characterization-first guard above is the mitigation; where characterization is impractical, the honest outcome is a *named exception in the PR* (touch deferred, follow-up issue filed in the same PR per scope discipline) — an exception mechanism that is visible, or the rule will be silently routed around.
3. **Baseline gaming.** A lane could avoid touching baselined files, stranding them forever. That's acceptable: baselines shrink by slice work (the existing programmes) *and* by touch; touch is an accelerant, not the only engine.
4. **Merge-queue friction.** A void-on-touch failure discovered late (in the queue) restarts the cycle like any red check; the local battery (`verify-before-merge.sh`) should run the touch evaluation so failures surface before the PR, not in the queue.

2. **Two catalogs vs "the single catalog."** C1 says one outcome catalog; the tx/data-foundation family still emits from `src/aspects/errorCodes.ts` (Q2/Q3). Both are single *within their family*, but the doc set must state the split or the AOP file and the errors file contradict each other on their face.
3. **`src/ports/` vs `src/data/`.** A directory named `ports` holding one file, while 371 files of ports+adapters live in `data/`, is an active trap for new placements (O3). The structure file must rule: `src/data/` is the home; `src/ports/` is dispositioned (emptied by migration or explicitly scoped to what it holds).
4. **One-class-per-file vs the MCP registry pattern.** The worst P1 offenders are the MCP command files, whose multi-class shape *is* the K3 standard (one command class per tool, grouped per domain). The two standards must be written together: P1 with a registry exemption, or K3 restructured — ruling needed, not discoverable.
5. **Two "15-factor" authorities.** Factor numbering follows `docs/agentic-org/architecture.md` §6 (factor 15 = auth), not the classic 12-factor+3 ordering a reader may assume; both 3186 docs warn about this. `12-design-principles.md` must pin the numbering source or every future audit risks talking past the last one.
6. **Retention numbers disagree by programme.** 365-day rulings (audit, discovery runs), a 90-day default in the retention register's own header examples, per-table decisions in `storageRetention.ts` — R4/R9 cannot be stated as one standard until someone rules the platform default. Flagged for the discussion gate.
7. **Stale counts in the new areas' sources too.** `api-mcp.md` claims 17 MCP tools / 11 resources / 4 prompts; the live inventory says 118 / 14 / 5. `mcp-security.md` says "30 tools" for the catalog. Any figure copied from the assessment-era docs into the new set would be wrong on arrival (SURVEY.md Conflicts #8, recurring).
