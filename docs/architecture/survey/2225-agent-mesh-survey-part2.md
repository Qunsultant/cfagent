# MESH SURVEY — FULL TEXT (part 2 of 2)

## §3 Workflow durability audit

All three workflows extend `ThinkWorkflow` (bindings `wrangler.jsonc:15-19`). All three are thin adapters delegating to a flow core written against a fakeable step interface — which is why their logic is unit-testable, and also why **no test at this base exercises the real runtime's eviction/resume behaviour for any of them** (all workflow tests drive fake steps/ports: `tests/trading_trade_workflow.test.ts`, `tests/payment_workflow_flow.test.ts`, `tests/screener_workflows.test.ts`). Resumability below rests on the step structure + **[platform docs: Cloudflare Workflows memoize completed steps and resume after eviction]**; the repo-side proof G6 requires does not exist yet.

### 3.1 TradingTradeWorkflow — `src/agents/trading-trade-workflow.ts:86`

- **Shape**: `ThinkWorkflow<any, TradeApprovalParams>` (agent type `any` per ADR 0004 W13, `:86-98`). Steps: `step.waitForEvent("await-approval", { type: "approval", timeout: "24 hours" })` → one `step.do("settle-trade", …)` (`:52-77`). No decision within 24 h → outcome `expired`, settles nothing (`:59-61`).
- **Who starts it**: only `TradingAgent.startTradeApproval` via the Agent base's `this.runWorkflow(TRADE_WORKFLOW_BINDING, params)` (`trading-agent.ts:1187`); decisions arrive via `decideTradeApproval` → `this.sendWorkflowEvent` (`:1218`). **Neither method has a production caller** (§1) — tests only.
- **Retry/idempotency**: the settle step is the only side-effecting step. A step retry re-runs `settleTradingOrder` — the same core the synchronous approval door uses — which claim-then-executes against the draft's current state and refuses when the draft no longer matches (`trading-agent.ts:780-799`). A retried settle of an already-settled draft therefore refuses rather than double-placing. Identity is fail-closed: a payload without `userLogin` throws before any step (`trading-trade-workflow.ts:106-108`).
- **Status query**: none. No route or service queries trade-workflow instances; the class writes no D1 projection (its only external call is the settle core). A run's state is knowable only to whoever holds the workflow id and binding access.
- **Eviction**: wait + one memoized step — the simplest resumable shape in the fleet; a run waiting 24 h for approval is precisely the eviction-crossing case, and it is held by the workflow, not the agent (2.3e).

### 3.2 ScreenerScreenWorkflow — `src/workflows/screenerWorkflow.ts:254`

- **Shape**: `ThinkWorkflow<any, WorkflowJobCommand>`; parent/child fan-out — a parent run creates shard child runs of the same workflow (`workflowChildOps`, `:141-167`), polls them with `step.sleep` + `step.do("poll-<n>")` (`screenerWorkflowFlow.ts:902-903`), then `project-final` (`:786`). Shard steps: `screen` (retries `{ limit: WORKFLOW_STEP_MAX_RETRIES }` = 3, `src/workflows/workflowPorts.ts:137`; adapter supplies a 1 s retry delay, `screenerWorkflow.ts:225-246`), `store-shard` (`flow:603`), `deliver-shard` (`:615`), `project-shard` (`:633`). Params/outputs are claim-check sized (summaries/flags only; full results travel store→door, header `:10-14`).
- **Who starts it**: `CfWorkflowAdapter` / `createWorkflowPorts` — an **idempotent start**: the instance id is derived from the jobId (SHA-256 fallback id at `cfWorkflowAdapter.ts:70-71`), create-or-adopt on collision (`:83-128`), so a retried start converges on one run. Production starters: synchronous screen routes via the opt-in async flag (`screenerWorkflowRoutes.ts:46-60` — on any start failure the route falls back to the synchronous path, `:8-15`), goal-screen submissions (`src/services/goalScreenWorkflowSubmission.ts:132`), scheduled tasks (`src/services/scheduledTasks.ts:1364-1501`), and PaymentWorkflow's `startScreener` dep (`paymentWorkflow.ts:209-221`).
- **Retry/idempotency**: goal-screen shards carry `idempotencyKey` = the caller run id, deduped in ScreenerAgent's task ledger (`screener-agent.ts:1112`, `:1038`); a deduplicated run with no result **fails loud** rather than recording an empty success (`screenerWorkflow.ts:134-140`). The deliver step uses a deterministic delivery id (`` `workflow:${command.jobId}` ``, `:207-215`) so a retried delivery converges in the outcome sink instead of forking a second record. The store step (`recordWorkflowScreenReport` / `recordWorkflowGoalScreenReport` on the shared orchestrator instance, `:186-200`) has no explicit dedupe evidence in the flow — re-storing the same run's result overwrites the same canonical report by construction of the report store, but no pin proves it (G6 material).
- **Status query**: the fleet's best surface — instance `status()` (`:158-167`), D1 projection rows via the shard store (`createShardJobAdapter` over `AGENT_DB`, `src/data/createShardJobPorts.ts:23-27`), a read route (`src/agents/routes/workflowRuns.ts:2-3`, list at `:138`), a client panel (`src/client/WorkflowRunsPanel.tsx`), and pins (`tests/workflow_runs*.test.*`, `tests/screener_workflow_routes.test.ts`).
- **Eviction**: parent runs poll children across sleeps — long-lived by design; step memoization is the resume mechanism [platform docs]. No repo eviction test (§3 preamble).

### 3.3 PaymentWorkflow — `src/workflows/paymentWorkflow.ts:126`

- **Shape**: `ThinkWorkflow<any, PaymentWorkflowEventParams>` delegating to `runPaymentWorkflowFlow` (`src/workflows/paymentWorkflowFlow.ts`). Steps in order: `gate-check` (`flow:207`, the CfPay monetization gate — read-only), `record-coverage-required` (`:223`) / `record-checkout` (`:238`), `waitForEvent("await-payment-approval")` → `record-approval` (`:254-260`), `waitForEvent("await-payment-verified")` (`:281`, `PAYMENT_VERIFICATION_TIMEOUT = "24 hours"`, `:191`), `confirm-paid` (`:292`), `record-payment` (`:306`, `:331`), `consume-coverage` (`:345`), `start-screener` (`:370`), `issue-failure-credit` on screener failure (`:379`).
- **Who starts it**: `startPaymentWorkflowViaBinding` / `ViaHost` (`src/services/paymentWorkflowSubmission.ts:117`, `:131`; approval/verified events delivered via `:143`, `:158`) from orchestrator-mounted routes — `routes/agenticPayments.ts:754`, `:1189`; `routes/paymentAssuranceLive.ts:124`, `:214`; `routes/screenerResearch.ts:1523` — and from `ScheduledTasksService` via `paidScreenSubmission.ts:59`. All behind the **monetization feature flag, default OFF, fail-closed** (`paymentWorkflow.ts:28-57`) — so in the deployed default, these starts do not happen and the free path runs. The class header's "No route calls this workflow yet by default" (`:32`) is stale about the wiring, right about the flag (§6.3).
- **Retry/idempotency** (the fleet's most careful money path): a confirmed payment writes ONE `mas_transactions` charge row **deduped per run** — a retried step logs "already exists (retried step, deduped)" and proceeds (`paymentWorkflow.ts:236-262`); the write fails loud (a payment is never recorded into the void). The D1 journal projection is replay-safe (posting is a no-op for an already-posted `transactionRef`, `:269-272`; the credit uses a distinct `<runId>:credit` ref so charge and credit can't swallow each other). Failure credits are likewise deduped per run and fail loud (`:296-345`). `start-screener` goes through the idempotent-by-jobId workflow port and **fails loud rather than falling back to a direct screen after payment** (`:209-221`).
- **Identity**: payload must carry verified `userId`/`email`/`tenantId` and the tenant must match the account's — fail-closed throws (`:136-146`). Prices come from the operator catalogue port, never a code constant; an unbound catalogue fails the gate closed (`:148-160`, #2185).
- **Budget check**: the workflow's gate is the **monetization gate** (checkout/coverage), NOT PaymentsAgent — `grep -c PAYMENTS_AGENT src/workflows/paymentWorkflow.ts src/workflows/paymentWorkflowFlow.ts` = 0/0. G5's "PaymentsAgent budget check consulted before spend" is new wiring.
- **Status query**: via the shared workflow-runs read surface (§3.2) plus the payment-assurance surface (`routes/paymentAssuranceLive.ts`; `FEATURE_PAYMENT_ASSURANCE`).

## §4 Scheduling ownership

Two systems, disjoint state, one overlap zone:

**System A — OrchestratorAgent self-scheduling (SDK scheduler).** Per-login instances schedule callbacks on **themselves** via the Agents SDK (`this.schedule`/`this.scheduleEvery` — ports at `orchestrator.ts:419-466`, `:2400-2560`). It owns: NLQ-created ad-hoc schedules (via the NLQ scheduling port, `nlqPorts.ts:47-52`), the hourly strategy scan and stale-ledger sweep maintenance (armed in `onStart`, `orchestrator.ts:824`, `:667-700`), async-job follow-ups, and everything `ScheduledTasksService` (4,098 lines, `src/services/scheduledTasks.ts`) manages for that user — scheduled options analyses and screener follow-ups over `mas_async_jobs`, constructed per instance at `orchestrator.ts:909`. User-facing schedule routes (`/api/schedules`, `server.ts:3040-3052`; `src/agents/routes/schedules.ts`) operate on THIS system (session login only — a caller-supplied identity fallback was removed, #154). State: the instance's own SQLite/storage. Firing: the SDK's alarm machinery inside the DO.

**System B — ScheduledAgent goals (worker cron).** A singleton instance (`"default"`) holds the goal catalogue (`"goals"` key, seeded `DEFAULT_SCHEDULES`, `scheduled-agent.ts:216-218`). The **worker's** cron (`*/30 * * * *`, `wrangler.jsonc`) calls `server.ts` `scheduled()`, which invokes `onCron()` on the singleton (`server.ts:3756-3763`), which budget-gates each due goal through PaymentsAgent (`scheduled-agent.ts:307-318`) and fires it via `createJob` chains onto the orchestrator (`:645-646`), social executors, or resource goals. User-facing goal management (`/api/schedule/operations`, goals GET/POST) is worker routes → this singleton (`server.ts:1010-1045`, `:1534`). State: one instance's `ctx.storage`. Firing: the worker cron, not any DO alarm.

**Overlaps and anomalies the ruling must dispose of**:
1. Both systems can originate screener runs (A via ScheduledTasksService, B via goal chains → orchestrator jobs → goal-screen workflow submissions, `scheduledTasks.ts:1364-1501`).
2. The daily research run is conceptually a "scheduled goal" but rides System A's side of the tick: `scheduled()` forwards `/research/scheduled-tick` to the **orchestrator** (`server.ts:3779-3790`), with its once-per-weekday guard in the orchestrator's `mas_settings` — not a ScheduledAgent goal at all.
3. `qa.run_sweep` is a System B goal (`src/schedule.ts:52` in `DEFAULT_SCHEDULES`) with no in-worker executor (§9) — its real execution is an external script.
4. The 03:00 and 04:00 crons (token renewal enumeration; `mas_messages` retention) also dispatch through `scheduled()` to the shared orchestrator instance (`server.ts:3750-3755`), failing closed when no service identity is configured (`:3764-3777`).

**Ruling the evidence supports** (the decision itself is the programme's): ScheduledAgent owns the **user-visible goal catalogue** — singleton, budget-gated, UI-listed, cron-fired. Orchestrator self-scheduling owns **instance-local machinery** — turn follow-ups, per-user maintenance, NLQ ad-hoc schedules, async-job recovery — which is per-login state that cannot move into a singleton without changing its meaning. The anomalies (2) and (3) are catalogue-shaped work living outside the catalogue; the ruling should either move them into System B as goals or record them as System A exceptions with reasons. Consolidating A into B wholesale is contradicted by the state shapes: A's schedules are keyed by, and fire as, the per-login instance itself.

**Can both bindings name class `OrchestratorAgent` after the rename?** Yes as a configuration shape: a binding is a namespace; `class_name` is the implementation, and multiple bindings may reference one class **[platform docs]**. There is no repo precedent today (every binding has a distinct class_name, `wrangler.jsonc:48-75`), but semantically it merely makes today's arrangement — one class exported under two names, bound twice — honest: two namespaces, one class.

**What happens to existing SEARCH_AGENT instances/state?** Under a `renamed_classes` migration, the class registration is renamed in place: existing instances keep their ids and their storage — that is the documented purpose of `renamed_classes` versus delete-and-recreate **[platform docs]**. Per-login chat instances (id = login) and the fixed addresses (`default_trader`, `system_webhook_receiver`, …) are instance names within the namespace and are unaffected by the class rename.

**⚠ The collision the issue does not mention**: `OrchestratorAgent` is **already a registered class** — migration v9 (`wrangler.jsonc:88-89`) created it as a separate class with its own namespace behind the `ORCHESTRATOR_AGENT` binding. Renaming `SearchAgent → OrchestratorAgent` therefore targets a name that already exists as a distinct class registration. Whether wrangler accepts a rename onto an existing class name is **not established by anything in the repo**, and it is not a documented rename pattern **[platform docs: renamed_classes renames a class to a new name; the onto-existing-name case is not covered]**. The G0 slice must resolve this BEFORE merge — e.g. by proving the exact migration set in a preview deploy (the programme already makes Build & Deploy part of the rename's gate) — and must not discover it on the production deploy. A related unknown the slice must establish: whether any live instances hold state in the ORCHESTRATOR_AGENT namespace (sub-agent root dispatches resolve stubs there); code evidence can neither confirm nor deny it.

## §6 Contradictions + slice candidates

### 6.1–6.10 Contradictions (programme/problem-statement claims vs code)

1. **Fibers**: the programme says fibers "exist only as the durableFibers service" — accurate. But the service's own header claims durable checkpointing **and an `onFiberRecovered` resume hook** (`durableFibers.ts:9`); neither exists (checkpoints are write-only; the hook's only occurrence in `src/` is that comment). Any G7 Fibers cell that reads "IMPLEMENTED (durableFibers)" would inherit a false claim — the honest cell is GAP for every agent, with the service recorded as a checkpoint-logging preview helper.
2. **Attestation**: G14's premise "the codebase already has one attestation pattern" is half true. The pattern (proposer/authorizer/executor DID triple on payment drafts) exists; the proof does not — `createDidAttestation`'s signature is an unkeyed SHA-256 of the payload (`did.ts:236`), the sync variant's is a 32-bit non-cryptographic hash (`did.ts:289`, `:302-310`), the DID document's `publicKeyMultibase` is derived from that same weak hash of the DID string itself (`did.ts:71`), and **no verify function exists**. Unifying the pattern as-is would standardize a checksum and call it attestation.
3. **PaymentWorkflow status**: its header (`paymentWorkflow.ts:28-34`, dated 2026-10-27) says no route calls it; four call sites do (§3.3), gated by a default-OFF flag. The programme's problem statement ("only the payment flow starts its workflow today, from orchestrator-mounted routes") is the correct version.
4. **SlackAgent's header** claims the class "has no wrangler DO binding, so it is unreachable in production" (`slackAgent.ts:13-16`) — stale since #2215 bound `SLACK_AGENT` in the same base the header ships in (`wrangler.jsonc:75`). The substance (never instantiated) stands; the stated reason is wrong.
5. **"Chat trading runs in-process"** is true but incomplete in a way that matters for G4: TradingAgent's proposal services are ALSO unreachable from chat — chat doesn't merely bypass the workflow, it bypasses the agent entirely. G4 is a first-caller slice for the agent, not only for the workflow.
6. **The self-healing loop's in-worker half is dormant**: `handleQAFailure` has no caller (§9). G13's "mesh failures feed the existing QA self-healing loop, which already files issues from failures" — today the filing is done by an external script (`scripts/qa-smoke.mjs`), and the loop's trigger surface is a schedule goal (`qa.run_sweep`) with no in-worker executor. G13 builds on a loop whose in-worker trigger must first be made real.
7. **MAS ≠ chat tools**: programme-adjacent descriptions treat MAS tools as the chat toolset; at this base the turn's tools are the MCP command set and MAS's only production constructor is a SearchHub route (§1). G1/G12 scoping must treat MAS as a route surface or explicitly promote it — not assume it is already in the turn.
8. **G2 is narrower than it reads**: synchronous screen routes already adopt ScreenerScreenWorkflow (opt-in). The un-adopted path is specifically chat/NLQ (§3.4). The slice is a port change, not a workflow build.
9. **Orchestrator A2A surfaces are not agents**: the cards/catalog name search/tasks/memory/nlq as if they were dispatchable agents; they are surfaces of one class on one namespace (#2223 §6.4). The G0 registry must model them as surfaces, or G12 will re-encode the confusion.
10. **The `"default"` identity fallback is a family** (§2 headline 8): G8/G14 retirement scoped to `runDiscovery` alone would leave the orchestrator's stub default (`orchestrator.ts:593`), the seven propagation sites, PaymentsAgent's attribution default, and the DID `"anonymous"` derivations in place.
