## How to read this

- **One row per method+path**, except PUT/PATCH alias pairs on the channel-admin routes, which share one row (identical body, interchangeable in code). **150 rows total.**
- **Route** shows the canonical `/api/…` spelling. The commercial family also answers the bare spelling (`/payments/agentic/commercial/*`, alias — `src/server/routes/platform.ts:472`, `src/data/commercialUrlCatalog.ts:7-11`). Handlers match with `path.endsWith(...)`, so both spellings hit the same block.
- **Registration** = the line where the path is matched. There is no route table: matching is sequential `if` chains (see §F2). **Handler** = where the work happens; most commercial/legacy blocks are inline in the matching function, so both columns point at the same line.
- **★** in Response = an ID, URL, or token the caller can chain from.
- **Gate legend** (all gates fail closed):
  - `EDGE-SESS` — Worker edge requires a session (`requireAuth`, 401) before dispatch; the verified login rides the `x-user-login` header.
  - `SESS` — handler requires a verified login via `commercialLogin()` (`src/agents/routes/agenticPayments.ts:841`, reads `x-user-login`).
  - `OP` — store operator: `isStoreOperator()` (`agenticPayments.ts:875`) = env `COMMERCIAL_STORE_OPERATORS` ∪ D1 store operator list; empty = deny all.
  - `OWN/OP` — account owner or store operator: `canAccessAccount()` (`agenticPayments.ts:911`).
  - `FLAG` — monetization flag ON via `requireMonetization()` / FeatureFlagPort (`agenticPayments.ts:1077`).
  - `ADMIN` — platform-admin membership via IAAA (`isPlatformAdmin` over the membership store; wired-login alias required).
  - `SIG` — webhook signature verification, no login. `TOKEN` — signed token, no login.
- **Client caller** = a caller found in `src/client` (panels, `*Api.ts`, or direct `fetch`) or a named internal caller. "— none found" means no caller was found by grepping `src/` for the route id, the `commercialPath("…")` id, and the path literal (tests excluded). Absence here means *no caller found by those searches*, not proof none exists outside `src/`.
- Response shapes marked "not fully enumerated" name the file/function that settles them.

## Dispatch in one paragraph

`src/server.ts` `handleFetch` runs family handlers in order. The payments family (`src/server/routes/platform.ts:472-530`, `handlePlatformPaymentsRoutes`) requires a session and forwards `/api/payments/agentic/*` + the bare commercial alias to the caller's OrchestratorAgent DO instance (path prefix `/api` stripped); `/api/premium/*` forwards with anonymous traffic on a dedicated gateway instance; `/api/payments/webhook` + `/payments/webhook` forward to the `system_webhook_receiver` instance with no session. Everything else under `/api/` falls through (`src/server/routes/core.ts:156`, session or service token required) to the same DO, where `src/agents/orchestrator/routeRequest.ts` runs per-module handlers in a fixed sequence (payments → assurance → agentic-payments → platform users/tenants/accounts/channels → premium, `routeRequest.ts:463-560` approx). Saga routes are mounted earlier, at the Worker edge (`src/server/routes/messaging.ts:217-247`). Full dispatch + shared-layer verdict in §F2.

## F2 — Shared-layer check: is there a separately designed "CBO API" layer?

**Verdict: no.** There is no separately designed "CBO API" layer, no shared commercial/platform router module, no API versioning on any commercial/platform route, and no OpenAPI description of the commercial routes. What exists instead is (a) a path catalog, (b) a hand-rolled sequential dispatcher, and (c) an OpenAPI *spike* whose pilot coverage excludes the commercial family. Details with file:line:

### What exists

1. **Path catalog, not a router — `src/data/commercialUrlCatalog.ts`.** `COMMERCIAL_ROUTES` (one entry per catalogued route: id, methods, bare path, match suffix) is the single source of truth for commercial *paths* only. The dispatcher, handlers, and clients derive paths from it; a pin test (`tests/commercial_url_catalog_2846.test.ts`) fails on hardcoded commercial literals or handler/catalog drift. It performs no routing, no auth, no versioning, and it does NOT cover the 10 parameterized routes in Group C (matched by `includes` + segment parsing) or any non-commercial group.
2. **Static endpoint catalog for the IAAA explorer — `src/client/iaaaEndpointCatalog.ts`.** Static code knowledge "derived by reading the sources" (header :1-24). The entire commercial family is ONE entry (`id: "payments-agentic"`, :1209) carrying the two dispatcher prefixes — not per-route entries. It serves a read-only panel, not requests.
3. **OpenAPI spike, pilot coverage only — `src/security/openapiSpec.ts`.** Generates an OpenAPI 3.x document from the IAAA catalog (#1024 Phase 1, "no framework change… this module only DESCRIBES it", header :1-8). Hand-written schemas exist for the pilot set only (GET `/api/me`, `/health`, `/api/iaaa/overview`) plus the stock set (#2860 Factor 13); every other path carries an explicit "schema: not yet specified (spike pilot coverage)" marker. Served session-gated at GET `/openapi.json` + GET `/api/docs` (`src/server/routes/core.ts:136`). No commercial/platform route has a schema in it (verified: zero matches for the commercial/tenant/account path strings in `openapiSpec.ts` and `src/api/openApiDrift.ts`).
4. **Ingress guards, explicitly not a router — `src/api/ingress.ts` (#1768).** Uniform throttle keying, identity-header stripping, webhook signature header names, WS burst caps. Its header names the non-coverage: "it does not extract the handleFetch if-else chain into a router table — that refactor is the follow-up" (:14-17).
5. **Ingress route table, narrow scope — `src/api/openApiDrift.ts:31` (`API_INGRESS_ROUTES`).** Covers WS + webhook + quote + gated search only (14 entries). The only commercial-adjacent entries are POST `/api/payments/webhook` and POST `/payments/webhook` (auth: signature). The drift check validates the generated spec against this table — it is not a request router.

### How routes are actually dispatched (no central router table)

1. **Worker edge — `src/server.ts`, `handleFetch`.** A sequential chain of family handlers (`src/server/routes/*.ts`), each returning a `Response` or `null`. Order relevant here: saga (`handleMessagingSagaRoutes`, `src/server/routes/messaging.ts:217-247`, mounted first, session via `requireAuth`) → payments family (`handlePlatformPaymentsRoutes`, `src/server/routes/platform.ts:472-530`, called from `server.ts:214`) → `/openapi.json` + `/api/docs` and the generic `/api/*` fallthrough (`handleCoreLateRoutes`, `src/server/routes/core.ts:136-156`, session or service token, then forward to the OrchestratorAgent DO).
2. **Payments-family edge dispatch (`platform.ts:472-530`).** `/api/payments/agentic/*` + bare `/payments/agentic/commercial/*`: session required (401), `/api` prefix stripped, forwarded to the DO instance named by the session login. `/api/premium/*`: session when present, else the dedicated `PREMIUM_GATEWAY` instance with identity headers stripped. Webhooks: no session, forwarded to `system_webhook_receiver`.
3. **DO thin router — `src/agents/orchestrator/routeRequest.ts`.** "Thin-router wiring — routeRequest delegates to route modules only" (`67beca31a`, #380). `routeRequest` calls per-module `handle*Routes` functions in a fixed sequence; each module runs its own sequential `path.endsWith` / `path.includes` `if` chain and returns `null` on no match. Commercial-relevant mounts in order: `handlePaymentsRoutes` → `handlePaymentAssuranceLiveRoutes` → `handleAgenticPaymentsRoutes` → `handlePlatformUsersRoutes` → `handlePlatformTenantRoutes` → `handlePlatformAccountRoutes` → `handlePlatformChannelRoutes` → `handlePremiumRoutes` (plus `handleMeterRoutes` earlier in the sequence, :301). There is no shared middleware, no shared auth wrapper, and no shared response envelope at this layer: each block repeats its own `commercialLogin()` / `isStoreOperator()` / coded-response calls (the shared pieces are the *helpers* inside `agenticPayments.ts` — `commercialLogin` :841, `isStoreOperator` :875, `canAccessAccount` :911, `requireMonetization` :1077, `codedOutcomeResponse` :446 — plus the outcome catalog `src/outcomes/outcomeCatalog.json` for response codes).
4. **Client side.** No generated client and no shared API client module for the commercial family: each `src/client/*Api.ts` module (and several panels directly) builds paths from `COMMERCIAL_API_BASE` / `commercialPath(id)` and calls `fetch`/`apiFetch` itself. The catalog guarantees path consistency, not interface consistency.
